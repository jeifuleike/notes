# Migration数据库迁移

补充专题：Migration数据库迁移。本文为通用学习知识，示例和实验不表示已经执行到项目数据库。项目运行与验收仍在独立代码仓库维护。

## 1. Migration：让已有数据库有序演进

### 1. 为什么不能只留最终 CREATE TABLE

第一次建库只需创建初始结构，但以后会出现新增字段、补唯一约束、重建索引等变化。

```text
开发库：已有 users 和 projects
测试库：还没有新增字段
生产库：有大量旧数据
```

仅有最新版建表语句，不能说明怎样把旧库升级过来。Migration 是记录并执行数据库变更的机制；它不只是“把数据搬到另一台机器”。

### 2. 变更文件和执行记录

一个简单的有序迁移方案可能是：

```text
001-create-users.sql
002-create-projects.sql
003-create-project-members.sql
004-create-tasks.sql
005-add-task-description.sql
```

```sql
ALTER TABLE tasks ADD COLUMN description TEXT NULL;
```

迁移器判断当前版本，只执行尚未应用的变更，并在执行后记录结果。上面的文件命名是本例约定，不是所有工具都必须采用相同实现。

| 记录信息 | 用途 |
| --- | --- |
| 迁移标识 | 确认哪些变更已经执行 |
| 应用时间 | 排查发布顺序 |
| 校验和（若实现） | 发现已应用文件被修改 |
| 状态或修复信息（若实现） | 处理执行失败与人工修复 |

已经共享或应用的迁移不要直接改内容，后续变化新增迁移；否则相同文件名可能在不同环境代表不同结构。

### 3. 数据迁移与结构迁移

结构迁移负责列、索引、约束；数据迁移可能需要把旧 status 值映射为新值、回填新字段、清理重复关系。

例如新增必填 project_code，不应直接假设已有百万条记录都有合法值。可采用：先允许 NULL → 分批回填唯一值 → 校验 → 加唯一与非空约束。

### 4. 扩展、迁移、收缩

把 name 改成 display_name，直接重命名可能让仍在运行的旧版应用出错。可按需求设计：

```text
增加兼容的新列
  ↓
部署兼容代码，明确新旧字段写入规则
  ↓
分批回填并核对
  ↓
切换读取，确认旧版本不再依赖旧列
  ↓
最后删除旧列
```

双写和回填之间也可能竞争，需要设计顺序、幂等和校验，不能认为“写两列”天然可靠。

### 5. MySQL DDL 的特殊边界

MySQL 中许多 DDL 触发隐式提交，不能把整个迁移目录放进一个普通事务，就宣称任何失败都会全部回滚。[隐式提交](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)

支持的原子 DDL 主要保证单个 DDL 的内部一致性与故障恢复，不表示用户可以 ROLLBACK 任意 DDL，也不表示 DDL 与迁移记录插入自动组成一个事务。[原子 DDL](https://dev.mysql.com/doc/refman/8.4/en/atomic-ddl.html)

如果 ALTER 成功，而写迁移记录之前程序崩溃，重跑时可能遇到“结构已变、记录未写”的状态。应先检查真实 schema，再按工具规则修复，不能删库重建或假填成功记录。

Online DDL 不等于没有锁、没有等待和没有资源开销，具体能力取决于版本、变更类型及算法。[Online DDL](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl.html)

### 6. 本学习项目的迁移器边界

项目的 lab-kit 迁移器显式列出文件顺序，使用 schema_migrations 记录已执行名称，通过 GET_LOCK 协调参与同一约定的初始化进程；每个文件限定一条 DDL。

当前实现没有文件校验和，也不提供“任意失败自动 down 回滚”。GET_LOCK 是会话级命名锁，不能理解成数据库自动禁止所有其他客户端改表。通用概念要和实际工具具备的能力分开。

### 7. 迁移检查清单

- 能从空库建立预期结构，也能从已有旧版本升级。
- 在有代表性的旧数据上检验重复、空值和约束冲突。
- 预估执行时间、锁等待、额外空间和应用兼容窗口。
- 明确备份、故障修复和恢复路径；不是所有 down 都能还原被删除的数据。
- 确认不会由多个不协调进程同时执行同一迁移。
