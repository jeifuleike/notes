# 分布式数据库

数据库学习主线的最后一篇。先理解事务、锁和缓存；本文建立多节点概念，不要求现在部署集群。

## 1. 从单机到多节点，究竟改变了什么

单机数据库中，应用主要面对一个数据库实例管理的数据与事务。分布式数据系统把存储、复制或计算放到多个节点上，需要通过网络协调。

```text
应用
  ↓
访问入口 / 路由
  ├─ 节点 A
  ├─ 节点 B
  └─ 节点 C
```

节点可能保存相同数据，也可能各自保存不同数据，甚至同时采用两种方式。节点数不能单独说明系统能力，必须问“数据如何分布、写入怎样确认、故障后如何处理”。

MySQL 配上 Redis 缓存是一个使用多个数据服务的应用架构，不能因此断言它拥有一个统一的跨节点数据库事务。

## 2. 为什么考虑分布式

| 目标 | 要解决的问题 | 可能的代价 |
| --- | --- | --- |
| 高可用 | 一台机器故障后继续提供服务 | 故障检测、切换及数据安全设计 |
| 扩展读取 | 单实例读压力过大 | 副本延迟、读路由复杂度 |
| 扩展存储或写入 | 单节点资源不足 | 分片、跨片查询和事务 |
| 地域部署 | 数据靠近不同地区用户 | 跨区延迟、一致性与成本 |

先定位瓶颈。慢 SQL、错误索引或无界查询，不会因为换成多节点就自然消失。缓存也不能直接解决所有持续写入容量问题。

## 3. 复制：同一份数据保存多份

```text
写入 → 主节点
          ↓ 复制修改
       副本 1、副本 2
```

复制常用于冗余与读取扩展。不同系统有不同复制协议，不能用某一种产品的行为概括所有数据库。[MySQL 复制文档](https://dev.mysql.com/doc/refman/8.4/en/replication.html)

### 异步与同步等待

异步复制下，主节点可能在副本应用变更之前就向客户端返回成功。因此：

```text
用户改名，写主节点成功
  ↓
立即从尚未追上的副本查询
  ↓
仍看到旧名字
```

如果某种同步方案等待副本确认，还要问：确认收到日志、持久化，还是已经应用？不同确认点对应不同保证和延迟，不能仅凭“同步”二字判断。

### 读写分离

常见做法是写主节点、部分读副本。需要“刚写完立即读到”的流程可以按系统能力选择读主节点、等待复制位置或其他一致性机制。

副本会同步删除和错误修改，因此副本不是历史备份。备份、时间点恢复和复制分别承担不同任务。不同高可用及复制方案的权衡可参考 [PostgreSQL 官方比较](https://www.postgresql.org/docs/current/different-replication-solutions.html)。

## 4. 分片：不同节点保存不同部分

```text
按租户路由：
tenant A 的数据 → 分片 1
tenant B 的数据 → 分片 2
tenant C 的数据 → 分片 3
```

复制回答“同一数据有几份”；分片回答“这条数据归谁管理”。每个分片又可以有自己的多个副本，两者不是替代关系。

### 分片键为什么重要

按 tenant_id 分片，某租户的大部分查询可以落在一个分片内。但全站统计可能需要访问所有分片；一个特别大的租户也可能造成热点。

常见策略包括哈希分布与范围分布。哈希可能有利于分散负载，范围可能有利于相邻数据访问；两者都要考虑热点与扩容迁移。

### 新出现的设计问题

- 查询条件没有分片键时，是否需要广播到多个节点？
- 两个分片中的数据如何 JOIN、排序和分页？
- UNIQUE、外键和 ID 的唯一性由谁在什么范围内保证？
- 增加节点后，数据如何迁移，路由如何平滑切换？
- 节点迁移或故障时，正在执行的事务怎么办？

不能把单库的自增 ID、外键或事务边界直接照搬到任意手工分库架构。

## 5. 高可用：副本存在不等于自动安全切换

高可用还需要检测故障、选择可接管节点、更新路由，并防止失去资格的旧主节点继续接收冲突写入。

网络断开时，节点可能仍在运行，只是其他节点联系不到它。“联系不到”与“确定已经关闭”不同，这也是故障判断困难的原因。

MySQL InnoDB Cluster 集成 Group Replication、管理工具及路由等能力，但它不等于自动把一张业务表分片到多个节点来提升全部写入吞吐。[InnoDB Cluster](https://dev.mysql.com/doc/refman/8.4/en/mysql-innodb-cluster-introduction.html)

评价故障方案时至少问：可接受丢失多少已确认数据、最多中断多久、如何验证恢复后的数据。这些往往用 RPO（恢复点目标）与 RTO（恢复时间目标）表达。

## 6. 多数派与共识：先理解用途

某些系统使用 Raft 等协议，在一个复制组内对日志顺序达成一致。简单的三投票副本组通常需要两个副本形成多数，才能继续提交相应写入；具体还受配置、成员变更及产品实现约束。

```text
3 个投票副本，1 个故障 → 可能仍有多数
3 个投票副本，2 个故障 → 失去多数，相关写入通常不能继续
```

多数派机制帮助限制冲突决定，但不是所有副本在任意时刻都已经应用到相同位置。也不能从“用了 Raft”直接推导整个数据库所有隔离级别与跨分片事务语义。[CockroachDB 复制层说明](https://docs.cockroachlabs.com/docs/stable/architecture/replication-layer)

## 7. 一致性：要问清具体保证

ACID 中的一致性主要围绕数据约束与业务不变量；分布式读取一致性关心一次写入之后，不同读取会以什么顺序观察到结果。两处使用同一个中文词，关注点并不完全相同。

需要逐项问：

- 写成功后，下一次读是否保证读到它？
- 从不同副本读取是否可能先见新值、再见旧值？
- 一组事务能否表现得像按某种顺序逐一执行？
- 哪些场景允许旧值，允许多久，如何观察和修复？

最终一致性不等于“随便写，迟早正确”，系统仍需要传播与冲突处理机制。强一致性也不是“所有请求零等待”，网络与协调可能增加延迟，故障下也可能拒绝操作。

## 8. 跨节点事务为什么更复杂

```text
转账：分片 A 扣款，分片 B 入账
  ↓
A 已完成，B 超时
  ↓
B 没执行、执行失败，还是已成功但响应丢失？
```

普通 MySQL 单连接事务不能自动跨多个独立实例回滚。分布式事务需要额外协议或数据库自身提供的协调能力。

两阶段提交等机制协调参与者的提交决定，但仍要结合故障恢复、超时、锁与持久化设计理解。Saga 等业务补偿方案通过额外动作修正结果，不等价于数据库瞬间撤销全部可见影响。

有些分布式 SQL 数据库集成分布式事务，但应用仍需理解冲突重试、隔离级别和延迟。[CockroachDB 事务层](https://docs.cockroachlabs.com/docs/stable/architecture/transaction-layer)

## 9. 为什么重试必须配合幂等

请求超时，调用方可能无法确定操作是否已执行。立即重试一次扣款，有可能扣两次。

幂等设计让同一业务请求被重复提交时，不重复产生业务效果，例如用唯一业务请求号记录处理结果，并将记录与相关写入放到合适的事务边界内。

“最多重试三次”限制次数，不保证幂等；“消息系统会投递”也不保证消费者只产生一次结果。要明确重复、乱序、丢失、确认与重放的处理方式。

## 10. 分布式数据库与应用手工分库

| 方案 | 应用通常承担什么 |
| --- | --- |
| 多个独立库，由应用路由 | 路由、跨库操作和不少故障处理 |
| 中间件协调分片 | 了解中间件支持与不支持的查询、事务范围 |
| 集成分布式 SQL 系统 | 使用统一入口，同时理解事务、热点和资源边界 |

例如 TiDB 将 SQL、存储和调度等职责分给不同组件，对外提供统一访问能力。兼容某种 SQL 协议不意味着所有行为、性能及运维方式都与原数据库完全相同。[TiDB 架构](https://docs.pingcap.com/tidb/stable/tidb-architecture/)

## 11. 现阶段怎么学

先做纸面推演，不急于搭建集群：

1. 画出一主两副本，解释一次更新如何传播、为什么可能读旧值。
2. 按租户划分两个分片，分别推演租户查询与全站统计。
3. 推演主节点失联但未停止写入时的风险。
4. 推演转账的响应丢失，说明为什么“超时”不能直接等于“未执行”。
5. 对一个真实慢接口先分析 SQL、索引与缓存，再判断是否需要增加节点。
