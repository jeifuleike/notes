# 数据库疑问解答

---

## 1. MySQL 是不是比较垃圾？大型企业通用的是啥，比如淘宝那种

**结论：不是垃圾，但确实不是"大型企业唯一选择"。**

- MySQL 是企业里用得最广的数据库之一，淘宝早期就是用 MySQL（+ 分支 AliSQL），Facebook、Twitter、YouTube、GitHub、美团、京东……大量用 MySQL。
- 说它"垃圾"通常指它的**默认配置和默认引擎**：
  - 默认存储引擎如果是 MyISAM → 不支持事务、行锁，几乎没人用在生产了。
  - 默认字符集以前是 latin1 → 中文乱码。
  - 但换成 InnoDB + utf8mb4，MySQL 撑起日活过亿的系统没问题，关键在**架构**而非数据库本身。

**"淘宝那种"实际是什么？**
淘宝不是单库单表，是**分库分表 + 中间件 + 缓存**的组合拳：
- 早期：MySQL 主从 + 分库分表中间件（Cobar/TDDL）
- 现在：自研分布式数据库（OceanBase，淘宝系自研，已开源）
- 缓存：Redis 扛读
- 搜索：Elasticsearch

**主流数据库格局（分类理解）：**

| 类型 | 代表 | 适用场景 |
|------|------|----------|
| 关系型 / 传统 OLTP | MySQL、PostgreSQL、Oracle、SQL Server | 交易、业务数据，90% 场景 |
| 分布式关系型 / NewSQL | OceanBase、TiDB、CockroachDB | 海量数据、强一致 + 水平扩展 |
| NoSQL - 文档 | MongoDB | 结构灵活、半结构化数据 |
| NoSQL - KV | Redis、etcd | 缓存、会话、计数 |
| NoSQL - 列式 | HBase、Cassandra | 海量写入、时序 |
| 分析型 OLAP | ClickHouse、Doris、StarRocks、Snowflake | 数据分析、报表 |
| 搜索引擎 | Elasticsearch、OpenSearch | 全文检索、复杂查询 |
| 嵌入式 | SQLite | 单机、本地、App 内置 |
| 图数据库 | Neo4j | 社交关系、知识图谱 |

**一句话**：MySQL 是"够用的主力选手"，不是"垃圾"；大厂是在 MySQL 之上叠架构，或换成 NewSQL。

## 2. 有哪些数据库是必学的

**必学（面试 + 工作都绕不开）：**
1. **MySQL** —— 关系型基本盘，后端岗位必考
2. **Redis** —— 缓存/KV 基本盘，几乎每个后端岗位都要求
3. **PostgreSQL** —— 越来越主流，功能强（JSON、GIS、全文检索），很多公司用它替代 MySQL

**按方向选学：**
- 做后端/Java/Go：MySQL + Redis +（PostgreSQL 或 一个 NewSQL）
- 做大数据：ClickHouse / Doris / Hive + Spark（Hive 严格说是数仓不是数据库）
- 做搜索/日志：Elasticsearch
- 做 Node/前端全栈：SQLite（本地）→ MySQL/PostgreSQL（服务端）
- 追求技术广度：MongoDB（了解文档模型）

**学习顺序推荐：** MySQL（SQL 基础 + 索引 + 事务 + 锁）→ Redis（缓存与数据结构）→ PostgreSQL（对比着学更有收获）→ 选一个 OLAP（ClickHouse）会用即可。

**核心建议**：先吃透 MySQL 一个，把索引、事务隔离级别、锁、慢查询优化搞明白，其他数据库都能触类旁通。**"会十个"不如"精通一个 + 了解其余"**。

## 3. 字段类型里有 float 浮点型？怎么没看到

在 MySQL 里，浮点类型有三个，容易忽略的是它们的**精度差异**：

| 类型 | 精度 | 字节 | 说明 |
|------|------|------|------|
| `FLOAT` | 单精度（约 6-7 位有效数字） | 4 | 有误差 |
| `DOUBLE` | 双精度（约 15-16 位有效数字） | 8 | 有误差 |
| `DECIMAL(M,D)` | 定点，精确 | 变长 | 无误差，M 位总长 D 位小数 |

**关键：money 钱不要用 FLOAT/DOUBLE！**

浮点数在二进制里无法精确表示小数，典型坑：
```sql
SELECT 0.1 + 0.2;   -- 输出 0.30000000000000004
```

所以**金额、价格必须用 `DECIMAL`**：
```sql
price DECIMAL(10,2)   -- 最多 10 位数，其中 2 位小数
```

前端同样的问题用 `big.js` 处理（你项目经历里就写了这个）——本质是同一个原因。

**所以：** FLOAT 没看到，可能是你之前学的材料只讲了 INT/DECIMAL，或者介绍时跳过了。记住：**整数用 INT/BIGINT，金额用 DECIMAL，科学计算/非精确值才用 FLOAT/DOUBLE**。

## 4. 外键会随引用表变化而变吗？外键能做别的表的主键吗？

**前半句：外键的值不"自动跟着变"，但受约束。** 分两种情况：

- **被引用表删了某行** → 外键表如果不加规则会报错；可以用 `ON DELETE`/`ON UPDATE` 规则自动处理：
  ```sql
  FOREIGN KEY (user_id) REFERENCES users(id)
    ON DELETE CASCADE      -- 删用户，订单也删
    ON UPDATE CASCADE      -- 用户 id 改了，订单里的 user_id 也跟着改
  ```
  不加 `ON UPDATE CASCADE` 时，你去改被引用表的主键值 → 直接报错（因为会破坏引用完整性）。
- **被引用表的主键值本身改了** → 只有配了 `ON UPDATE CASCADE` 才自动同步，否则禁止改。

**后半句：外键可以做别的表的主键。** 这叫"外键兼主键"，典型是**一对一关系**：

```sql
CREATE TABLE users (id INT PRIMARY KEY, ...);
CREATE TABLE user_profiles (
  user_id INT PRIMARY KEY,                     -- 既是主键，又是外键
  FOREIGN KEY (user_id) REFERENCES users(id)
);
```
好处：一个用户只能有一条 profile（主键唯一），同时强制必须对应一个存在的用户。

**补充：** 现在很多互联网公司**不用物理外键**，改在应用层维护关系。原因是分库分表、高并发下物理外键的锁和外键检查影响性能。但**学习阶段一定要懂外键**，面试也会问。

## 5. 第二范式那个例子没看懂

先纠正你的一个理解偏差：**`order_items` 表可以有多个 `order_id` 相同（一个订单多个商品）**，你理解的"一个 order_items 就有一个 order_id"是对的，但一个 `order_id` 对应的**是它这一行自己的数据**，和 `order_created_at` 无关。

第二范式（2NF）的核心：**非主键列必须完全依赖主键，不能只依赖主键的一部分（消除部分依赖）**。这只有**联合主键**时才可能违反。

**例子：** 假设 `order_items` 主键是 `(order_id, product_id)` 联合主键：

| order_id | product_id | quantity | product_name | **order_created_at** |
|----------|-----------|----------|--------------|---------------------|
| 1 | 100 | 2 | 苹果 | 2026-05-01 |
| 1 | 101 | 1 | 香蕉 | 2026-05-01 |
| 2 | 100 | 3 | 苹果 | 2026-06-01 |

这里 `order_created_at` 只依赖 `order_id`（订单创建时间），**不依赖 `product_id`**。也就是说它只依赖了**联合主键的一部分** → 违反 2NF。

**为什么是问题？** 同一个订单的每一行都重复存一样的订单创建时间，改起来要改多行，浪费空间还容易不一致。

**正确做法：** 把 `order_created_at` 放回 `orders` 表（它在那里才完整依赖 `order_id`）：

```
orders       (order_id PK, order_created_at)
order_items  (order_id, product_id, quantity, product_name)  -- PK(order_id, product_id)
```

你理解的"order_created_at 是 orders 层级的"——**完全正确，就是这个意思。** 你觉得奇怪，只是因为原例子没把"联合主键"这个前提讲清楚。

一句话记法：**只依赖联合主键的一部分 → 该列挪到它完整依赖的那张表去。**

## 6. 索引是想建几个建几个吗？全上索引会怎样？

**不是。索引是"空间换时间"，有明确代价。**

建索引会带来：
1. **占空间**：每个索引都是一份额外数据结构（B+树），数据多时索引可能比数据还大。
2. **拖慢写**：每次 INSERT/UPDATE/DELETE 都要同步维护所有索引 → 表上 10 个索引，一次写入改 11 处（表 + 10 索引）。
3. **优化器可能选错索引**：索引太多会干扰查询优化器的判断。

**"全上索引会怎样？"** → 读可能快一点，但**写入性能断崖式下降**，磁盘暴涨，得不偿失。

**该给谁建索引：**
- 主键（自动）
- 频繁出现在 `WHERE`、`JOIN ON`、`ORDER BY` 的列
- 区分度高的列（性别这种只有 2 个值的**不适合**，区分度低）

**代价与收益的心法：**
- 读多写少 → 可以多建
- 写多读少（日志表）→ 少建
- 联合索引注意**最左前缀**：`INDEX(a,b,c)` 能用于 `a`、`a,b`、`a,b,c` 的查询，但单独查 `b` 用不上。

**面试高频**：`EXPLAIN` 看是否命中索引、回表、覆盖索引、索引失效场景（函数运算、`!=`、`like '%x'` 前置通配）。

## 7. transaction 是数据库自带的功能吗？SQL 怎么写？

**是的，事务（transaction）是数据库引擎自带的能力**（InnoDB 支持，MyISAM 不支持）。开发只需要"开启 → 执行 → 提交/回滚"。

**基础 SQL 写法：**
```sql
START TRANSACTION;   -- 或 BEGIN
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;              -- 成功提交
-- 出错则 ROLLBACK;  回滚，两条都撤销
```

你写的"xxx 减少后 xxx 增加"就是这个经典**转账**例子，用 `balance = balance - 100` 直接算，数据库保证这俩操作**要么都成功要么都失败**。

**ACID 四大特性：**
- **A 原子性**：全成功或全失败
- **C 一致性**：前后数据合法（如转账总额不变）
- **I 隔离性**：并发事务互不干扰（隔离级别：读未提交/读已提交/可重复读/串行化，MySQL 默认**可重复读**）
- **D 持久性**：提交后断电也不丢（靠 redo log）

**实务提醒（你问"还是写业务时注意设计"）——两者都要：**
- 数据库层面：用事务包住一组必须同生共死的操作。
- 业务/代码层面：事务要**尽量短**（别在事务里做网络请求、发消息），注意锁范围，避免死锁。
- 框架层：Java Spring 用 `@Transactional`，Node 用 `sequelize.transaction()` / `pg` 的 `BEGIN/COMMIT`。

**关键**：简单单条 SQL 自带原子性，不需要手动开事务；**多条语句要一起成功时才需要显式事务**。

## 8. 每次改表都写迁移文件，不是一大堆吗？改字段名和数据处理怎么办？

**你的担心是对的，但迁移（migration）恰恰是为了解决你担心的问题，不是制造问题。**

**为什么"一大堆迁移文件"反而更好：**
- 迁移文件是**追加**的，等于表的"修改历史（changelog）"。谁在什么时候为什么改了表，一眼能查（配合 git）。
- 团队协作时，每个人的数据库结构**靠迁移文件就能同步**，不用手工对表。
- 每个迁移有唯一时间戳 + 版本号，框架记在 `migrations` 表里，**不会重复执行**。
- 想快速了解当前结构，不看几十个迁移，而是直接看**表结构**或框架的 schema 文件（如 Prisma 的 schema.prisma、Django 的 models.py）——那是"当前真相"，迁移只是"怎么走到这里"。

**改字段名：** 光改建表 SQL **确实不行**（数据库不会因为你改代码就自动改表）。正确流程是**生成一个新迁移**：
```sql
-- 以 MySQL 为例
ALTER TABLE users CHANGE old_name new_name VARCHAR(50);
-- PostgreSQL
ALTER TABLE users RENAME COLUMN old_name TO new_name;
```

**已有数据怎么办**（你问的重点）——迁移不只是改结构，**可以在里面写数据转换逻辑**：
```sql
ALTER TABLE users ADD COLUMN full_name VARCHAR(100);
UPDATE users SET full_name = CONCAT(first_name, ' ', last_name);  -- 数据搬运
ALTER TABLE users DROP COLUMN first_name, DROP COLUMN last_name;
```
框架（Flyway / Prisma / Django / TypeORM）都支持你把"改结构 + 搬数据"写在**同一个迁移**里，一次跑完。

**大表改结构注意（实战）：** 几千万行的表直接 `ALTER` 会锁表很久，线上要用工具（`pt-online-schema-change` / `gh-ost`）做在线变更。

**一句话：** 迁移 = 数据库的 git 提交记录，改结构、搬数据都写进新迁移，别手工改生产库。

## 附：几个概念的通俗对照

| 概念 | 一句话 |
|------|--------|
| 主键 | 唯一标识一行，不能空、不能重复 |
| 外键 | 指向别的表的主键，保证引用有效 |
| 索引 | 书的目录，查得快，写索引要维护成本 |
| 事务 | 一组操作同生共死（ACID） |
| 范式 | 减少冗余的设计规范（1NF 原子、2NF 无部分依赖、3NF 无传递依赖） |
| 迁移 | 数据库结构的版本化变更脚本 |
