# 收集判定

## 提议门槛

主动提议前先过四个问题，至少两条为“是”才提议：

1. 离开当前项目、版本、这台机器，还成立吗？
2. 三个月后还会再用吗？
3. 能写成一句可执行的规则、方法或决策吗？
4. 现有笔记没有覆盖吗？

优先两类：

- 通用知识：原理、方法论、架构模式、决策框架、边界条件。
- 提效资产：可复用流程、脚本、模板、检查清单、工具配置。

## 值得沉淀

- 以后还会再用。
- 有明确结论、决策或根因。
- 能指导下一次行动。
- 有来源或经过验证。
- 与现有笔记有增量。
- 是一个可重复执行、输入输出稳定的流程。
- 是一个值得评估的 Skill 或工具。

## 不值得沉淀

- 一次性状态、临时命令输出。
- 只有过程，没有结论。
- 已有笔记完整覆盖。
- 无来源且无法验证。
- 纯情绪、纯日记、闲聊。
- 只是“看起来不错”，没有具体用途。
- 单次小修复、偶发环境问题、一次性命令输出。
- 只对当前文件或当前版本有效的改动。
- 踩坑事件本身，除非能提炼出可迁移的规则。

## 级别

| 级别 | 判断 | 产出 |
|---|---|---|
| L1 | 一句话、链接、临时想法 | 合并进旧笔记，或淘汰 |
| L2 | 文章、教程、原理 | 人读笔记 + 来源 |
| L3 | 工程约束、踩坑、决策 | 人读笔记 + AI 操作卡 |
| L4 | 反复执行、输入输出稳定 | AI 操作卡 + Skill 候选 |

## capture_reason

- `repeatable`：以后还会反复用到。
- `decision`：方案或取舍已经定下。
- `gotcha`：踩坑、根因、易错点。
- `source`：值得保留的外部资料。
- `workflow`：可重复执行的流程。
- `manual`：用户直接要求保存。

## 不确定时

留 L1，写清“为什么可能有用”。整理时再决定是否升级，不要一开始就写成长文。

## 落点

- 所有收集先写 `00-Inbox/`，一条一个文件，不写正式库。
- 不询问是否发布；批量整理时再决定去向。

## 提问格式

主动提议时先写三行，再问一句：

```text
要存什么：<标题>；<最多 3 条要点>
为什么值得存：<未来什么场景会复用>
去向：00-Inbox

要记到 00-Inbox 吗？
```

不能只问“要沉淀吗”。单次小修复直接不问。
