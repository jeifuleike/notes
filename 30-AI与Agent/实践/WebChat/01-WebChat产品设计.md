## 2. 项目背景

AI Agent 的核心能力依赖大模型推理，但对于个人开发者和开源项目而言，长期使用商业模型 API 会带来较高成本。尤其是在代码分析、文件处理、网页自动化和多轮工具调用等场景下，一次任务往往需要多轮模型交互，调用成本会被进一步放大。

本项目希望提供一个轻量、可扩展的本地 Agent 框架，通过统一的模型适配层和工具调用协议，支持开发者接入不同的大模型服务，并根据自身账号、额度和使用场景选择合适的模型来源。

项目重点不绑定具体模型厂商，而是关注 Agent 的执行流程、工具封装、权限控制、本地任务执行和结果反馈能力，帮助开发者以较低成本搭建自己的本地 AI 助手。

## 3.2 阶段二：核心架构搭建

在 Demo 验证通过后，完成产品核心架构拆分，形成可扩展的 Agent 基础框架。  

本阶段重点建设三层能力：  

1. UI 展示层  
   负责对话输入、任务状态展示、工具调用过程展示、确认弹窗、执行结果展示。  

2. Agent Runtime 层  
   负责任务调度、上下文管理、模型调用、工具选择、工具调用、结果回传、异常处理和流程控制。  模型接入能力需要同时支持 API Key 调用模式与 AI 页面会话接入模式，便于后续根据不同模型来源进行扩展。

3. Tool 工具层  
   负责封装具体可执行能力，例如文件读取、文件写入、命令执行、页面操作、接口请求等。  

阶段交付物：

## 4. 目标用户与使用场景

### 4.1 目标用户

本产品主要面向个人开发者、小团队开发者以及希望低成本使用代码 Agent 能力的技术用户，重点服务于本地代码分析、开发辅助、自动化任务执行和 Agent 能力验证等场景。

目标用户包括：

1.个人开发者

具备一定前端、后端或脚本开发能力，希望在本地使用低成本代码 Agent 工具，辅助完成代码理解、代码生成、问题排查和项目维护。

2.小团队技术负责人

希望以较低成本验证 AI Agent 在团队研发流程中的可行性，例如代码辅助、项目分析、文档生成、问题排查和自动化工具调用。

3.对模型调用成本敏感的用户

希望在不强依赖商业 API Key 的前提下，通过 AI 页面会话接入等方式，降低使用代码 Agent 的成本。

### 4.2 用户痛点

当前用户在使用 AI 辅助开发和代码 Agent 工具时，主要存在以下问题：  

1. 模型调用成本较高  
   现有代码 Agent 产品通常依赖商业模型 API，多轮任务执行会产生较高调用成本，个人开发者和小团队在长期使用时压力较大。  

2. 普通 AI 聊天工具缺少本地执行能力  
   用户虽然可以通过 AI 聊天获得代码建议，但仍需要手动复制代码、查找文件、修改项目、运行命令和验证结果，自动化程度不足。  

3. 项目上下文接入不方便  
   普通聊天工具无法直接读取本地项目结构，用户需要反复粘贴代码、报错信息和文件内容，沟通成本较高。  

4. Agent 工具调用能力不透明  
   现有部分 Agent 工具执行过程不够清晰，用户难以了解 Agent 做了什么、调用了哪些工具、修改了哪些文件、是否存在风险操作。  

### 4.3 核心场景

#### 场景一：本地代码理解

用户在桌面端应用中选择本地项目，并输入问题：

> “帮我看一下这个项目的主要结构。”
> “这个组件是干什么的？”
> “这个方法在哪里被调用？”

Agent 读取项目目录和相关文件后，输出项目结构说明、代码逻辑分析和关键文件说明。

预期结果：

- 用户能够快速理解项目结构；
- Agent 能够读取本地项目上下文；
- UI 能展示 Agent 的分析过程和引用文件。

---

#### 场景二：代码问题排查

用户输入报错信息或描述问题：

> “页面报 undefined，帮我看看可能是哪儿的问题。”
> “这个组件没渲染出来，帮我分析一下。”
> “build 报错了，帮我定位原因。”

Agent 根据用户描述读取相关文件，结合错误信息分析问题原因，并给出修复建议。

预期结果：

- Agent 能够根据问题定位相关文件；
- Agent 能够输出可理解的问题原因；
- 必要时能够建议修改方案或执行验证命令。

---

#### 场景三：基础工具调用验证

用户输入一个简单任务：

> “读取 package.json 看一下有哪些打包命令。”
> “帮我查看当前项目目录。”
> “读取这个组件文件并总结功能。”

Agent 通过 Tool 工具层调用文件读取、目录读取等基础工具，并将结果返回给模型继续分析。

预期结果：

- 跑通“用户输入 → 模型判断 → 工具调用 → 工具结果回传 → 最终回复”的 Agent 闭环；
- 验证 Tool 工具注册和调用机制；
- 在 UI 中展示工具调用过程。

---

#### 场景四：代码修改辅助

用户输入明确修改需求：

> “给这个组件加一个 loading 状态。”
> “把这个接口返回类型补完整。”
> “帮我优化一下这个方法的 TS 类型。”

Agent 读取相关文件，生成修改建议或 diff 方案。涉及文件写入时，需要用户确认后再执行。

预期结果：

- Agent 能根据上下文生成代码修改建议；
- 文件修改前展示变更内容；
- 高风险操作需要用户确认；
- 修改完成后输出修改摘要。

---

#### 场景五：命令执行与结果验证

用户希望 Agent 辅助执行命令：

> “帮我执行 build 看看有没有问题。”
> “跑一下 lint。”
> “执行打包命令并分析报错。”

Agent 在用户确认后执行本地命令，并将命令输出返回给模型分析。

预期结果：

- 命令执行前展示命令内容；
- 用户确认后再执行；
- 执行过程和结果在 UI 中展示；
- 执行失败时，Agent 能分析错误原因并给出建议。

---

#### 场景六：低成本模型接入验证

用户希望在不强依赖商业 API Key 的情况下体验代码 Agent 能力。

Agent 支持 AI 页面会话接入模式，并预留 API Key 调用模式。用户可以根据自身情况选择模型来源。

预期结果：

- 支持低成本模型接入方式；
- 验证 AI 页面会话驱动 Agent 流程的可行性；
- 为后续模型接入层扩展打基础。

## 6. 产品架构

产品采用桌面端应用 + Agent Runtime + Tool 工具层 + 模型适配层的基础架构。

### 6.1 架构分层

1. UI 展示层

   负责用户交互、任务输入、执行状态展示、工具调用过程展示、Diff 预览、命令输出、错误提示和最终结果展示。

2. Agent Runtime 层

   负责接收用户任务、维护任务上下文、调用模型、解析模型意图、选择工具、执行工具调用、处理工具结果、生成最终回复。

3. Model Adapter 层

   负责统一不同模型来源的接入方式，包括 API Key 调用模式和 AI 页面会话接入模式。对 Agent Runtime 暴露统一的模型调用接口。

4. Tool 工具层

   负责封装本地可执行能力，例如目录读取、文件读取、文件写入、代码搜索、命令执行等。工具需要定义名称、描述、参数 Schema、权限等级和执行方法。

5. Permission 权限层

   负责判断工具调用风险等级，并在文件写入、命令执行等高风险动作前触发用户确认。

6. Log 日志层

   负责记录任务执行过程、模型调用摘要、工具调用参数、工具执行结果、异常信息和用户确认记录。

### 6.2 核心模块

| 模块 | 职责 |
| ---- | ---- |
| App Shell | 桌面端窗口、路由、全局状态、应用配置 |
| Workspace Manager | 管理当前项目目录、目录树、文件索引 |
| Chat Panel | 承载用户输入、模型回复、任务状态 |
| Agent Runtime | 任务调度、上下文管理、模型调用、工具调用 |
| Model Adapter | 统一封装 API 模型和 AI 页面会话模型 |
| Tool Registry | 注册、查询和调用工具 |
| Permission Manager | 权限判断、确认弹窗、风险提示 |
| Diff Manager | 生成和展示文件变更 |
| Command Runner | 执行本地命令并返回输出 |
| Log Viewer | 展示任务执行过程和错误信息 |

### 6.3 数据流

基础数据流如下：

用户输入任务 → UI 创建任务 → Agent Runtime 接收任务 → Model Adapter 调用模型 → 模型返回工具调用意图 → Tool Registry 执行工具 → 工具结果返回 Agent Runtime → 模型基于结果继续推理 → UI 展示过程和最终结果。

涉及高风险工具时，流程需要增加权限确认：

模型请求工具调用 → Agent Runtime 判断权限等级 → UI 展示确认弹窗 → 用户确认 → Tool 执行 → 返回执行结果。

### 6.4 技术边界

一期不要求模型完全自主控制桌面环境。Agent 只能通过已注册工具执行明确能力，不能绕过 Tool 层直接操作系统。所有文件写入和命令执行必须经过权限确认。

## 7. 核心流程

### 7.1 创建任务流程

1. 用户在对话区输入任务。
2. UI 创建任务记录，状态为 `pending`。
3. Agent Runtime 接收任务，状态变更为 `running`。
4. Agent Runtime 组装上下文，包括用户输入、当前项目目录、已读取文件摘要、历史工具调用结果。
5. Model Adapter 调用模型或 AI 页面会话。
6. 模型返回普通回复或工具调用意图。
7. 如果是普通回复，UI 展示结果，任务结束。
8. 如果是工具调用，进入对应工具流程。
9. 工具结果返回后，Agent Runtime 将结果追加到上下文。
10. Agent Runtime 再次调用模型生成下一步动作或最终结果。
11. 任务完成后状态变更为 `success`。
12. 若流程中出现异常，状态变更为 `failed`，并展示错误原因和可选建议。

### 7.2 文件读取流程

1. 模型判断需要读取文件或目录。
2. Agent Runtime 调用 `read_file` 或 `list_directory` 工具。
3. Tool 层校验路径是否在当前项目目录内。
4. 读取文件内容或目录结构。
5. 对大文件进行截断或摘要处理，避免上下文过长。
6. 将读取结果返回 Agent Runtime。
7. UI 在工具调用记录中展示读取文件路径、读取状态和摘要。
8. 模型基于文件内容继续分析并输出结果。

安全要求：

- 只能读取用户选择的项目目录及其子目录；
- 隐藏文件、环境变量文件、密钥文件需要提示风险；
- 单次读取内容需要有大小限制；
- 读取失败时需要明确展示失败原因。

### 7.3 文件修改流程

1. 用户提出明确修改需求。
2. Agent Runtime 读取相关文件上下文。
3. 模型生成修改方案。
4. Diff Manager 生成变更预览。
5. UI 展示待修改文件、变更行和修改说明。
6. 用户确认后，Agent Runtime 调用 `write_file` 或 `apply_patch` 工具。
7. Tool 层再次校验路径和写入权限。
8. 写入成功后返回结果。
9. UI 展示修改摘要。
10. 必要时引导用户执行验证命令。

安全要求：

- 文件写入必须由用户确认；
- 不允许静默覆盖用户未查看的变更；
- 修改前应保留原始内容或可回滚信息；
- 批量修改需要展示文件列表和风险提示；
- 写入失败时不得继续执行后续依赖步骤。

### 7.4 命令执行流程

1. 用户请求执行命令，或模型建议执行命令。
2. Agent Runtime 生成待执行命令。
3. Permission Manager 判断命令风险等级。
4. UI 展示命令内容、执行目录和风险提示。
5. 用户确认后，Command Runner 执行命令。
6. 执行过程中实时展示 stdout、stderr 和执行状态。
7. 命令结束后返回退出码、耗时和输出摘要。
8. Agent Runtime 将命令结果交给模型分析。
9. 模型输出执行结论、错误原因或下一步建议。

安全要求：

- 命令执行必须确认；
- 默认在当前项目目录执行；
- 高风险命令需要额外提示；
- 长时间运行命令需要支持中断；
- 输出过长时需要截断并保留完整日志入口。

### 7.5 任务状态流转

任务状态包括：

| 状态 | 含义 |
| ---- | ---- |
| `pending` | 已创建，等待执行 |
| `running` | 正在执行 |
| `waiting_confirm` | 等待用户确认 |
| `tool_running` | 工具执行中 |
| `success` | 执行成功 |
| `failed` | 执行失败 |
| `cancelled` | 用户取消 |

状态流转规则：

- `pending` 只能进入 `running` 或 `cancelled`；
- `running` 可以进入 `tool_running`、`waiting_confirm`、`success`、`failed`；
- `waiting_confirm` 可以进入 `tool_running` 或 `cancelled`；
- `tool_running` 可以进入 `running`、`success` 或 `failed`；
- 终态包括 `success`、`failed`、`cancelled`。

## 8. 功能模块设计

### 8.1 项目目录选择

功能目标：

让用户选择本地项目目录，作为 Agent 的工作空间和工具执行边界。

核心能力：

- 选择本地目录；
- 展示当前工作空间路径；
- 读取一级或多级目录结构；
- 排除 `node_modules`、`.git`、`dist`、`build` 等大目录；
- 支持重新选择目录；
- 切换目录时清空或隔离当前任务上下文。

验收标准：

- 用户能成功选择项目目录；
- UI 能展示当前目录；
- Agent 只能访问该目录范围内的文件；
- 目录读取失败时有明确提示。

### 8.2 对话任务

功能目标：

提供自然语言任务入口，让用户通过对话驱动 Agent 执行。

核心能力：

- 输入任务；
- 展示用户消息和 Agent 回复；
- 展示任务状态；
- 展示工具调用卡片；
- 支持取消执行中任务；
- 支持复制回复内容；
- 支持查看任务执行详情。

验收标准：

- 用户输入后能生成任务；
- Agent 能返回普通文本回复；
- 涉及工具调用时 UI 能展示过程；
- 任务失败时能展示错误信息。

### 8.3 文件读取

功能目标：

允许 Agent 读取项目中的文件内容，为代码理解、问题排查和修改建议提供上下文。

核心能力：

- 按路径读取文件；
- 自动识别文本文件；
- 对二进制文件给出不可读取提示；
- 对超大文件截断；
- 展示文件引用；
- 将读取内容返回给模型。

验收标准：

- 能读取常见代码文件；
- 超出大小限制时能提示截断；
- 读取不存在文件时能提示失败原因；
- UI 能展示被读取文件路径。

### 8.4 代码搜索

功能目标：

帮助 Agent 在项目内定位函数、组件、变量、报错关键字和调用关系。

核心能力：

- 按关键字搜索；
- 支持文件类型过滤；
- 支持忽略目录；
- 返回命中文件、行号和片段；
- 搜索结果可作为模型上下文。

验收标准：

- 能按用户问题搜索相关代码；
- 搜索结果包含路径、行号和片段；
- 搜索失败或无结果时有明确提示；
- 大量结果需要限制返回数量。

### 8.5 修改方案生成

功能目标：

让 Agent 基于当前上下文生成可审阅的代码修改方案。

核心能力：

- 读取目标文件；
- 生成修改说明；
- 生成结构化变更；
- 标注影响文件；
- 标注潜在风险；
- 给出验证建议。

验收标准：

- 修改方案能说明为什么改；
- 修改内容能映射到具体文件；
- 不直接写入文件；
- 需要用户确认后才进入写入流程。

### 8.6 Diff 预览与确认

功能目标：

让用户在文件写入前明确看到即将发生的变更。

核心能力：

- 展示文件级 Diff；
- 展示新增、删除、修改内容；
- 支持按文件确认；
- 支持取消修改；
- 支持展示修改摘要。

验收标准：

- 文件写入前必须展示 Diff；
- 用户取消后不写入文件；
- 用户确认后才执行写入；
- 写入结果能和 Diff 对应。

### 8.7 文件写入

功能目标：

在用户确认后，将修改内容写入本地文件。

核心能力：

- 写入指定文件；
- 新建文件；
- 覆盖文件；
- 写入前校验工作区边界；
- 写入失败时返回错误；
- 写入成功后展示结果。

验收标准：

- 只能写入当前项目目录；
- 必须经过用户确认；
- 写入后 UI 展示成功状态；
- 写入失败时不影响其他文件。

### 8.8 命令执行

功能目标：

允许 Agent 在用户确认后执行本地命令，用于构建、测试、Lint 和问题验证。

- 展示待执行命令；
- 展示执行目录；

- 执行命令；
- 展示实时输出；
- 展示退出码；

验收标准：

- 未确认时不执行命令；

- 失败时 Agent 能基于输出给出分析。

功能目标：

- 展示读取文件列表；

- 展示命令执行结果；
- 展示异常信息；
- 支持复制结果。

验收标准：

- 用户能看清任务过程；
- 用户能追踪工具调用；
- 用户能区分建议和已执行操作；

## 10. 权限与安全设计

### 10.1 权限原则

产品应遵循以下安全原则：

- 默认最小权限；
- 所有工具调用必须可见；
- 高风险动作必须确认；
- Agent 不能绕过 Tool 层直接执行系统操作；
- 文件访问默认限制在用户选择的项目目录内；
- 密钥、环境变量和敏感文件需要风险提示；
- 命令执行必须展示命令内容和执行目录。

### 10.2 工具权限等级

| 权限等级 | 类型 | 示例 | 是否需要确认 |
| -------- | ---- | ---- | ------------ |
| L0 | 只读低风险 | 读取目录、读取普通代码文件 | 默认不需要 |
| L1 | 只读敏感 | 读取 `.env`、密钥文件、隐藏文件 | 需要确认 |
| L2 | 写入风险 | 写入文件、新建文件、删除文件 | 需要确认 |
| L3 | 命令风险 | 执行 build、test、lint 等命令 | 需要确认 |
| L4 | 高危操作 | 删除目录、安装依赖、系统级命令 | 强确认或禁止 |

一期默认支持 L0、L2、L3。L1 需要提示，L4 默认禁止或不纳入一期。

### 10.3 敏感文件规则

以下文件默认视为敏感：

- `.env`
- `.env.*`
- `*.pem`
- `*.key`
- `id_rsa`
- `id_ed25519`
- 包含 `secret`、`token`、`password`、`credential` 的文件名

读取敏感文件前需要提示用户；模型回复中不得主动完整输出密钥内容。

### 10.4 命令风险规则

以下命令属于高风险，需要禁止或强确认：

- 删除类：`rm -rf`、`del /s`、`rmdir /s`
- 系统修改类：修改系统目录、注册表、环境变量
- 网络安装类：全局安装依赖、执行远程脚本
- 权限提升类：`sudo`、管理员权限命令
- Git 破坏性操作：`git reset --hard`、`git clean -fd`

一期建议仅允许用户确认后执行项目内常见命令，例如 `npm run build`、`npm test`、`pnpm lint` 等。

## 11. 异常状态设计

### 11.1 异常类型

| 异常类型 | 说明 | 处理方式 |
| -------- | ---- | -------- |
| 模型调用失败 | API 错误、页面会话断开、超时 | 展示失败原因，允许重试 |
| 工具调用失败 | 文件不存在、权限不足、参数错误 | 展示工具名称和错误信息 |
| 文件读取失败 | 路径无效、编码不支持、文件过大 | 展示失败原因和建议 |
| 文件写入失败 | 权限不足、文件被占用、路径越界 | 停止后续流程 |
| 命令执行失败 | 退出码非 0、命令不存在 | 展示输出并交给模型分析 |
| 用户取消 | 用户拒绝确认或中断任务 | 标记任务取消 |
| 上下文过长 | 文件内容或日志过大 | 截断、摘要或提示缩小范围 |

### 11.2 错误展示

错误信息需要包含：

- 出错环节；
- 简短原因；
- 原始错误摘要；
- 是否可重试；
- 建议下一步。

示例：

```text
文件读取失败
路径：src/App.tsx
原因：文件不存在
建议：检查文件路径，或先让 Agent 搜索相关文件。
```

### 11.3 重试策略

- 模型调用失败可手动重试；
- 文件读取失败不自动重试；
- 命令执行失败不自动重试；
- 页面会话断开需要用户重新连接；
- 用户取消后不自动恢复任务。

## 12. 数据与埋点设计

### 12.1 本地数据

一期可优先使用本地存储，不依赖后端。

建议存储内容：

- 工具权限偏好；
- 任务历史摘要；
- 执行日志；
- UI 设置。

敏感信息处理：

- API Key 不应明文存储；
- 日志中避免保存完整密钥；
- 用户可清空任务历史和日志；
- 默认不上传本地代码内容。

### 12.2 任务日志

单个任务日志建议包含：

- 任务 ID；
- 创建时间；
- 当前项目路径；
- 用户输入；
- 模型来源；
- 工具调用列表；
- 文件读取记录；
- 文件写入记录；
- 命令执行记录；
- 最终状态；
- 错误信息。

### 12.3 埋点指标

如后续接入后端，可关注以下指标：

- 任务创建次数；
- 任务成功率；
- 平均任务耗时；
- 模型调用次数；
- 工具调用次数；
- 文件读取次数；
- 文件写入确认率；
- 命令执行确认率；
- 常见失败原因；
- 用户取消率。

一期可以先在本地日志中沉淀这些字段，不强制接入在线埋点。

## 13. 非功能需求

### 13.1 性能要求

- 应用冷启动时间控制在可接受范围内；
- 目录扫描需要跳过大目录；
- 文件读取和搜索不能长时间阻塞 UI；
- 命令输出需要流式展示；
- 大文件和长日志需要截断或分页；
- 常用操作应有明确加载状态。

### 13.2 稳定性要求

- 单个任务失败不能导致应用崩溃；
- 工具调用异常需要被捕获；
- 命令执行超时需要可中断；
- 页面会话断开需要明确提示；
- 文件写入失败不能产生半完成状态。

### 13.3 可扩展性要求

- 模型接入需要通过统一接口扩展；
- 工具需要通过注册机制扩展；
- 权限规则需要可配置；
- UI 展示工具调用时不应绑定具体工具实现；
- 后续可接入外部工具协议和插件市场。

### 13.4 兼容性要求

一期优先支持 Windows 桌面环境，后续可扩展 macOS 和 Linux。

需要关注：

- 文件路径分隔符差异；
- Shell 命令差异；
- 文件编码差异；
- 权限模型差异；
- 桌面端打包差异。

### 13.5 可用性要求

- 用户应能在 3 分钟内完成项目选择和一次基础任务；
- 高风险操作前必须有明确提示；
- 工具调用过程要能被用户理解；
- 错误提示不能只展示技术堆栈；
- 最终结果需要给出明确结论。

## 14. 验收标准

### 14.1 一期总体验收

一期版本满足以下条件即可认为 Demo 验证通过：

- 能启动桌面端应用；
- 能选择本地项目目录；
- 能在对话区输入任务；
- 能接入至少一种模型来源；
- 能读取项目目录或文件；
- 能将工具结果返回给 Agent；
- 能展示工具调用过程；
- 能输出最终分析结果；
- 文件写入前有确认；
- 命令执行前有确认；
- 异常场景有基础提示。

### 14.2 核心链路验收

必须跑通以下 Demo 链路：

1. 用户选择项目目录。
2. 用户输入“读取 package.json 看一下有哪些脚本命令”。
3. Agent 调用文件读取工具。
4. UI 展示工具调用过程。
5. Agent 返回 package.json 中的 scripts 摘要。

建议额外跑通：

1. 用户输入“帮我分析这个项目的主要结构”。
2. Agent 读取目录结构。
3. Agent 输出项目结构说明。

建议额外跑通：

1. 用户输入“帮我执行 build 看看有没有问题”。
2. UI 展示待执行命令。
3. 用户确认。
4. 命令执行并展示输出。
5. Agent 分析执行结果。

### 14.3 安全验收

- 未确认时不能写入文件；
- 未确认时不能执行命令；
- 路径越界访问会被阻止；
- 敏感文件读取有提示；
- 高风险命令默认禁止或强提示；
- 工具调用记录可追踪。

### 14.4 文档验收

- 产品目标清晰；
- 一期范围明确；
- 核心流程完整；
- 功能模块可拆分开发；
- 权限与异常设计可执行；
- 验收标准可用于测试。
