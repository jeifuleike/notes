# 数据库设计综合案例

补充专题：数据库设计综合案例。本文为通用学习知识，示例和实验不表示已经执行到项目数据库。项目运行与验收仍在独立代码仓库维护。

## 1. 阅读前：这条流程在做什么

```text
人说的业务需求
  ↓ 识别对象、关系和规则
可以解释业务的数据模型
  ↓ 选择表、字段、键、约束和访问方式
可以落地的数据库设计
  ↓ 迁移并封装访问
应用能够稳定使用的数据能力
```

不要把每一步当成只做一次的流水线。设计到索引时发现查询很困难，可能需要回头修改关系；编写 Repository 时发现缺少唯一条件，也应该回到表设计。

进行综合设计复习时可以按本篇流程；实际开发中要反复校对需求和设计，而不是把某个框画完就认为它永远不会变。

| 阶段 | 要回答的问题 | 本阶段产出 |
| --- | --- | --- |
| 需求 | 谁要做什么，受到哪些规则限制？ | 用例、规则、查询清单 |
| Entity | 哪些对象有独立身份，需要保存？ | 实体、属性与标识候选 |
| Relationship | 对象之间如何关联？ | 基数、可选性、关系属性 |
| ER图 | 模型能否被整体检查？ | 实体关系图和规则说明 |
| Table | 模型如何变成数据库结构？ | 表、列、类型、默认值 |
| PK/FK | 怎样唯一标识并约束引用？ | 主键、唯一约束、外键策略 |
| 范式 | 是否存在重复事实与修改异常？ | 依赖分析和拆表决策 |
| Index | 常见查询如何有效执行？ | 索引方案与执行计划 |
| Transaction | 哪些修改必须作为一个整体？ | 事务边界和并发策略 |
| Migration | 怎样可靠地演进已有数据库？ | 版本化变更与发布步骤 |
| Repository | 应用如何读写并接收结果？ | 数据访问接口与映射约定 |

## 2. 沿完整流程走一遍“增加任务截止时间”

| 阶段 | 这次需要做什么 |
| --- | --- |
| 需求 | 截止时间是否可空？按哪个时区显示？谁能修改？是否保留变更历史？ |
| Entity | Task 增加截止属性；若独立管理提醒，则评估 Reminder 实体 |
| Relationship | 截止属性本身不增加关系；提醒接收人可能增加关系 |
| ER图 | 更新属性与必要联系，写明可选性 |
| Table | 选择 due_at 类型、NULL 含义与时间精度 |
| PK/FK | 新属性不必强行新增键；新提醒关系才评估引用 |
| 范式 | due_at 是任务事实，不在每条成员行里重复保存 |
| Index | 若经常查询即将到期任务，评估相应过滤与排序索引 |
| Transaction | 修改截止时间和提醒记录是否必须一起提交？ |
| Migration | 增列、兼容旧数据、回填和发布顺序 |
| Repository | 增加字段映射与查询参数，保留明确错误和分页语义 |

流程的意义是逐项检查，而不是每次改一个小字段都必须新增十一份文档。简单变更可以把决策写在同一份变更说明中。

基础设计与 SQL 见 [[20-后端/数据库/02-SQL基础与数据库设计]]、[[20-后端/数据库/03-索引]]、[[20-后端/数据库/04-事务]]、[[20-后端/数据库/56-Migration数据库迁移]]、[[20-后端/数据库/57-Repository数据访问]]。

## 3. 练习与验收：先解释，再动手

1. 用自己的话写出五条项目系统业务规则，标明哪些尚未确认。
2. 列出实体和属性，解释角色为什么属于成员关系。
3. 为每条关系标注两端最小和最大数量，画出 ER 图。
4. 写数据字典并检查空值、时间、唯一性和删除规则。
5. 用函数依赖找出一处不合理重复，说明拆分后解决了哪种异常。
6. 从两个具体查询推导候选索引，结合执行计划验证。
7. 为创建项目或转让负责人画事务边界，再推演并发请求。
8. 设计一次安全的增列迁移，写出旧数据处理与故障恢复步骤。
9. 为两条 Repository 方法定义输入、输出、错误和事务连接要求。

这份练习用于检查理解，不改变现有项目 TODO，也不能仅凭读完正文就标记为掌握。

## 4. 历史学习记录（原 SQL 笔记）

以下是原 SQL 笔记保留的历史自述，不作为整理后的实时学习进度：

- 近百万条 `tasks` 数据的 SQL 查询；
- `WHERE project_id = 100` 的索引检索；
- `EXPLAIN` 和 `EXPLAIN ANALYZE`；
- `IGNORE INDEX` 对照全表扫描与索引查询；
- 理解为什么不同 SQL 即使条件相同，也可能选择不同的执行计划。

**下一阶段**：`Node.js + TypeScript + mysql2/promise` → 连接池 → Repository → 事务处理 → Express 项目接口开发。

> **最后的安全底线**：真实业务数据上，先 `SELECT` 确认范围，再考虑 `UPDATE` / `DELETE`；线上表结构变更使用 Migration、备份和审核流程，别把 Workbench 当成“随手点一下就能撤销”的文本编辑器。
