# 功能开发与验收

用仓库已有的功能记录跟踪同一个功能。用户只要求规划时，止于方案；已获执行授权时，沿用该授权推进可确定的工作。

## 让下一位开发者能接手

1. 从用户、入口、前置条件和可观察结果描述目标。给出本次范围、排除项及实际存在的失败或取消路径。
2. 查当前实现、公共能力、接口契约和受影响的调用方。区分观察到的事实、已决定的取舍及仍缺的证据。影响权限、数据写入或接口契约的问题集中交有权决定的人；无依赖部分可先推进。
3. 冻结范围和验收场景。首次开工前应能回答“实现什么、用什么数据、怎样证明做到了”。续做或返修时，核对原冻结范围、当前授权和本轮缺口，沿用已有结论。

**复刻已有系统时**，以获准观察的运行行为为依据。需要独立实现时，分析者只交脱敏行为规格、允许使用的接口与资源清单。实现者使用独立上下文。涉及 UI 时固定视口、数据、角色、主题和时钟，采集原界面的关键状态（优先用 `ego-browser` 复用已登录测试会话与人工协作认证，不可用时回退到受控浏览器并注明工具）；另存当前实现的回归快照，说明各自用途。动效记录触发方式、起止状态和时间参数；正文引用原始证据链接，不重复展开全量测量数据。

## 最小功能记录

| 字段 | 要写的内容 |
| --- | --- |
| 用户目标和范围 | 用户从哪里进入、完成什么操作、预期可看到什么；本次排除什么 |
| 依据和边界 | 已确认的行为、数据契约、权限、可使用的材料、尚待解决的问题 |
| 实现影响 | 入口与调用方、可复用能力、依赖顺序；分工时标明写入者 |
| 验收场景 | 用下表逐项记录，约定执行阶段 |
| 结论 | 已验证范围、待人工处理项、负责人和人工验收决定 |

| 场景 | 执行阶段 | 条件与操作 | 预期结果 | 负责人 | 实际结果与证据 |
| --- | --- | --- | --- | --- | --- |
| 示例：保存失败后继续编辑 | 交接前必过 | 在受控测试中令保存失败 | 草稿仍在，可重试，成功提示未出现 | 实现或测试负责人 | 执行后记录结果及用例位置 |
| 示例：受限角色只能看到授权记录 | 交人工复测（仅当规格如此约定） | 使用具备相应权限的测试身份查询 | 界面可见范围与授权一致 | 指定复测人 | 未执行时保留现状及所需条件 |

## 实现和交接

按依赖先稳定数据契约，再实现一条可运行的用户路径，覆盖该路径实际存在的异常与状态。变更范围或验收阶段时，在原记录写明依据。已失败的必过项不能靠改标签放行。

运行项目约定的检查，逐项填入实际证据。单功能交付优先按“本功能 + 受影响调用方 + 核心冒烟”基于同一份构建产物（preview）执行定向门禁；累计交付多个功能、发版前或修改共享底座且影响不明时执行全量门禁。自动视觉回归收敛为 2–4 张能区分主要布局的核心稳态，控件 hover 位移、颜色与过渡参数优先由 E2E 行为和计算样式断言覆盖。

区分浏览器工具与证据边界：Playwright 等自动化框架负责固定 fixture、路由拦截与视觉快照的可复现回归门禁；`ego-browser` 优先用于原系统运行态 UI 采样、真实测试环境联调与人工协作复现（仅操作当前任务空间，不在全局清理 Cookie/缓存，不访问生产写接口，结束释放页面）。单测、Mock 浏览器测试、真实联调与视觉快照各证其事，不互相替代；系统日志、截图和样本只保留允许记录的最小信息。

交接前必过项全部有通过证据，才交人工验收。交人工复测的未执行项写清前置条件、操作和预期。验收人实际确认后再记录完成；若接受遗留项，标明接受人和影响范围。
