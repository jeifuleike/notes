# 锁与并发控制

先读事务篇。实验复用事务篇的 study_tx_lock_lab.accounts 专用表，不操作项目业务表。

本文以 MySQL 8.x / InnoDB 为背景，主要讨论 RC（读已提交）和 RR（可重复读）。SQL 实验给出操作顺序与预期现象，尚未在本次笔记修订中实际运行。

第一次读建议分三轮：

1. 先读第 1～4 节：明白并发为什么出错、谁持有锁、锁何时释放。
2. 再读第 8～10 节：用扣余额例子理解三种写法，再观察普通读与锁定读的区别。
3. 最后读索引范围、间隙锁、死锁和排查方法。先能解释单行竞争，再研究范围竞争。

全文反复问四个问题：**谁在操作哪条数据？读到的是什么版本？要申请什么锁？锁保护到哪一步结束？**

## 1. 为什么需要锁

锁用于协调并发访问：一个事务正在处理某些数据，另一个事务的冲突操作需要等待、失败或按其他明确策略处理。

例如只剩一件商品：

```text
A 读到库存 1 → 判断可以买
B 读到库存 1 → 判断可以买
A 写回库存 0 → 创建订单
B 写回库存 0 → 创建订单
```

最终库存虽然是 0，却有两个成功订单。两个请求都使用事务，也不意味着“读取旧值 → 应用判断 → 写回计算值”自动安全。

事务确定一组操作的提交边界；锁、条件更新等机制处理并发协调。只有正确组合，才能维护业务规则。

### 1. 并发不要求两条指令在同一瞬间执行

只要两个业务流程在时间上重叠、操作互相穿插，就可能产生竞争。假设账户有 1000 元，A、B 各扣 100 元，正确结果应为 800 元：

| 时间 | 请求 A | 请求 B | 数据库余额 |
| --- | --- | --- | --- |
| 1 | 普通查询得到 1000 | | 1000 |
| 2 | | 普通查询也得到 1000 | 1000 |
| 3 | 在应用里计算 `1000 - 100 = 900` | | 1000 |
| 4 | | 在应用里也计算出 900 | 1000 |
| 5 | 写入固定值 900，提交 | | 900 |
| 6 | | 写入固定值 900，提交 | 900 |

两个请求都返回成功，余额却只少了 100。这叫**丢失更新**：第二次写入覆盖了第一次扣款的效果。

这里不是数据库把一行同时写坏了。两次 UPDATE 完全可以依次取得写锁、依次成功；问题是第二次写入的 900，早就在应用中根据过期数据算好了。**写入排队，并不能修正写入参数本身。**

### 2. 为什么包上事务仍然可能出错

如果把 A、B 各自的“查询 → 计算 → 更新”放进事务，但查询仍是普通 SELECT，两边依然可能先读到 1000。事务允许并发，不会自动识别“这次查询是为了后面扣款”。

可以把问题拆成三层：

| 需要解决的问题 | 对应机制 | 扣款中的含义 |
| --- | --- | --- |
| 多步操作一起成功或失败 | 事务 | 扣款与业务记录应一起提交 |
| 查询能看到哪些版本 | 隔离级别与 MVCC | 能否看到别人的未提交修改、是否复用旧快照 |
| 别人同时来改怎么办 | 锁、条件更新、版本检查 | 等待、重新判断或报告冲突 |

后文三种安全写法，都是在明确表达第三层规则。

## 2. 先区分三种层面的锁

| 概念 | 协调范围 | 例子 |
| --- | --- | --- |
| 进程内互斥 | 同一进程中的参与者 | Node 中某个队列或互斥工具 |
| 数据库锁 | 数据库会话间的数据访问 | InnoDB 行锁 |
| 分布式锁 | 多进程、服务间的约定 | 基于 Redis 的租约协调 |

Node 只有一个 JavaScript 主执行线程，也能因异步 I/O 交错而发生竞争。部署多个进程后，本地变量更无法协调所有请求。

数据库锁由数据库执行冲突检查，不要求所有请求都经过同一个 Node 进程；Redis 分布式锁不能简单取代 InnoDB 的事务锁。

例如 Node 处理请求 A，执行 `await 查询余额` 时，可以转去处理请求 B；A 的业务流程还没结束，B 的查询已经发给数据库了。`await` 保证当前函数等结果再向下执行，不会让其他请求一起暂停。

“加锁”也不意味着整台数据库停下：A 锁住账户 1 后，B 修改账户 1 可能等待，C 修改账户 2 通常仍能继续。锁保护的对象和范围越小，不冲突的业务越有机会并发执行。

### 1. 先理解共同结构：保护对象、持有者、等待规则

可以把锁理解成对某项资源的“使用资格”。互斥锁要求同一时刻只有一个参与者进入受保护的操作过程，这段过程叫**临界区**。

```text
确定资源 → 申请锁 → 成功后进入临界区 → 完成操作 → 释放锁
               └→ 未成功：排队等待、立即失败，或稍后重试
```

锁不是给业务函数加一个名字就自动生效。需要有一个所有参与者都能访问的协调者，负责判断谁能进入。三类锁的关键区别，就是**协调者在哪里、能管到谁**。

### 2. 进程内互斥：让同一 Node 进程里的异步任务排队

#### 是什么

锁状态保存在当前进程内存中，例如一个对象和等待队列。所有要修改这份资源的代码，都必须使用同一个锁实例。

适合保护本进程里的可变状态，例如一个内存计数器。它不能协调另一个 Node 进程，即使两个进程运行在同一台机器上。

#### 为什么单线程也需要它

下面的函数先读、等待，再写。假设初始 `count=0`，两个调用都在等待前读到了 0，之后各自写入 1，最终就少加了一次：

```js
let count = 0;

async function increment() {
  const old = count;
  await Promise.resolve(); // 让出执行机会，其他异步调用可以继续
  count = old + 1;
}

await Promise.all([increment(), increment()]);
console.log(count); // 1，而期望是 2
```

这里每一小段 JavaScript 的确依次执行，但完整的“读 → 等待 → 写”并不是不可分割的一步。

#### 怎样实现：用 Promise 串成等待队列

下面是教学用的互斥队列，只用于同一事件循环，不支持跨线程共享、取消、超时或重入：

```js
function createMutex() {
  let tail = Promise.resolve();

  return async function runExclusive(task) {
    const previous = tail;
    let unlock;
    // 同步接到队尾，再等待前一位。中间不能先 await 再接队。
    tail = new Promise(resolve => { unlock = resolve; });

    await previous;
    try {
      return await task();
    } finally {
      unlock(); // 成功或抛错，都要让下一位继续
    }
  };
}

const withCounterLock = createMutex(); // 共享实例，不能每次请求都新建
let count = 0;

async function increment() {
  return withCounterLock(async () => {
    const old = count;
    await Promise.resolve();
    count = old + 1;
  });
}

await Promise.all([increment(), increment()]);
console.log(count); // 2
```

A 先进入，B 等 A 对应的 Promise；A 完成后在 finally 中解锁，B 才读取最新的 count。`return await task()` 保证异步任务真正结束后才进入 finally。

注意：不要在持有这把锁时再次申请同一把锁，否则内层等外层释放、外层等内层结束，会自己等自己。某任务永久不结束，后面的任务也会一直排队。

#### 为什么部署两个实例就失效

```text
Node 实例 A：内存里有锁 A → 请求 1 取得锁 A
Node 实例 B：内存里有锁 B → 请求 2 也取得锁 B
```

两把锁互不知情。如果两边都在操作同一个数据库账户，本地互斥就不能保护它。所有代码路径还必须遵守同一约定：有一条路径直接修改 count、不经过队列，保护也会被绕过。

### 3. 数据库锁：由数据库协调不同连接对数据的访问

#### 是什么

锁状态由数据库引擎管理。应用表达“我要修改这条记录”或“我要锁定读取”，InnoDB 根据索引访问、隔离级别和锁兼容规则协调请求。应用不需要自己在表里增加 `locked=true`。

即使两个请求来自不同 Node 进程，只要访问同一数据库中的冲突对象，数据库也能协调它们。InnoDB 事务锁通常以事务为持有单位；它不是 JavaScript 内存中的布尔变量。

#### 怎样实现：应用发 SQL，引擎申请和管理锁

用主键等值锁定一条已经存在的账户记录：

```sql
-- 连接 A
USE study_tx_lock_lab;
START TRANSACTION;
SELECT id, balance FROM accounts WHERE id = 1 FOR UPDATE;
-- 此时先不要提交；应用应在同一连接中检查、修改。
```

另一个独立连接执行：

```sql
-- 连接 B
USE study_tx_lock_lab;
START TRANSACTION;
UPDATE accounts SET balance = balance - 100
WHERE id = 1 AND balance >= 100;
-- A 未结束时，这里通常等待它持有的冲突锁。
```

切到 A 执行 `COMMIT` 或 `ROLLBACK`，B 才有机会继续。观察完成后在 B 执行 `ROLLBACK`，撤销实验扣款。实际并发测试步骤见第 9 节。

从实现机制上，可先用下面的简化模型理解：

1. A 的 SQL 找到目标索引记录，向引擎申请对应锁。
2. 引擎检查有没有不兼容的持有者；没有就授予 A，并维护锁与事务的关系。
3. B 请求冲突锁时，引擎维护等待关系，B 的 SQL 暂不能完成。
4. A 的事务结束，引擎释放相应锁，让符合条件的等待请求继续竞争或执行。

这只是机制模型，真实实现还涉及记录锁、范围锁和死锁检测，并不是“一条数据就固定存一个锁对象”。相关类型见后续章节。[InnoDB 锁机制](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)

#### 能保护什么，不能保护什么

它能保护数据库里的冲突读写；即使另一条 UPDATE 没有先执行 FOR UPDATE，引擎仍会为 UPDATE 申请必要的写锁。

但它不会让一个 HTTP 接口自动只能调用一次，也不会撤销已经发出的邮件。数据库事务回滚只撤销相应数据库修改。普通快照 SELECT 也通常仍能读取历史版本，不能把行锁理解成禁止任何人查看数据。

### 4. 分布式锁：让多个进程向同一个外部协调者申请资格

#### 是什么

例如部署三个 Node 实例，它们都可能尝试重建同一个商品缓存。希望同一段时间只让一个实例重建，就可以向共同的 Redis 申请 `lock:cache:product:42`。

锁名表示资源：商品 42 和商品 43 可以使用不同锁名，各自重建；锁名若不一致，两个实例就不会互相排斥。

#### 怎样实现：Redis 单实例上的基础租约

下面演示基本命令，不是完整的高可用分布式锁方案。每次申请生成独立、不可复用的随机 token，例如 UUID：

```text
SET lock:cache:product:42 token-A NX PX 10000
```

- `NX`：仅当这个 key 不存在才写入，避免覆盖当前持有者。
- `PX 10000`：10 秒后过期。持有者崩溃时，锁不会永远留着。
- `token-A`：标识本次申请的持有者；它不是商品 id，也不是固定进程名。
- 返回 `OK`：本次拿到租约；未成功就不能进入受保护操作。

检查不存在、写 token、设置过期必须作为一个原子操作完成。不能拆成 `GET → SET → PEXPIRE`：两个实例可能同时查到不存在，或进程写入后尚未设置过期就崩溃。

```text
实例 A：SET ... token-A NX PX 10000 → 成功 → 重建缓存 → 释放
实例 B：SET ... token-B NX PX 10000 → 未成功 → 等待后重试或返回
```

#### 释放时为什么不能直接 DEL

可能发生这样的时序：

```text
1. A 拿到 10 秒租约，执行中暂停了很久。
2. 10 秒到，A 的锁过期。
3. B 拿到新锁，Redis 中保存 token-B。
4. A 恢复，执行 DEL：把 B 的锁删掉了。
```

因此必须“确认 token 还是自己的，才删除”，而且比较和删除也必须原子完成。可用 Lua 表达：

```lua
-- KEYS[1] 是锁 key，ARGV[1] 是本次申请的 token。
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end
```

调用示意：`EVAL "上面的 Lua 脚本" 1 lock:cache:product:42 token-A`。返回 0 表示已不存在或不再属于 A，不能强行删除。[Redis 官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

#### 过期时间解决了崩溃，却带来“旧持有者恢复”的问题

比较 token 只能防止误删别人的锁，**不能阻止过期的 A 继续执行原来的业务代码**。上例第 3 步后，A、B 可能同时重建缓存，A 甚至可能把更旧的结果覆盖回去。

较长任务可以设计续租，但续租必须原子检查持有者，续租失败后也不能继续假装自己拥有锁。暂停、断网仍会使租约失效，不能仅靠“过期时间设得足够长”保证互斥。

对不能接受旧持有者写入的资源，可以进一步设计 fencing token：协调者按顺序发出递增凭证，下游保存并检查凭证，拒绝旧凭证的写入。这要求下游资源真正执行校验，随机 UUID 本身没有这种顺序能力。

Redis 故障切换也需要单独考虑：主节点授予锁但尚未复制就故障，新主节点可能允许另一实例拿锁。不能把单实例 SET 示例当成所有故障情况下的安全证明。缓存重建可结合版本校验；扣款等业务仍应依靠数据库条件、事务和幂等约束保证正确性。

### 5. 放在同一个业务里，应该选哪一种

| 具体需求 | 合适的协调位置 | 原因 |
| --- | --- | --- |
| 同一 Node 进程里的内存计数器按顺序修改 | 进程内互斥 | 数据和参与者都在同一进程 |
| 多个 Node 实例扣同一个 MySQL 账户余额 | 数据库条件更新或事务锁 | 最终余额由数据库保存，写入必须在那里保证正确 |
| 多个实例减少同一缓存的重复重建 | 可考虑 Redis 租约 | 需要跨进程协调一段操作，并处理过期与旧结果覆盖 |

三类锁可以组合，但不能相互自动替代。例如 Redis 决定谁负责领取任务，数据库再用状态条件更新检查任务是否仍可领取；重试时还要用业务唯一标识防止重复处理。**锁控制谁能尝试执行，业务条件与幂等约束决定执行结果是否正确。**

Redis 命令与其他用途继续见 [[20-后端/数据库/06-Redis]]；本节只解释跨进程协调所需的基础机制。

## 3. 共享锁 S 与排他锁 X

### 1. S 和 X 到底表示什么

先把名字翻译成人话。下面说的“别人”，都指**其他事务**：

- **S 锁（Shared，共享锁）**：我需要保护这条记录，别人也可以拿 S 锁一起保护，但别人暂时不能拿 X 锁来修改它。
- **X 锁（Exclusive，排他锁）**：我要独占这条记录的锁定访问资格，别人暂时不能再拿它的 S 锁或 X 锁。

它们不是 SQL 独有的概念，其他并发控制中的读写锁也有类似思想。这里具体讨论 MySQL InnoDB 对同一条已有索引记录的加锁。

**“共享”不是共享修改权，“排他”也不是禁止一切查询。** 普通快照读通常不申请这里的 S / X 记录锁，后面单独举例。

先只看“同一条索引记录上”，不同事务之间的 S / X 锁：

| 已持有的锁 | 另一个事务申请 S | 另一个事务申请 X |
| --- | --- | --- |
| S（Shared，共享） | 兼容 | 冲突 |
| X（Exclusive，排他） | 冲突 | 冲突 |

共享锁允许多个事务共同持有读保护；排他锁用于修改等需要排他处理的操作。

“X 锁存在”不等于普通 SELECT 一定卡住。RC / RR 下普通一致性读通常可以通过 MVCC 读取对自己可见的历史版本。

上表不适用于所有其他类型锁。例如间隙锁的兼容规则另有特点，不能把表格直接套在 gap lock 上。[InnoDB 锁类型](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)

### 怎样读这张兼容表

“兼容”表示不同事务可以同时持有这些锁；“冲突”表示后来的申请不能立即获得，通常进入等待。

- A 执行 `SELECT ... FOR SHARE`，B 也执行 `FOR SHARE`：都要 S 锁，可以共同保护同一记录。
- A 持有 S 锁，B 想 UPDATE 同一记录：B 要 X 锁，必须等待。
- A 执行 `SELECT ... FOR UPDATE`，B 也执行 `FOR UPDATE`：都要 X 锁，B 等 A 结束。
- A 持有 X 锁，B 执行普通 SELECT：RC / RR 下通常走 MVCC，不是来申请表中那个 S 锁，所以不能直接用兼容表判断它会等待。

共享锁保护的是“我处理期间，不让其他事务随意修改这条记录”。如果读完就确定要改，通常直接考虑 FOR UPDATE：两个事务先拿 S 锁、再都尝试升级为 X 锁，可能相互等待而形成死锁。

### 2. 先对应到 SQL：哪条语句在申请什么

| SQL | 本节例子中对目标记录的作用 |
| --- | --- |
| `START TRANSACTION` | 开启事务，本身不锁住账户 1 |
| `SELECT ... FOR SHARE` | 锁定读取，申请 S 锁 |
| `SELECT ... FOR UPDATE` | 锁定读取，申请 X 锁，即使还没有修改数据 |
| `UPDATE ...` / `DELETE ...` | 修改或删除时自动申请必要的 X 锁 |
| 普通 `SELECT ...` | RC / RR 下通常通过 MVCC 读取，不申请这里的 S / X 记录锁 |
| `COMMIT` / `ROLLBACK` | 结束事务，释放相应事务锁 |

S / X 表示**访问模式**，行锁、表锁表示**保护粒度**。因此“账户 1 这条记录上的 X 锁”是完整的一种描述，不是两把互不相关的锁。

下面所有例子都假设：使用事务篇的专用实验库，`id` 是主键，账户 1 已存在；A、B 是两个不同数据库连接，隔离级别为 RC 或 RR。每个连接先执行 `USE study_tx_lock_lab;`。每个例子开始前，先结束上一个例子的事务。表格从上往下执行，不是让一侧全部执行完再执行另一侧。

### 3. 例子一：S + S，可以同时拿到

两个事务都想锁定读取账户 1，但暂时不允许别人修改：

| 步骤 | 连接 A | 连接 B |
| --- | --- | --- |
| 1 | `START TRANSACTION;` | |
| 2 | `SELECT balance FROM accounts WHERE id=1 FOR SHARE;` → 拿到 S 锁 | |
| 3 | | `START TRANSACTION;` |
| 4 | | `SELECT balance FROM accounts WHERE id=1 FOR SHARE;` → 也拿到 S 锁，不必等 A |
| 5 | `COMMIT;` → 释放 A 的 S 锁 | B 的 S 锁仍然持有 |
| 6 | | `COMMIT;` → 释放 B 的 S 锁 |

这就是“共享”：**同一条记录可以同时由 A、B 各自持有 S 锁**。A 释放自己的锁，不会替 B 释放锁。

如果此时第三个连接想修改账户 1，它要等所有与其冲突的 S 锁释放，而不是只等其中一个事务结束。

### 4. 例子二：S + X，后来的修改需要等待

| 步骤 | 连接 A | 连接 B |
| --- | --- | --- |
| 1 | `START TRANSACTION;` | |
| 2 | `SELECT balance FROM accounts WHERE id=1 FOR SHARE;` → 拿到 S 锁 | |
| 3 | | `START TRANSACTION;` |
| 4 | | `UPDATE accounts SET balance=balance+10 WHERE id=1;` → 要 X 锁，等待 |
| 5 | `COMMIT;` → 释放 S 锁 | 等待中的 UPDATE 随后有机会取得 X 锁并完成 |
| 6 | | `ROLLBACK;` → 撤销加 10，并释放锁 |

为什么 B 不能修改？因为 A 的 S 锁表达的是：**“我还在处理这条记录，请先不要改动它。”**

这里 B 并没有写 `FOR UPDATE`，但 UPDATE 会自动申请修改所需的 X 锁。锁兼容性检查由引擎执行，不要求双方都主动写锁定读。

第 4 步等待时，应切到 A 提交，不能继续向正在等待的 B 发送第 6 步。若 B 已经等到超时报错，先在两个连接回滚，再重新实验。

### 5. 例子三：X + X，即使双方只是锁定查询，也要等待

| 步骤 | 连接 A | 连接 B |
| --- | --- | --- |
| 1 | `START TRANSACTION;` | |
| 2 | `SELECT balance FROM accounts WHERE id=1 FOR UPDATE;` → 拿到 X 锁 | |
| 3 | | `START TRANSACTION;` |
| 4 | | `SELECT balance FROM accounts WHERE id=1 FOR UPDATE;` → 也要 X 锁，等待 |
| 5 | `ROLLBACK;` → 释放 X 锁 | B 的锁定查询随后返回，并持有自己的 X 锁 |
| 6 | | `ROLLBACK;` → 释放 B 的锁 |

**A 还没修改余额，也已经持有 X 锁。** FOR UPDATE 的作用就是先取得排他保护，覆盖后续的判断和修改过程。

如果把 B 第 4 步换成 `FOR SHARE`，它会申请 S 锁，同样与 A 的 X 锁冲突，所以也要等待。这就是表格里的 X + S。

### 6. 例子四：已有 X 锁，为什么普通 SELECT 还能读

先在没有活动实验事务时，将账户 1 的余额恢复成 1000。然后按下面顺序执行：

| 步骤 | 连接 A | 连接 B（autocommit=1，无活动事务） |
| --- | --- | --- |
| 1 | `START TRANSACTION;` | |
| 2 | `UPDATE accounts SET balance=900 WHERE id=1;` → 持有 X 锁，未提交 | |
| 3 | | `SELECT balance FROM accounts WHERE id=1;` → 通常直接读到已提交的 1000 |
| 4 | `ROLLBACK;` → 撤销 900，释放锁 | |

B 不是拿着 S 锁申请来和 A 的 X 锁竞争，而是通过 MVCC 读取对自己可见的历史版本。因此，不能用“S 与 X 冲突”推导出“所有查询都会等待”。

如果第 3 步改成显式事务里的 `SELECT ... FOR SHARE`，B 就需要申请 S 锁，会等 A 结束。这两种查询虽然都叫 SELECT，访问方式却不同。

也不能把“普通查询能读”理解成“可以读到 A 的未提交结果”。本例能读到的是 1000，A 尚未提交的 900 对 B 不可见。

### 7. 例子五：同一个事务拿到 X 锁后，还能自己修改吗

当然能。兼容表讲的是**不同事务之间**的冲突，并不是持有 X 锁后连自己也不能写：

```sql
START TRANSACTION;

SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- 当前事务先拿到 X 锁，应用检查余额。

UPDATE accounts SET balance = balance - 100
WHERE id = 1 AND balance >= 100;
-- 同一事务继续修改，不会因为自己之前拿的 X 锁而卡住。

ROLLBACK; -- 教学示例结束，撤销修改并释放锁。
```

但是，如果查询和 UPDATE 分别走连接池的两条连接，就可能变成两个事务：连接 A 拿着锁，连接 B 的 UPDATE 等 A。这也是为什么锁定查询与后续修改必须使用同一连接、同一事务。

### 8. 最后用四句话检查理解

1. A 拿 S，B 也拿 S：可以一起持有。
2. A 拿 S，B 要 X：B 等待。
3. A 拿 X，B 要 S 或 X：B 等待。
4. B 只是普通快照查询：通常不申请上述记录锁，另按 MVCC 可见性规则读取。

上面讨论的是默认等待方式；实际还可能遇到超时、死锁或 NOWAIT 立即报错。S / X 锁不是对所有后续 SQL 建一个总队列，而是根据**同一资源上的锁请求是否冲突**来协调。

## 4. 如何取得锁，什么时候释放

UPDATE、DELETE 等会自动申请必要的锁；需要“先读取并检查，再修改”的业务，可以使用锁定读。

```sql
START TRANSACTION;
SELECT id, balance FROM accounts WHERE id = 1 FOR UPDATE;
-- 应用检查余额，再决定是否修改
COMMIT;
```

FOR UPDATE 在这里取得排他保护；FOR SHARE 取得共享保护。为了保护后续操作，必须让读取和修改处于同一个显式事务、同一个连接中。

事务结束时释放对应事务锁。不要在自动提交环境执行完一条 FOR UPDATE 后，认为下一条 SQL 仍受它保护。初学阶段不用“SELECT ...; 很快再 UPDATE”代替锁定读。[锁定读官方说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

### 1. 锁属于数据库事务，不属于某一行 JavaScript 代码

下面是一条锁从申请到释放的时间线：

```text
A：开始事务 → FOR UPDATE 取得账户 1 的 X 锁 → 检查 → UPDATE → COMMIT
                           │                          │         │
                           └──── 事务内持续保护 ──────┘         释放
B：                 尝试 UPDATE 账户 1 → 等待 ───────────────→ 继续
```

`SELECT` 已返回、JavaScript 已拿到查询结果，都不代表锁释放。A 的 UPDATE 已返回成功也不代表提交；显式事务还在，B 就可能继续等。

相反，如果没有显式事务、每条语句自动提交，前一条锁定读结束后就不能继续保护下一条 UPDATE。**保护期必须覆盖“读取 → 判断 → 写入”，不能只覆盖读取那一瞬间。**

### 2. 等待结束后，不应继续用等待前的余额

假设余额 150，A、B 都要扣 100：

| 步骤 | A | B |
| --- | --- | --- |
| 1 | FOR UPDATE 取得锁，读到 150 | |
| 2 | | FOR UPDATE 申请同一行的锁，等待 |
| 3 | 判断足够，扣成 50，提交 | 仍在等待 |
| 4 | | 得到锁，锁定读返回 50 |
| 5 | | 判断不足，回滚，不扣款 |

B 的判断使用锁定读返回的 50，不能使用请求进入时缓存的 150。若 A 回滚，B 则可能读到恢复后的 150。

锁定读属于通常所说的“当前读”：它要处理当前可锁定的数据，必要时等待冲突事务结束。RR 下即使之前普通 SELECT 读过旧快照，也不能推断 FOR UPDATE 仍会返回同一个旧余额。

### 3. 连接池里最容易写错的地方

```text
错误：pool 执行 BEGIN → pool 执行 SELECT → pool 执行 UPDATE
                     这些调用可能分别使用不同连接

正确：借出 connection
      → connection 开始事务
      → 同一 connection 查询、判断、更新
      → 提交或回滚
      → 归还 connection
```

Repository 方法若参与同一个事务，也需要接收并使用这条 connection。完整连接池事务边界见 [[20-后端/数据库/04-事务]]，不要只靠函数调用顺序判断事务是否成立。

## 5. 索引为什么会影响加锁范围

InnoDB 的行级锁主要通过索引记录来实现。判断锁范围时需要看：

```text
隔离级别 + 实际访问的索引 + 查询条件 + 数据分布
```

例如用主键等值查找一条已存在的记录，和用非唯一索引扫描一个范围，不是同一种加锁情况。

缺少合适索引，可能扫描并锁住大量记录，导致看似无关的请求等待。这不等于“没有索引，InnoDB 就自动把行锁升级成一个表锁”。InnoDB 不通过这种锁升级来处理大量行锁。

也不能只看 WHERE 中最后匹配几行，就断言只锁了几行；执行计划和扫描范围同样重要。索引原理复用 [[20-后端/数据库/03-索引]]。

### 用“找数据的路线”理解锁范围

假设表里有很多账户，现在要锁住邮箱为某个值的账户：

```sql
SELECT id FROM accounts WHERE owner_name = 'Alice' FOR UPDATE;
```

这里只是访问路径示意，`owner_name` 是否有索引以实际表结构为准：

- 有合适索引：数据库可能沿索引定位到较小范围，再处理对应记录。
- 没有合适索引：数据库可能逐条扫描大量记录。锁定扫描所触及的范围可能明显大于最终返回的结果。

RR 的范围锁定读还可能保护扫描涉及的间隙；RC 对不匹配记录的锁释放规则又不同。因此“返回一行”不等于“全程只影响一行”。

排查时先用 `EXPLAIN SELECT ...` 查看计划中的 `key`、访问方式和预计扫描行数，再结合实际锁表观察。EXPLAIN 是访问路径线索，本身不能完整列出运行时每一把锁。[不同 SQL 的加锁规则](https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html)

## 6. 记录锁、间隙锁、临键锁

以下先按 RR 下常见的范围锁定读理解，实际锁范围仍要结合执行计划核对。

### 1. 记录锁 Record Lock

锁住索引中的具体记录。例如主键 id=1 已存在，通过唯一索引完整等值匹配并锁定它，通常不需要顺便锁住前方间隙。

如果记录不存在，或者联合唯一索引只匹配了一部分字段，就不能直接套用“唯一等值只锁一行”的结论。

### 2. 间隙锁 Gap Lock

索引里已有 id=10、20，中间的 (10,20) 是一个间隙。间隙锁主要阻止其他事务向该间隙插入记录，保护的不只是已有行。

```text
已有记录：10              20
                 ↑
            插入 15 可能等待
```

纯间隙锁之间可以共存，不用记录级 S / X 冲突表推导其兼容性。

### 3. 临键锁 Next-Key Lock

可以先理解成“记录锁 + 该记录前面的间隙锁”。在简单有序索引中，常画成 `(前一记录, 当前记录]`。

它用于在范围访问时保护记录与相关插入位置。示意区间帮助理解机制，不保证某条 SQL 恰好只锁图上的区间；边界、扫描结束位置及索引选择会影响结果。

RC 下普通搜索和索引扫描一般减少间隙锁使用，但外键检查和重复键检查等仍存在例外。不能说“RC 完全没有间隙锁”。这些边界以 [隔离级别说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html) 为准。

### 4. 为什么需要锁住“还不存在的数据”

假设 A 正在锁定读取 `10 < id < 20`。当前没有符合条件的记录，如果只锁已有记录，A 什么也锁不到，B 就可以插入 15，使这个范围多出一行。

间隙锁保护的是**插入位置**：即使当前没有 15，也能阻止别人把 15 插进受保护的区间。这与记录锁保护已有的 10、20，是两件不同的事。

用已有键值 10、20、30 的索引做纯示意：

```text
记录锁锁 20：          只标记 [20]
间隙锁锁 (10,20)：     标记 10 与 20 中间的插入位置，不含端点记录
临键锁锁 (10,20]：     同时标记中间插入位置和记录 20
```

上图用于区分三种对象，不是某条查询的精确加锁报告。扫描末尾还可能涉及最大记录之后的间隙，不能只画返回行就停止分析。

### 5. 间隙锁为什么能共存

两个事务都要求“暂时不许别人往这段间隙插入”，这两个要求可以同时成立，所以纯间隙锁之间可以兼容。但第三个事务若真的要插入，仍可能受阻。**间隙锁互相兼容，不代表间隙内插入自由。**

也不要用间隙锁代替唯一约束。例如用户名必须唯一，应在数据库建立 UNIQUE 约束；“先查询不存在，再插入”是否安全还涉及隔离级别、索引和竞争路径，不能只依赖应用查询的结果。

## 7. 其他锁先认识用途

| 类型 | 基本用途 |
| --- | --- |
| 意向锁 IS / IX | 在表级表达事务准备对某些行取得共享或排他锁，协调表级与行级锁 |
| 插入意向锁 | 插入前表达对间隙中某插入位置的请求，不同位置插入未必互相阻塞 |
| AUTO-INC 相关机制 | 协调自增值分配，行为受模式和语句类型影响 |
| 元数据锁 MDL | 保护表结构与相关对象定义，协调查询与 DDL |

意向锁不代表“已经把整张表的行都锁死”。MDL 也不是行锁：一个长事务访问过某表，可能使另一连接的 ALTER TABLE 等待，即使没有在修改相同数据行。[元数据锁](https://dev.mysql.com/doc/refman/8.4/en/metadata-locking.html)

## 8. 三种常见并发写法

### 1. 用一条条件更新表达规则

例如扣余额 100：

```sql
UPDATE accounts
SET balance = balance - 100
WHERE id = 1 AND balance >= 100;
```

数据库把判断与更新放在同一语句中执行，并协调写锁。这里不把应用早先读到的余额作为新值写回。

必须检查 affectedRows：本例匹配并修改一行才算扣款成功；为 0 时可能用户不存在，也可能余额不足。不要把所有 UPDATE 的影响行数语义都机械套用到此例之外。

如果还要向另一账户加钱或创建订单，应把相关写入放进同一事务。单条条件 UPDATE 只维护它表达的规则，不能替代整个业务事务。

### 2. 悲观并发控制：先锁再判断

```text
START TRANSACTION
  ↓
SELECT ... FOR UPDATE
  ↓
检查当前余额
  ↓
修改数据及相关记录
  ↓
COMMIT / ROLLBACK
```

适合需要基于当前数据进行多步判断的流程。代价是竞争请求需要等待，所以事务要短。

### 3. 乐观并发控制：版本号比较

应用先读到 balance 和 version，例如 version=0，再更新：

```sql
UPDATE accounts
SET balance = 900, version = version + 1
WHERE id = 1 AND version = 0;
```

若别人已更新并推进版本，影响行数为 0，应用应重新读取、重算或返回冲突，不能当成功。

所有相关更新路径都必须遵守版本规则，且版本比较不能替代余额等业务条件。所谓“乐观锁”是一种冲突检测策略，这条 UPDATE 在数据库里仍会取得必要的写锁。

### 4. 同一笔扣款，三种写法分别在保护什么

#### 条件更新：把判断和计算交给数据库

仍假设余额 150，两个请求各扣 100，执行相同语句：

```sql
UPDATE accounts
SET balance = balance - 100
WHERE id = 1 AND balance >= 100;
```

1. A 取得写锁，条件满足，将余额改成 50。
2. B 若遇到 A 尚未结束的事务，就等待它释放冲突锁。
3. A 提交后，B 的更新会根据可更新的当前记录检查条件；余额 50 不满足 `>= 100`，不再扣款。
4. A 修改一行，B 修改零行。应用只有检查结果，才能给出正确业务响应。

这里 `balance - 100` 是数据库执行更新时根据记录值计算，与应用先算出 900 再写 `SET balance = 900` 不同。条件 `balance >= 100` 则负责防止透支：没有这个条件且没有其他约束时，第二次扣款可能把余额变成负数。本实验表已有非负 CHECK 约束，违规更新会报错；条件更新能把余额不足表达成影响零行，应用仍须检查结果。

#### 悲观控制：先获得保护，再做多步判断

下面 SQL 中的分支需要由应用根据查询结果选择，不是让所有语句无条件执行：

```sql
START TRANSACTION;
SELECT id, balance FROM accounts WHERE id = 1 FOR UPDATE;
-- 应用：若账户不存在或余额不足，执行 ROLLBACK 并结束。
-- 应用：只有检查通过，才执行下面的 UPDATE。
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- 如需写入业务记录，在此处使用同一连接完成。
COMMIT;
```

先取得锁，意味着别的冲突写入不能在“我检查通过”和“我完成更新”之间插进来。若还有复杂条件，必须确认那些条件依赖的数据也受到正确保护；只锁账户 1，不会自动锁住其他表里的业务规则。

#### 乐观控制：允许先各自计算，提交修改时检查前提是否仍成立

假设 A、B 都读到 `balance=1000, version=0`，各自在应用里计算出 900：

| 步骤 | A | B |
| --- | --- | --- |
| 1 | 带 `WHERE version=0` 更新，写入 900，版本变成 1，提交 | |
| 2 | | 也带 `WHERE version=0` 更新 |
| 3 | | 当前版本已为 1，匹配零行，发现自己的读取前提过期 |

B 若要继续，必须重读 900 / version=1，再算出 800，再带 version=1 提交更新。也可以直接向用户报告数据已变化，让用户刷新。

对于扣款，可以把版本与余额条件一起表达：

```sql
UPDATE accounts
SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 0 AND balance >= 100;
```

这里的 0 是示意值，真实应用应绑定本次读到的版本。结果为 0 可能是版本冲突、余额不足或账户不存在；不能一律回答“余额不足”。所有修改余额的入口都应按约定推进版本，否则某条路径绕开版本更新，检查就可能漏掉修改。

### 5. 怎样选择

| 业务形态 | 优先考虑 | 需要承担的处理 |
| --- | --- | --- |
| 条件和计算能用一条 SQL 清楚表达 | 条件 UPDATE | 检查影响行数，处理业务失败 |
| 必须读当前值后做多步判断和写入 | FOR UPDATE + 短事务 | 等锁、超时和死锁处理 |
| 编辑表单等允许先读取、过一段时间再提交 | version 条件更新 | 告知冲突，或重读后重新计算 |

悲观和乐观描述的是处理冲突的策略，不是 MySQL 两种互斥的引擎开关。乐观更新也可能短暂等待数据库写锁；悲观锁也必须检查业务条件。

不要为了等待用户在网页上确认而一直持有数据库锁。表单打开几分钟后才提交，通常更适合用版本检查发现冲突。

## 9. 实验 1：观察行锁等待

准备：A、B 是两个不同 CONNECTION_ID 的会话，都 USE study_tx_lock_lab，autocommit=1，隔离级别设为 RR。开始前确认没有遗留事务。

先在没有活动事务时恢复专用实验数据：

```sql
UPDATE accounts SET balance = 1000, version = 0 WHERE id IN (1, 2);
```

按以下步骤操作：

| 步骤 | 会话 A | 会话 B |
| --- | --- | --- |
| 1 | START TRANSACTION; | |
| 2 | SELECT * FROM accounts WHERE id=1 FOR UPDATE; | |
| 3 | | START TRANSACTION; |
| 4 | | UPDATE accounts SET balance=balance-10 WHERE id=1; → 等待 |
| 5 | COMMIT; | 等待中的 UPDATE 随后完成 |
| 6 | | SELECT balance FROM accounts WHERE id=1; → 990 |
| 7 | | ROLLBACK; |

不要在 B 等待时继续往同一会话发送其他命令；切到 A 释放锁即可。若等待太久已报超时，先在 B ROLLBACK，再重新做实验。

B 的 UPDATE 返回成功后仍未提交，其锁也还没释放。第 7 步回滚后余额应恢复为 1000。

**实验后应能回答：**

- B 卡在 UPDATE，不是卡在 START TRANSACTION，因为开始事务本身不等于已经锁住账户 1。
- A 提交后，B 获得机会执行；不是 A 替 B 完成了提交。
- B 能读到自己的 990，即使它还没有提交。这不代表其他连接也能读到 990。
- B 回滚撤销的是 B 的减 10；A 在这个实验中只锁定读取，没有修改余额。

## 10. 实验 2：有排他锁，普通 SELECT 也能读取

A 执行：

```sql
START TRANSACTION;
UPDATE accounts SET balance = 900 WHERE id = 1;
```

A 暂不提交。B 在事务外、autocommit=1、RC 或 RR 下执行：

```sql
SELECT balance FROM accounts WHERE id = 1;
```

B 预期读到已提交的 1000，而不是 A 的未提交 900。它通常不会像冲突 UPDATE 一样等待这条记录的排他锁。

然后 B 执行：

```sql
START TRANSACTION;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
```

这次预期等待。切换到 A 执行 COMMIT 后，B 锁定读返回 900。最后 B ROLLBACK，在所有事务结束后恢复实验余额。

这个实验比较普通一致性读与锁定读，不能用“所有 SELECT 都不加任何锁”概括；例如 MDL 仍是另外一层机制。

## 11. 实验 3：观察间隙内插入等待

先在事务外准备独立表：

```sql
CREATE TABLE lock_ranges (
  id INT PRIMARY KEY
) ENGINE=InnoDB;
INSERT INTO lock_ranges(id) VALUES (10), (20), (30);
```

两个连接都在没有活动事务时确认 RR：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

A：

```sql
START TRANSACTION;
SELECT * FROM lock_ranges WHERE id >= 10 AND id < 20 FOR UPDATE;
```

B：

```sql
START TRANSACTION;
INSERT INTO lock_ranges(id) VALUES (15);
```

B 预期等待。A 查询返回的现有行中没有 15，但它仍可保护插入位置，这就是仅盯着返回行数会误判的原因。

A 执行 ROLLBACK 后，B 的插入完成，再在 B 执行 ROLLBACK，恢复表内原有三条记录。本实验只证明 15 的插入受到影响，不据此断言其他边界位置一定不被锁住。

## 12. 死锁与普通等待有什么区别

```text
普通等待：B 等 A；A 可以继续完成并释放锁

死锁：A 持有资源 1，等 B 的资源 2
      B 持有资源 2，等 A 的资源 1
```

在开启死锁检测的常见配置下，InnoDB 选择某个事务回滚以打破循环。被选中者不保证总是最后发 SQL 的连接。关闭检测等情况下也可能依赖超时结束等待。[死锁说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks.html)

### 实验 4：两个会话形成循环等待

确认前面事务都结束，accounts 两行都存在。严格按表格顺序：

| 步骤 | 会话 A | 会话 B |
| --- | --- | --- |
| 1 | START TRANSACTION; | |
| 2 | UPDATE accounts SET balance=balance+1 WHERE id=1; | |
| 3 | | START TRANSACTION; |
| 4 | | UPDATE accounts SET balance=balance+1 WHERE id=2; |
| 5 | UPDATE accounts SET balance=balance+1 WHERE id=2; → 等待 | |
| 6 | | UPDATE accounts SET balance=balance+1 WHERE id=1; → 构成死锁 |

一个会话通常收到 1213 / ER_LOCK_DEADLOCK，另一个可以继续。观察完在两个会话都执行 ROLLBACK，使幸存事务的修改也撤销，不把实验改动留下。[官方死锁实验](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlock-example.html)

### 为什么数据库必须打断其中一个事务

第 5 步结束时，A 持有账户 1，正在等账户 2；B 持有账户 2，但尚未等待 A，仍能继续操作。到第 6 步 B 又请求账户 1，等待关系才闭环：

```text
A 持有账户 1 ──想要账户 2──→ B
     ↑                        │
     └──────想要账户 1────────┘
```

这时只让两边“再等一会儿”没有用，因为谁都要等对方先释放。数据库回滚一个事务，才能让另一个继续。

若两个转账流程都按账户 id 从小到大获取锁，B 通常会在账户 1 处先等 A，无法先占住账户 2，从而避免这里的循环。获取顺序和实际扣款方向可以不同：先统一锁定顺序，再按业务方向修改金额。

## 13. 遇到死锁、超时应该怎样处理

死锁牺牲者的整个事务被回滚；锁等待超时在默认配置下通常只撤销失败语句。不能把二者当成相同的事务状态。

应用可以在确认放弃当前业务后显式回滚，再按策略有限重试整个事务。重试必须重新读取并重新判断，不能只重发最后一句并依赖过期结果。[错误处理规则](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)

降低冲突的方向：

- 多处操作相同资源时尽量使用一致顺序，例如先账户 1 再账户 2。
- 用合适索引缩小扫描和锁范围。
- 缩短事务，不在持锁期间等待外部接口、用户输入或长计算。
- 对可重试冲突设置次数上限及适当退避。
- 如果事务涉及外部副作用，先设计幂等与可靠投递，不能盲目重发扣款或通知。

一致顺序可以降低死锁风险，不是任意复杂业务绝无死锁的证明。

### 应用处理时，先识别错误，再决定是否重试

| 现象 | 常见错误 | 事务状态与处理 |
| --- | --- | --- |
| 形成循环等待，被选为受害者 | 1213 / ER_LOCK_DEADLOCK | 整个受害事务已回滚；如重试，应重新开始整个业务事务 |
| 等待超过时限 | 1205 / ER_LOCK_WAIT_TIMEOUT | 默认通常只撤销本条语句；决定放弃后显式回滚整个事务 |
| 条件更新影响零行 | 不一定是 SQL 错误 | 常是业务条件不满足或版本冲突，应走对应业务分支 |

例如一次转账已成功扣除账户 1，给账户 2 加钱时超时。若只忽略错误然后提交，默认语句级回滚规则下，可能提交“只扣不加”的结果。因此异常路径的事务回滚也是业务正确性的一部分。[错误回滚范围](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)

有限重试可以按下面的流程理解：

```text
开始新事务 → 重新读取和判断 → 执行全部业务写入 → 提交成功 → 返回成功
                   │
                   └→ 可重试的锁冲突 → 结束当前事务
                                       → 次数未超限：退避后从头再试
                                       → 次数已超限：返回失败
```

余额不足等业务失败不应盲目重试；提交时连接断开造成的“提交结果未知”也不能直接当成死锁重试。扣款接口还需要请求唯一标识等幂等设计，避免同一业务请求被重复执行。

## 14. 怎样判断“SQL 很慢”是否在等锁

先观察，不要直接结束未知会话：

```sql
SHOW FULL PROCESSLIST;
SELECT * FROM performance_schema.data_lock_waits;
SELECT ENGINE_TRANSACTION_ID, OBJECT_SCHEMA, OBJECT_NAME,
       INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_STATUS, LOCK_DATA
FROM performance_schema.data_locks
WHERE OBJECT_SCHEMA = 'study_tx_lock_lab';
SHOW ENGINE INNODB STATUS;
```

data_lock_waits 描述等待者与阻塞者的关系，data_locks 帮助查看具体对象和锁；权限、版本及 Performance Schema 配置会影响可见性。[等待表说明](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-data-lock-waits-table.html)

锁等待期间，可以另开第三个只读观察连接。SHOW ENGINE INNODB STATUS 中的最近死锁记录是诊断线索，不是所有历史死锁的完整存档；MDL 等待还需结合 metadata_locks 等信息分析。

HTTP 请求很慢还可能是连接池排队、SQL 扫描量大或网络问题，不能看到延迟就断言存在死锁。

### 按“等待者 → 阻塞者 → 未结束事务”追查

1. 先确认慢请求是否已经拿到数据库连接。还在连接池排队的请求，此时可能根本没有 SQL 在数据库执行。
2. 查 `data_lock_waits` 是否存在等待关系；若有，再通过 `data_locks` 的锁对象、事务 id 等字段关联等待者与阻塞者。
3. 结合 `SHOW FULL PROCESSLIST` 和 `information_schema.innodb_trx` 查看阻塞连接是否有长期未结束的事务。连接显示 Sleep，也可能仍持有事务锁，不能理解成“空闲就没有锁”。
4. 回到应用代码确认：是不是漏了 COMMIT / ROLLBACK，或持锁期间调用了慢接口。
5. 若是 ALTER TABLE 等结构变更等待，再查 `performance_schema.metadata_locks`，不要只看行锁表。

排查输出可能包含业务 SQL 和数据，应按项目规则处理。没有权限或查不到记录时，也不能据此认定从未发生过等待：短暂等待可能已经结束。

## 15. NOWAIT 与 SKIP LOCKED：进阶了解

```sql
START TRANSACTION;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
ROLLBACK;
```

NOWAIT 遇到冲突行锁时立即报错；报错后也要结束这次事务。

SKIP LOCKED 会跳过当前锁住的行，适用于经过设计的队列领取场景。它返回的集合可能不完整，不适合直接套在余额或库存校验上。二者主要针对行级锁，不保证对 MDL 等所有等待都生效。细节参见前面的锁定读官方说明。

## 16. 常见误解与自检

| 误解 | 正确理解 |
| --- | --- |
| 用了事务就不会超卖 | 还要正确表达条件与并发控制 |
| await 会阻止其他请求访问 | await 不提供数据库互斥 |
| FOR UPDATE 只要执行过一次就一直保护 | 必须在正确的同连接事务边界内使用 |
| UPDATE 有锁，就不会丢失更新 | 写回基于旧值计算的常量仍可能覆盖别人结果 |
| 没索引会自动升级成表锁 | 常见问题是扫描、加锁范围扩大 |
| RR 下所有读取都看到相同状态 | 要区分快照读、锁定读和自己的修改 |
| 乐观锁完全不使用数据库锁 | 版本检查语句仍需要正常的写锁 |
| 超时后整个事务必然没了 | 默认通常仅失败语句回滚 |

建议先完成实验 1、2，能解释“哪些请求等待，哪些仍然能读”；再做范围锁与死锁实验。最后尝试分别用条件 UPDATE、FOR UPDATE、version 检查解释同一扣款场景。

### 自测：先自己推演，再展开答案

> [!question]- 1. 两个事务都先读到 1000，再写入 900。UPDATE 本身有写锁，为什么结果仍然不对？
> 写锁让两次写入按冲突规则协调，但第二个事务写入的仍是应用根据旧值算出的 900。数据库无法知道它本意是“在别人扣款之后再扣 100”。应改用数据库内相减并检查条件，或在读取前锁定，或用版本条件发现过期读取。

> [!question]- 2. A 把余额改成 900 但没提交，B 普通查询得到 1000，这说明锁没生效吗？
> 不能这样判断。RC / RR 下 B 可以通过 MVCC 读到可见的已提交历史版本。若 B 要 UPDATE 或 FOR UPDATE 同一记录，则可能等待 A 的冲突锁。数据可见性和写入互斥需要分别分析。

> [!question]- 3. A 的 FOR UPDATE 已经返回，为什么 B 仍然改不了同一行？
> 语句返回不等于事务结束。显式事务中的保护需要跨越读取、判断和修改，通常到 COMMIT / ROLLBACK 才释放对应事务锁。

> [!question]- 4. 范围查询返回零行，为什么插入仍然可能等待？
> RR 下锁定范围扫描可能保护间隙，也就是尚不存在记录的插入位置。没有返回记录，不代表没有受保护的范围。

> [!question]- 5. 乐观更新影响零行，直接把 version 改成新值再发一次可以吗？
> 不可以只换版本号而保留旧计算结果。冲突表示计算前提可能已改变，需要重新读取、重新判断、重新计算，或者报告冲突。

> [!question]- 6. 遇到锁等待超时，能跳过失败 SQL，继续提交之前成功的语句吗？
> 如果这些语句属于必须整体完成的业务，就不能这么做。默认超时通常只撤销失败语句，之前的修改可能仍在事务里。应放弃并回滚整个业务事务，再判断是否有限重试。

能清楚说明事务边界、数据可见性、锁的持有与释放后，再学习 [[20-后端/数据库/06-Redis]] 的并发缓存更新部分。
