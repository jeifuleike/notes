# 事务

从事务用途进入 ACID、隔离级别与 MVCC。以 MySQL 8.x / InnoDB 为范围；实验只提供步骤与预期，不表示已经执行。

## 1. 先看问题：为什么需要事务

假设创建一个项目需要执行两条 SQL：

```text
1. 向 projects 插入项目
2. 向 project_members 插入 owner 成员
```

业务要求：项目和 owner 成员必须一起存在。

如果第一条成功后，第二条因为约束或连接问题失败，可能留下“有项目、没有 owner 成员”的半成品。分别执行两条 SQL，并不能自动表达“这一组操作一起成功”。

事务（Transaction）把一组数据库操作放在同一个提交边界中管理：满足业务条件时提交，失败时回滚未提交修改。

```text
开启事务
  ↓
插入项目
  ↓
插入 owner 成员
  ├─ 全部满足要求 → COMMIT
  └─ 中途失败     → ROLLBACK
```

“失败时回滚”需要正确的异常处理。数据库不会因为你的 Node 函数抛了一个普通 JavaScript 异常，就自动替你执行 ROLLBACK。

## 2. 事务与连接是什么关系

连接是应用与 MySQL 之间的一条会话通道。事务状态属于会话，不能只看 SQL 在代码里是否写在同一个函数中。

```text
同一个连接：START TRANSACTION → SQL A → SQL B → COMMIT
```

连接池里的 `pool.execute()` 可能为不同调用借出不同连接。直接依次调用它们，不保证参与同一个事务；需要借出 connection，并在该 connection 上完成整个事务。

`await` 只负责等待某个异步操作完成，不会创建数据库事务，也不阻止其他 HTTP 请求、Node 进程或 SQL 客户端同时访问数据库。

## 3. 提交、回滚、自动提交

### 1. 显式事务

```sql
START TRANSACTION;
-- 执行需要一起处理的 DML
COMMIT;
```

或者在不满足要求时执行 `ROLLBACK`。提交是接受本事务的修改；回滚是撤销尚未提交、且支持事务回滚的修改。

事务中的一条 UPDATE 返回成功，只能证明该语句执行成功，不能证明整个业务已提交。COMMIT 成功之后，再执行 ROLLBACK 也不能撤销上一个已提交事务。

### 2. 自动提交

```sql
SELECT @@session.autocommit;
SELECT @@session.transaction_isolation;
```

MySQL 通常默认 `autocommit=1`。没有显式事务时，普通 InnoDB DML 每条语句各自作为事务执行并提交。两条自动提交语句是两个事务，不是“自动合并成一个事务”。

即使 autocommit 为 1，也可以通过 START TRANSACTION 开启一段显式事务。对初学者，优先使用显式开始和结束，避免在连接池中随意改会话级 autocommit 后忘记恢复。[官方说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-autocommit-commit-rollback.html)

## 4. ACID：四个不同的问题

| 性质 | 中文 | 要回答的问题 |
| --- | --- | --- |
| Atomicity | 原子性 | 一组操作会不会留下部分完成的结果？ |
| Consistency | 一致性 | 操作前后是否仍满足约束和业务规则？ |
| Isolation | 隔离性 | 多个事务并发时，怎样控制彼此影响？ |
| Durability | 持久性 | 已提交结果在故障后怎样保留？ |

### 原子性

例如转账：A 扣 100，B 加 100。这两步作为一个事务提交；应用发现异常时回滚，不接受只扣钱未加钱的结果。

这不代表数据库里的外部 HTTP 调用、发邮件或 Redis 操作也会一起撤销，事务的作用范围要明确。

### 一致性

业务规则可以是“账户不能为负”“两账户转账前后总额不变”。数据库约束和正确的程序共同维护这些规则。

如果代码误写成 A 扣 100、B 加 50，然后正常提交，事务不会自动理解这违反了你的转账业务。ACID 不是业务代码正确性的替代品。

### 隔离性

多个事务可以重叠执行，并不一定逐个串行。隔离级别决定它们能观察到什么；锁与多版本机制用于实现对应规则。

“放进事务”不等于“其他人完全不能访问这些数据”，也不等于“先读后写就没有并发竞争”。

### 持久性

提交后的恢复依赖日志、配置及存储可靠性，不能只理解为“全部数据页已经写到磁盘”。详细内容复用 [[20-后端/数据库/55-InnoDB提交与刷盘]]，这里不重复展开。

以上用业务示例解释四种性质；InnoDB 事务模型见 [官方手册](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-model.html)。

## 5. 准备一个独立实验环境

以下是供你手动执行的实验，不代表已在本机运行。只在专用学习环境使用；表结构准备在实验事务之外完成。

选用不会与现有业务冲突的独立库名。若下面库名已经被其他用途使用，换一个新名称，不覆盖已有数据。

```sql
CREATE DATABASE study_tx_lock_lab;
USE study_tx_lock_lab;

CREATE TABLE accounts (
  id INT PRIMARY KEY,
  owner_name VARCHAR(50) NOT NULL,
  balance DECIMAL(12, 2) NOT NULL,
  version INT NOT NULL DEFAULT 0,
  CONSTRAINT chk_balance_nonnegative CHECK (balance >= 0)
) ENGINE=InnoDB;

INSERT INTO accounts(id, owner_name, balance)
VALUES (1, 'Alice', 1000.00), (2, 'Bob', 1000.00);
```

DECIMAL 便于精确表示固定小数金额。CHECK 在 MySQL 8.0.16 起才真正执行约束，旧版本不能照搬本例预期；具体检查行为见 [CHECK 约束](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html)。

后续每个客户端连接都执行 `USE study_tx_lock_lab`。同一个编辑器的两个标签页可能共用同一连接，用下面语句确认：

```sql
SELECT CONNECTION_ID();
```

A、B 必须返回不同 ID，才是两个独立会话。每个实验结束都提交或回滚后，再进入下一个实验。

## 6. 实验 1：亲手观察回滚和提交

同一个连接执行：

```sql
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
SELECT id, balance FROM accounts ORDER BY id;
ROLLBACK;
SELECT id, balance FROM accounts ORDER BY id;
```

事务内先看到 900 和 1100，回滚后恢复为 1000 和 1000。当前事务可以读取自己尚未提交的修改，这不叫“脏读其他事务”。

再执行一遍相同更新，但将 ROLLBACK 换成 COMMIT：

```sql
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
SELECT id, balance FROM accounts ORDER BY id;
```

这次接受 900 和 1100。为了后面的实验，在确认两个会话都没有活动事务后，用自动提交语句把专用实验数据恢复：

```sql
UPDATE accounts SET balance = 1000.00, version = 0 WHERE id IN (1, 2);
```

## 7. 为什么报错后还要显式回滚

不同错误可能撤销不同范围，不能用“SQL 报错了，前面的操作一定都取消了”判断。

| 情况 | InnoDB 常见处理 |
| --- | --- |
| 重复键等普通语句错误 | 失败语句回滚，事务仍可能继续存在 |
| 检测到死锁并被选为牺牲者 | 整个事务回滚 |
| 锁等待超时 | 默认只回滚超时语句；配置可改变行为 |

因此应用决定放弃这次业务后，应主动结束整个事务，不要继续提交之前的部分结果。错误行为以 [InnoDB 错误处理](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html) 为准。

回滚也不代表自增 ID 会恢复连续，不能用“ID 有空洞”判断是否回滚失败。

## 8. 并发读写会出现什么问题

数据库同时服务多个连接时，事务的语句会交错执行。并发本身不是错误：合理并发能提高吞吐量；问题在于一个事务读写时，另一个事务的修改可能改变它看到的数据，或与它准备写入的结果冲突。下面 A、B 是两个独立连接中的事务，时间线按从上到下阅读。

### 1. 脏读：使用了最终被撤销的数据

账户余额初始为 1000：

| 顺序 | 事务 A：修改余额 | 事务 B：查询余额 |
| --- | --- | --- |
| 1 | `START TRANSACTION` | `START TRANSACTION` |
| 2 | `UPDATE accounts SET balance = 900 WHERE id = 1`，尚未提交 | |
| 3 | | 查询得到 900 |
| 4 | `ROLLBACK`，余额回到 1000 | |

B 读到的 900 尚未成为数据库已提交的结果。若 B 用它计算费用、库存或另一笔转账，后续业务就可能建立在一个被撤销的状态上。

“脏”指未提交、仍可能回滚，不是指数据格式有问题。即使 A 后来提交，B 在提交前读取的动作仍是脏读；最终碰巧提交，不会改变读取发生时的语义。InnoDB 的 RC、RR 普通一致性读不会这样读取其他事务的未提交版本；RU 才允许这种可见性。

### 2. 不可重复读：同一行在事务中读出不同值

余额初始为 1000：

| 顺序 | 事务 A：读取余额 | 事务 B：修改余额 |
| --- | --- | --- |
| 1 | 开启事务，查询得到 1000 | |
| 2 | | 改为 900 并提交 |
| 3 | A 在同一事务中再次查询，得到 900 | |

变化的是原来那条账户记录的值。它不同于脏读：B 的修改已经提交，A 读到的是已提交数据，只是前后两次读取所处的可见数据不同。

“不可重复读”描述结果不能保证重复一致，不是说 SQL 不能重复执行。隔离级别和读的类型会影响是否出现；例如 InnoDB RR 下普通一致性读通常沿用同一个 Read View，而 RC 普通一致性读通常每条语句建立新视图。详见本篇第 9、10 节。

### 3. 幻读：同一条件命中的行集合发生变化

假设 A 查询余额至少为 500 的账户：

```sql
SELECT id, balance FROM accounts WHERE balance >= 500;
```

| 顺序 | 事务 A：范围查询 | 事务 B：新增账户 |
| --- | --- | --- |
| 1 | 开启事务，查询得到 3 行 | |
| 2 | | 插入余额为 800 的账户并提交 |
| 3 | A 再次执行相同条件查询，结果看起来多了 1 行 | |

与不可重复读对照：不可重复读通常关注已经读过的某一行的列值变了；幻读关注谓词（查询条件）匹配的行集合改变，例如新行进入结果，或某行不再满足条件。具体文献和数据库对术语边界有细节差异，这里按常见教学场景区分。

不能仅凭“同一个事务、同一条 SELECT”断言 InnoDB 一定出现幻读。普通快照读、锁定读（如 `FOR UPDATE`）、隔离级别以及索引范围都会影响结果或等待行为。RR 普通一致性读通常继续读原快照；锁定范围读则可能通过范围相关锁阻止并发插入。相关机制见第 9、12 节和 [[20-后端/数据库/05-锁与并发控制]]。

### 4. 丢失更新：两个写入都成功，最终只保留一个效果

两笔业务都要从余额 1000 中扣除 100。应用采用“先查、在程序里计算、再把新值写回”的方式：

| 顺序 | 事务 A | 事务 B |
| --- | --- | --- |
| 1 | 查询得到 1000 | |
| 2 | | 查询也得到 1000 |
| 3 | 程序计算 1000 - 100 = 900 | |
| 4 | | 程序也计算出 900 |
| 5 | 写入 900 并提交 | |
| 6 | | 写入 900 并提交 |

若两次扣款业务都报告成功，正确余额应该是 800，实际却是 900：B 根据旧值计算的 900 覆盖了 A 已完成的一次扣款。这就是丢失更新。

```sql
-- 风险写法：900 是应用基于此前读到的 1000 算出的固定值
UPDATE accounts SET balance = 900 WHERE id = 1;
```

数据库在执行 UPDATE 时会锁定要改的行，但 SQL 传入的是“设为 900”；数据库无法从固定值推断它是基于哪个版本计算出来的。对于单行扣款，可把计算和余额条件放在一条语句中：

```sql
UPDATE accounts
SET balance = balance - 100
WHERE id = 1 AND balance >= 100;
```

随后根据受影响行数判断是否扣款成功。复杂业务可以采用 `SELECT ... FOR UPDATE` 后在同一事务中校验并更新，或用版本号作乐观并发检查；方案取决于冲突频率、业务约束和重试策略，详见 [[20-后端/数据库/05-锁与并发控制]]。

### 5. 如何快速辨认这几类问题

| 异常 | 核心问题 | 最小辨认线索 |
| --- | --- | --- |
| 脏读 | 是否读到其他事务尚未提交的值？ | 对方后来回滚，读到的修改从未成立 |
| 不可重复读 | 同一事务重复读同一行，列值是否变化？ | 关注已有记录的值 |
| 幻读 | 同一事务重复执行谓词查询，结果行集合是否变化？ | 关注符合条件的记录集合 |
| 丢失更新 | 并发写入是否让其中一笔业务的更新效果消失？ | 常见于应用拿旧值算好固定值再覆盖写回 |

分析具体案例时，先画两个独立连接的时间线，再标明每次读到的是未提交值、当前已提交值还是事务快照；最后确认写语句是基于数据库当前值计算，还是应用传入了旧快照计算出的固定结果。隔离级别控制可见性的一部分，不能代替业务层面的原子更新、约束、锁或版本检查。

## 9. 四种隔离级别

隔离级别描述并发事务之间的数据可见性和相互限制。它与自动提交是两个不同设置：自动提交决定没有显式事务时语句何时提交；隔离级别决定并发事务如何观察彼此的修改。

| 级别 | 初步理解 |
| --- | --- |
| READ UNCOMMITTED（RU，读未提交） | 普通读可能看到其他事务尚未提交的修改，因此可能脏读 |
| READ COMMITTED（RC，读已提交） | 普通一致性读通常每条语句建立新的 Read View；不读未提交数据，但同一事务前后查询可能看到新提交 |
| REPEATABLE READ（RR，可重复读） | 同一事务的普通一致性读通常复用首次此类读取建立的 Read View，保持稳定视图 |
| SERIALIZABLE（串行化） | 施加更强并发限制，使已提交结果等价于某种事务先后顺序；冲突等待通常更多 |

InnoDB 默认通常是 RR，但实际连接可能被项目配置覆盖，应查询确认。SERIALIZABLE 不意味着服务器只剩一个线程或所有操作一律排队；不冲突的事务仍可能并发。

### 1. RU：可能读到尚未提交的值

若 B 把余额从 1000 改成 900 但未提交，A 在 RU 下的普通读可能读到 900。若 B 随后回滚，A 已经使用了一个从未成为已提交结果的值。因此 RU 允许脏读，实际业务很少适合依赖这种读法。

### 2. RC：每条普通查询确定一次新的可见视图

RC 下普通一致性读不会读到其他事务未提交的修改。假设 A、B 使用不同连接：

| 顺序 | 事务 A | 事务 B |
| --- | --- | --- |
| 1 | 开启事务，查询余额得到 1000 | |
| 2 | | 将余额改为 900，尚未提交 |
| 3 | 再查，仍得到 1000 | |
| 4 | | 提交 |
| 5 | 再查，得到 900 | |

可以把 RC 理解为每条普通一致性读语句开始时重新确定可见数据。它不是查询执行期间不断刷新结果；每条语句仍按自身开始时的视图完成读取。

### 3. RR：同一事务的普通查询通常复用同一快照

| 顺序 | 事务 A | 事务 B |
| --- | --- | --- |
| 1 | 开启事务 | |
| 2 | 第一次普通查询，得到 1000 并建立快照 | |
| 3 | | 将余额改为 900 并提交 |
| 4 | 同一事务再次普通查询，仍得到 1000 | |
| 5 | A 提交或回滚结束事务 | |
| 6 | A 开启新事务再查，得到 900 | |

B 的提交确认其修改已经保存，但不会改写 A 已建立的旧快照。RR 让同一事务的多次普通读取尽量基于稳定视图；代价是事务可能暂时看不到其他事务较新的已提交数据。

这对需要多次查询的业务有用。例如先统计订单总额，再读取订单明细；若两条查询之间有新订单提交，RC 的两次查询可能基于不同视图，而 RR 通常让它们共享同一普通读快照。实际选择仍需结合业务对新鲜度和稳定性的要求。

### 4. RR 的边界：不是事务中的所有语句都读旧快照

通常是第一次普通一致性读建立 Read View，而不是一执行 `START TRANSACTION` 就立刻冻结整个数据库：

```sql
START TRANSACTION;
-- 通常在此时还没有建立普通一致性读快照
SELECT balance FROM accounts WHERE id = 1;
-- 第一次普通一致性读通常在此建立 Read View
```

当前事务自己的修改通常对自己可见：事务先读到 1000，再把余额更新成 800，之后在同一事务查询通常能看到自己写入的 800。RR 也不表示“当前事务改了数据，自己仍必须读到原值”。

普通 `SELECT` 与锁定读、写操作要分开分析：

```sql
-- 普通一致性读：通常读事务快照
SELECT balance FROM accounts WHERE id = 1;

-- 锁定读：当前读，可能等待冲突锁
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
```

`UPDATE`、`DELETE` 等修改操作也不会简单地把旧快照当成当前值直接覆盖。因此不能把 RR 理解成事务内所有 SQL 都对同一份静态数据操作。显式一致性快照属于另一种用法，见 [一致性读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)。

### 5. 自动提交下的两次查询通常不共享事务快照

若 `autocommit=1` 且没有显式执行 `START TRANSACTION`，两条独立的普通 `SELECT` 通常各自作为独立事务结束。第一条查询结束后，第二条进入新事务并建立新的视图，所以 RR 下第二次查询也可能看到期间其他事务已经提交的修改。“RR 重复查询复用快照”的前提是这些查询确实处于同一事务中。

### 6. RR 如何处理幻读

InnoDB RR 下需要区分读取方式：

| 读取方式 | 常见处理 |
| --- | --- |
| 普通一致性读 | 继续读取事务快照，通常看不到快照建立后其他事务提交的新行 |
| 范围锁定读 | 通常使用 next-key 等范围相关锁，阻止相关范围内的并发插入 |

例如 `SELECT * FROM accounts WHERE balance >= 500 FOR UPDATE` 是范围锁定读。具体锁住哪些记录和间隙，受索引、条件和执行计划影响。不能因此推导“RR 中任意混合读写流程都等价于串行执行”。[隔离级别官方说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)

### 7. 查看与设置隔离级别

```sql
SELECT @@session.transaction_isolation;
SELECT @@session.autocommit;

-- 在事务开始前，为当前连接设置后续事务的隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
-- 业务 SQL
COMMIT;
```

需要 RR 时可将级别设为 `REPEATABLE READ`。`SESSION` 只影响当前连接，不会直接改掉连接池中所有其他连接。项目可能沿用数据库默认值，也可能统一配置 RC 或为特定事务指定级别；排查行为时应检查实际连接，而不是只凭默认值推断。[隔离级别官方说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)

## 10. MVCC：为什么别人写着，我还能读

MVCC 是多版本并发控制（Multi-Version Concurrency Control）。它帮助 InnoDB 的普通一致性读在并发写入时读取当前事务可见的版本，减少读写双方互相阻塞的需要。

### 1. 如果只能读写一个版本

假设 B 正把余额从 1000 改为 900，但尚未提交。A 此时要查询，又不能读取未提交的 900。若数据库只能提供正在修改的一个版本，一个简单办法是让 A 等到 B 提交或回滚；大量普通查询都等待写事务，会降低读写并发效率。

### 2. 多版本让普通读可以读取历史值

```text
B 正在修改：较新版本 900，尚未提交
                         ↓
A 的普通一致性读不能读未提交的 900，可读取对 A 可见的已提交版本 1000
```

这不是给每个事务复制一份完整数据库。InnoDB 利用行上的版本信息和 undo 记录等，在需要时构造历史版本。于是 B 可以继续修改，A 的普通查询通常可以读取合适的历史版本，而不必等待 B 释放该行的写锁。[多版本机制](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html)

### 3. Read View 决定哪个版本可见

存在多个版本后，数据库还要判断当前查询可以读取哪一个。Read View 可理解为一组版本可见性规则：数据库依据版本所属事务及事务状态判断其是否对当前读取可见；若较新版本不可见，就沿版本链寻找符合规则的旧版本。

因此“快照”是逻辑上的数据视图，不是把整张表拍照并复制一遍。

### 4. MVCC 与 RC、RR 的关系

RC 与 RR 都能利用多版本读取，主要差异在普通一致性读使用 Read View 的时机：

| 隔离级别 | Read View 的常见使用方式 |
| --- | --- |
| RC | 每条普通一致性读语句通常创建新的 Read View |
| RR | 同一事务通常复用第一次普通一致性读创建的 Read View |

例如 A 第一次读取余额为 1000，随后 B 将余额改为 900 并提交，A 再次普通查询：RC 通常建立新 Read View 并读到 900；RR 通常沿用原 Read View 并仍读到历史版本 1000。MVCC 解释“为什么能读历史版本”，隔离级别决定“当前查询按什么规则选择版本”。

### 5. MVCC 不会替代所有锁

MVCC 主要帮助普通一致性读与写操作并发。两笔事务同时修改同一账户或库存行时，仍需要锁等机制协调；`SELECT ... FOR UPDATE` 也是锁定读，可能等待冲突事务。MVCC 不等于数据库不加锁，也不自动解决应用层丢失更新。锁等待、死锁和业务并发策略见 [[20-后端/数据库/05-锁与并发控制]]。

### 6. 长事务会延长历史版本的保留

若 A 在 RR 下建立快照后长期不提交或回滚，其他事务仍持续修改数据，数据库可能需要保留 A 后续读取所需的 undo 历史，延迟清理。长事务会增加历史版本保留与后台清理压力；只读事务也不应无故长期打开。应用应缩短事务范围，避免在事务内等待用户输入或执行耗时外部网络调用。[多版本机制](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html)

RR 下通常是第一次普通一致性读建立快照，不是简单执行 START TRANSACTION 就立即给所有查询拍照；显式一致性快照等用法需另行区分。当前事务自己的修改通常可见，不能把快照理解成“本事务任何操作后结果都绝对不变”。[一致性读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)

长事务可能让历史版本需要保留更久，增加清理压力。因此“只读事务”也不应长时间放着不结束。

## 11. 实验 2：比较 RC 与 RR

先结束所有实验事务，把 id=1 的余额恢复到 1000。按表格逐步执行，不能一次性执行 A 的整段后再执行 B。

会话 A 在没有活动事务时设置：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

| 步骤 | 会话 A | 会话 B |
| --- | --- | --- |
| 1 | START TRANSACTION; | |
| 2 | SELECT balance FROM accounts WHERE id=1; → 1000 | |
| 3 | | START TRANSACTION; |
| 4 | | UPDATE accounts SET balance=900 WHERE id=1; |
| 5 | SELECT balance FROM accounts WHERE id=1; → 1000 | 尚未提交 |
| 6 | | COMMIT; |
| 7 | SELECT balance FROM accounts WHERE id=1; → 900 | |
| 8 | COMMIT; | |

接着恢复余额，A 在事务外将隔离级别改为 RR：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

重做同样步骤，步骤 7 的普通 SELECT 预期仍是 1000。A 提交后再次查询，才读到 B 已提交的 900。

完成后让 A、B 都显式结束事务，再恢复实验余额。此实验只针对普通一致性 SELECT，不能把同样预期直接套到 SELECT ... FOR UPDATE。

## 12. 快照读与锁定读

| 写法 | 常见作用 |
| --- | --- |
| SELECT ... | RC / RR 下通常是一致性快照读 |
| SELECT ... FOR UPDATE | 读取并取得排他锁，供后续安全判断和修改 |
| SELECT ... FOR SHARE | 读取并取得共享锁 |
| UPDATE / DELETE | 针对需要修改的数据执行并取得必要锁 |

锁定读会等待冲突事务结束，再基于可操作的当前数据处理，不应当作旧快照查询。RR 下混合快照读和锁定读，可能观察到不同视角；详细示例见 [[20-后端/数据库/05-锁与并发控制]]。

## 13. SAVEPOINT 与事务边界的常见误解

```sql
START TRANSACTION;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
SAVEPOINT after_first_change;
UPDATE accounts SET balance = balance + 10 WHERE id = 2;
ROLLBACK TO SAVEPOINT after_first_change;
ROLLBACK;
```

回到保存点只撤销其后的部分修改，不结束整个事务；最后的完整 ROLLBACK 才放弃本事务。保存点也不是嵌套提交，不能把它当作可以独立持久化的子事务。[SAVEPOINT](https://dev.mysql.com/doc/refman/8.4/en/savepoint.html)

大部分 CREATE / ALTER / DROP 等 DDL 会触发隐式提交，TRUNCATE 也不能按普通 DELETE 的方式回滚。临时表等存在特例，不能靠“外面包了 START TRANSACTION”判断一切都能撤销。MySQL 也不支持通过重复 START TRANSACTION 创建真正嵌套事务。[隐式提交规则](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)

## 14. 放进 Node 项目时如何组织

```text
Service 借出连接
  ↓
开启事务
  ↓
Repository A 使用此连接
  ↓
Repository B 使用此连接
  ├─ 满足业务条件 → commit
  └─ 异常 → 尝试 rollback，保留原始错误
  ↓
finally 归还连接；已损坏的连接丢弃
```

关键判断：

- 事务内 SQL 都使用同一连接，不能中途又走 pool 去写。
- 不在事务里等待用户输入、长时间计算或外部网络调用。
- 事务提交后的额外查询失败，不代表已经提交的修改可以回滚。
- commit 时网络断开，应用可能无法确定数据库是否已经提交；不能不加判断地重复扣款，需要业务唯一键和幂等机制。
- HTTP 客户端重试不是一个新业务的证明，要区分同一操作的重复请求。

本项目事务编排代码与回滚验收仍见 [第 15 章](../../../node/node-backend-study/labs/15-transactions/README.md)。这里解释通用知识，不通过文档填写练习代码。

## 15. 学到什么程度再进入锁

能自己解释并观察下面的问题。每个问题下的答案默认折叠，点击问题标题展开：

> [!question]- 1. 自动提交下，两条 SQL 为什么不能自动保证一起成功？
> 自动提交开启时，没有显式事务包住的每条 InnoDB DML 通常各自提交。第一条成功后，即使第二条失败，第一条也不会因为第二条失败而自动回滚。若业务要求多条 SQL 一起成功或一起失败，必须在同一连接显式开启事务，并在全部成功后 `COMMIT`，失败时 `ROLLBACK`。

> [!question]- 2. 事务中的 SQL 成功与 COMMIT 成功有什么区别？
> 单条 SQL 成功表示语句在当前事务中执行完成，修改仍属于尚未结束的事务，之后仍可能回滚。`COMMIT` 成功才表示数据库接受并提交了整个事务的修改。若提交时连接中断，客户端可能无法确定服务端是否已经提交，不能把“没收到成功响应”直接当作“肯定没提交”。

> [!question]- 3. 为什么普通 SQL 报错后不能假设整个事务都回滚？
> InnoDB 对不同错误的处理范围不同：普通语句错误常只撤销失败的那条语句，事务仍可能保持开启；死锁受害事务通常整体回滚；锁等待超时默认通常只回滚当前语句（配置可能改变行为）。因此应用若决定放弃业务，应在异常处理路径显式回滚整个事务，并确保连接归还前没有遗留活动事务。

> [!question]- 4. 两个独立连接中，RC 与 RR 普通查询的结果为什么不同？
> InnoDB 下，RC 的普通一致性读通常每条语句建立新的 Read View，所以事务 A 第二次查询前若事务 B 已提交修改，A 通常能看到新值。RR 的普通一致性读通常复用本事务首次一致性读建立的 Read View，因此 A 后续查询仍看到原快照中的值。这里讨论的是普通快照读；`SELECT ... FOR UPDATE` 等锁定读遵循不同规则。

> [!question]- 5. 为什么事务和 `await` 都不能自动避免丢失更新？
> 事务定义一组数据库操作的提交边界，但并不意味着不同事务不能并发。`await` 只等待当前异步调用完成，也不会阻止其他请求或连接操作同一行。若两个事务都先读到 1000，在应用中分别算出 900，再写入固定值 900，后一次写入会覆盖前一次效果。应按业务使用原子条件更新、锁定读，或带版本号的条件更新并处理冲突。

## 16. Transaction：先画出必须一起成立的业务边界

创建项目的业务不变量是：项目存在时，指定负责人必须有对应 owner 成员关系。

```text
同一连接开始事务
  ↓
插入项目，取得 ID
  ↓
插入 owner 成员关系
  ├─ 全部成功 → 提交
  └─ 失败 → 回滚
```

转让负责人则可能涉及更新 projects.owner_id、调整旧成员角色、调整新成员角色。这些需要放到同一个业务边界中，并考虑两个转让请求同时发生时如何协调。

| 规则 | 可能承担的机制 |
| --- | --- |
| 成员不重复 | 联合主键或唯一约束 |
| 负责人用户存在 | 外键 |
| 项目和初始成员一起创建 | 事务 |
| 两个请求不能覆盖对方负责人变更 | 锁定读、条件更新或版本检查 |
| 当前访问者能否转让负责人 | Service 权限判断 |

一个机制不能代替全部其他机制。尤其“先查是成员，再执行修改”之间可能发生成员退出，严格并发要求需要把检查和修改一起设计。

事务基础、ACID、隔离与实验见本篇前面的对应章节；锁与并发策略见 [[20-后端/数据库/05-锁与并发控制]]；持久化见 [[20-后端/数据库/55-InnoDB提交与刷盘]]。

**本阶段产出**：每个重要用例的事务边界、失败结果、并发策略和重试/幂等要求。不是给所有接口统一套一个事务。

## 17. 事务：COMMIT / ROLLBACK

### 一个可回滚的练习

```sql
START TRANSACTION;

UPDATE sql_practice_tasks
SET status = 2
WHERE project_id = 100;

-- 检查本事务中的修改
SELECT *
FROM sql_practice_tasks
WHERE project_id = 100;

-- 放弃修改
ROLLBACK;
```

如果确认业务修改正确，应使用：

```sql
START TRANSACTION;

UPDATE sql_practice_tasks
SET priority = 4
WHERE project_id = 100;

COMMIT;
```

### 什么情况下要事务？

例如同一个业务操作需要：

1. 创建项目记录；
2. 写入项目创建者的成员记录；
3. 两步必须同时成功或同时失败。

这类跨多条 SQL 的一致性要求，适合用事务控制。

### 必须记住的边界

- 事务主要保护一组数据库操作的原子性等性质，前提是存储引擎支持事务（例如 InnoDB）。
- 事务内执行 DDL（如大部分 `ALTER TABLE`、`TRUNCATE`）可能发生**隐式提交**。
- `ROLLBACK` 不能撤销已经成功 `COMMIT` 的修改。
- Node.js 使用连接池时，同一事务中的 SQL 必须在**同一数据库连接**上执行。
