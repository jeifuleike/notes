# 登录处理重点：密码、Cookie、JWT 与 Session

本文整理第 16 节学习中讨论的登录处理概念，重点区分“如何验证密码”“用什么证明身份”“凭证怎样传输”和“如何判断权限”。不提供练习实现答案。

## 1. 先把四个问题分开

| 问题 | 本项目如何处理 |
| --- | --- |
| 输入的密码是否正确？ | 用原盐重新执行 scrypt，与保存结果比较 |
| 当前请求是谁发来的？ | 验证 JWT，取得用户 ID，并检查用户仍存在 |
| 登录凭证怎样传给服务端？ | 客户端主动设置 Authorization 请求头 |
| 当前用户能访问这个项目吗？ | 查询 project_members 中的真实成员关系 |

Cookie、JWT、session ID 不是同一层面的三种替代品：Cookie 是浏览器保存和携带数据的机制；JWT 是一种令牌格式；session ID 是查找服务端会话的标识。JWT 和 session ID 都可以通过 Cookie 发送。

## 2. 注册：密码参与计算，盐和结果参与存储

用户提交邮箱、密码等信息后，服务端生成随机盐，把密码、盐及派生参数交给 scrypt，得到派生结果。然后保存算法标记、盐和派生结果，不保存密码明文。

本项目存入 users.password_hash 的结构为：

```text
scrypt:随机盐:派生结果
```

不是“随机盐拼接原始密码”。密码和盐是 scrypt 的输入；它们不是被原样拼起来当作密码保存。

### 盐是什么，存在哪里

盐是每次生成密码保存值时产生的随机数据。它不需要保密，却必须随结果保存，否则以后无法按相同条件验证密码。

本项目使用 randomBytes 生成 16 字节盐，再用十六进制编码成 32 个字符。scrypt 生成 64 字节结果，编码后为 128 个十六进制字符。十六进制只是字节的文本表示，不是加密。

相同密码、相同盐和相同参数会产生相同结果；盐不同，结果通常不同。因此两个账户即使密码相同，也应有不同保存值。盐降低了攻击者对大量账户复用预计算结果的价值，scrypt 的成本则让每次猜测更耗资源；弱密码仍可能被逐个猜中。

### scryptCallback、promisify 和数据库各做什么

- scrypt 是 node:crypto 提供的密码派生函数，负责计算，不是本地存储。
- scryptCallback 是项目给原始回调版 scrypt 起的别名。
- promisify 把回调式调用转换为 Promise 形式，方便通过 await 等待结果，不改变算法。
- hashPassword 返回约定格式的保存字符串；Repository 再把它写入 MySQL。

保存格式需要与验证算法一致。本项目没有在字符串中记录成本参数，如果将来修改参数，还需要考虑旧数据兼容与版本设计。

## 3. 登录：取原盐重新计算，不解密密码

服务端根据邮箱查到用户后，从 password_hash 中取出原盐和原派生结果。使用本次输入的密码、原盐和相同参数重新计算，再比较结果。

```text
注册：原始密码 + 随机盐 → 派生结果 → 保存盐和结果
登录：本次密码 + 原来的盐 → 新结果 → 与原结果比较
```

验证时不能重新生成盐，否则计算条件不同，正确密码也无法正常匹配。这里没有从数据库还原原密码的过程，服务端只是重复计算并比较。

本项目先检查保存格式，再把结果恢复成 Buffer，用 timingSafeEqual 比较。它要求两个输入字节长度相同，只保护比较操作本身，不代表整个登录流程耗时完全一致。

用户不存在、密码错误或旧用户没有密码保存值时，统一返回 401 INVALID_CREDENTIALS。统一文案避免直接暴露邮箱存在性，但不等于消除了所有账户枚举渠道或计时差异。

登录成功后才签发 token；注册成功并不自动登录，本项目需要再调用登录接口。

## 4. 前端先做 SHA-256，后端会存什么

如果公司项目是“前端将密码做 SHA-256，再发送后端”，只能说明服务端接收的是前端处理结果，不能单凭这一点判断数据库内容。

| 后端做法 | 实际保存内容 |
| --- | --- |
| 原样保存收到的值 | 前端的 SHA-256 结果 |
| 把收到的值再加随机盐做密码派生 | 盐与二次派生结果 |

需要查看后端注册、改密的写入逻辑，以及登录时的比较逻辑，才能确定。

如果每次登录提交的 SHA-256 结果都相同，该结果本身就成为可以用于登录的凭证。别人拿到它后，可能不需要知道原始密码就能直接提交它。因此前端哈希不替代 HTTPS，也不替代后端密码存储保护。

## 5. JWT：验证签名与声明后取得身份

本项目登录成功后返回 JWT，里面包含用户 ID、签发时间、过期时间等声明，再用服务端密钥签名。

| 声明 | 含义 |
| --- | --- |
| sub | 用户身份，本项目为用户 ID 的字符串 |
| iss | 签发方 |
| aud | 预期接收方 |
| iat | 签发时间 |
| exp | 过期时间 |

本项目采用 HS256，签发与验证使用同一份服务端密钥。签名 JWT 的载荷通常可以读取，签名用于发现篡改，不会加密内容。不能把密码或密码哈希放进载荷。

后续请求通过 Authorization 头发送：

```http
Authorization: Bearer <token>
```

服务端必须验证签名、允许的算法、有效期、签发方、接收方和必需声明，再检查 sub 是否符合项目用户 ID 规则。仅解码载荷不能证明它可信。

验签通过后，服务端仍可能查数据库：确认用户未删除、读取用户资料、查询项目权限。JWT 不等于每次请求完全不查数据库。

## 6. Cookie：后端如何设置，浏览器如何自动携带

Cookie 是浏览器内置的保存和传输机制。以同源 HTTPS 请求为例，登录成功后，服务端可以在 HTTP 响应头中设置：

```http
Set-Cookie: sessionId=abc123; Path=/; HttpOnly; Secure; SameSite=Lax
```

这里的 abc123 只是便于理解的示意值，实际 session ID 应不可预测。

浏览器收到响应后，根据 Cookie 规则决定是否保存。这不是服务端直接操作浏览器文件，也不是把 sessionId 写入 JSON 就能自动保存。

随后访问匹配的地址时，浏览器会检查主机、路径、过期状态、Secure、SameSite 以及请求的凭证设置等条件，符合规则就自动附加：

```http
Cookie: sessionId=abc123
```

| 方向 | 请求头或响应头 | 作用 |
| --- | --- | --- |
| 服务端 → 浏览器 | Set-Cookie | 要求浏览器保存或更新 Cookie |
| 浏览器 → 服务端 | Cookie | 携带符合发送条件的名称和值 |

Cookie 的 Path、HttpOnly 等属性不会作为这条 Cookie 的属性原样跟随请求发送，而由浏览器用于管理和判断。

### 常见属性

- HttpOnly：阻止页面 JavaScript 直接读取 Cookie，但浏览器仍可自动发送。
- Secure：限制通过 HTTPS 发送。
- SameSite：控制 Cookie 在不同站点上下文中的发送行为，是 CSRF 防护的一部分。
- Path：限制匹配的请求路径，不应当作访问控制边界。
- Domain：影响可发送的主机范围；不设置时为设置该 Cookie 的主机。
- Max-Age / Expires：指定有效时间。没有显式指定时通常是会话 Cookie，但浏览器的会话恢复行为也会影响实际保留情况。

### 跨域时为什么不一定自动带上

同源 fetch 默认允许携带同源凭证。前后端不同源时，fetch 通常需要配置 credentials 为 include；服务端还需配置允许凭证的 CORS 响应，并明确允许的前端源，不能用通配符代替。

include 不会绕过 Cookie 的域、路径、SameSite 或浏览器隐私限制。跨源也不一定是跨站，例如 app.example.com 与 api.example.com 是不同源，在相同协议等条件下却可属于同站；CORS 和 SameSite 管的是不同边界。

## 7. JWT 与 session ID 的区别

session ID 通常是不可预测的随机编号。服务端保存“编号 → 用户 ID、过期时间等”的会话记录，记录可以放在 Redis、数据库或内存中。每次收到编号，查询会话是否有效，才能确定身份。

JWT 则携带声明和签名。服务端可通过验证签名与声明取得身份，通常不需要保存每一枚 token 对应的会话记录。

| 对比 | session ID | JWT |
| --- | --- | --- |
| 客户端持有什么 | 随机会话编号 | 包含声明与签名的令牌 |
| 身份信息主要在哪 | 服务端会话记录 | JWT 载荷 |
| 主要验证方式 | 查询有效会话 | 验证签名与声明 |
| 立即撤销 | 删除或作废会话记录 | 需额外机制，如拒绝列表、版本检查等 |
| 如何发送 | Cookie 或其他约定方式 | Cookie 或 Authorization 头等方式 |

清除客户端 JWT 只代表该客户端不再发送；如果别人已有副本，单靠清除无法让副本失效。在仅验签的方案中，副本可能一直有效到过期。

session ID 若只从浏览器删除、服务端会话仍有效，也不能保证已被盗副本失效。撤销需要让服务端不再接受该凭证。

## 8. Cookie 与 token：传输机制和凭证要分开看

当前练习采用“响应体返回 JWT → 客户端保存 → 主动设置 Authorization 头”。另一种方式可以是“响应头 Set-Cookie → 浏览器保存 JWT → 自动通过 Cookie 发送”。

所以不能简单记成“Cookie 是后端登录，token 是前端登录”。后端都需要验证凭证，只是凭证格式、保存和携带方式不同。

| 要决定的问题 | 可能的选择 |
| --- | --- |
| 用什么证明身份 | session ID、JWT 等 |
| 怎样传给服务端 | Cookie、Authorization 头等 |
| 服务端怎样判定权限 | 查数据库里的成员关系等业务规则 |

## 9. Cookie 被劫持，是不是应该废弃

登录劫持常指攻击者获得凭证后冒充用户。Cookie 里的 session ID 被盗有风险，Bearer JWT 被盗同样有风险；更换名称或传输方式不会自动消除风险。

| 风险 | 需要理解的保护边界 |
| --- | --- |
| 网络窃听 | 两种方式都需要 HTTPS；Secure 限制 Cookie 经 HTTPS 发送 |
| XSS：页面执行恶意脚本 | HttpOnly 阻止直接读取 Cookie，但不能阻止恶意脚本在页面内发起所有操作；JS 可读存储中的 token 可能被窃取 |
| CSRF：诱导浏览器发起带凭证的请求 | Cookie 会自动携带，需要按场景设置 SameSite、验证 CSRF token 或请求来源等；手动 Authorization 方案通常不依赖这条自动携带路径 |

HttpOnly 不等于能防住所有 XSS，SameSite 也不等于完整解决所有 CSRF 问题。

“废弃 Cookie”的讨论有时指第三方 Cookie 的跨站追踪与隐私问题，不是要求所有网站停止用 Cookie 维持登录。第一方登录 Cookie 与第三方追踪 Cookie 需要区分，不能把某个浏览器的隐私策略理解为 Cookie 整体失效。

## 10. 认证通过，不代表具有项目权限

认证回答“你是谁”，授权回答“你能做什么”。

用户 A 和 B 都可以拿到各自的有效 JWT，但 B 并不因此拥有 A 的项目权限。本项目用可信用户 ID 和请求的项目 ID 查询 project_members，有真实成员关系才允许读取成员列表。

- 401：登录凭据不成立，或请求未通过认证。
- 403：身份已确认，但没有项目权限。
- 404：按本项目顺序，目标项目不存在。

每次查数据库中的成员关系，能让后续请求反映成员变更，不必单纯等待 JWT 过期。但多次独立查询不是自动隔离的事务，更严格的并发权限要求需要另行设计。

## 12. 最后记住这几件事

1. 盐随机生成，和派生结果一起保存；原始密码只参与计算，不直接入库。
2. 登录用原盐重新计算，不是解密数据库里的密码。
3. 前端固定哈希也可能成为可重放凭证，不能代替 HTTPS 和后端密码保护。
4. JWT 与 session ID 是凭证方案，Cookie 是保存和携带机制，两者不能混为一谈。
5. Set-Cookie 是响应头；Cookie 是浏览器后续发送的请求头。
6. token 验证身份，数据库成员关系决定项目权限。
7. 清除客户端凭证与服务端撤销凭证不是一回事。
8. 凭证被盗对两类方案都有风险，必须理解实际保护边界。
