# MySQL 数据库核心知识整理

## 一、数据库为什么需要索引

当数据量很小时：

``` sql
SELECT * FROM users WHERE id = 100;
```

数据库可以直接扫描。

但是当数据达到：

-   百万级
-   千万级
-   亿级

如果每次都从第一条扫描，会非常慢。

索引的作用：

> 建立一种快速定位数据的数据结构，减少需要扫描的数据量。

类似书籍目录：

没有目录： - 一页一页翻

有目录： - 先找章节 - 再找具体内容

------------------------------------------------------------------------

# 二、B+ Tree 索引结构

MySQL InnoDB 常用 B+ Tree 作为索引结构。

核心思想：

> 先找到范围，再逐层缩小搜索。

例如：

                  [100 | 500]
                 /      |      \
              <100   100~499   >=500

查询：

    id = 238

过程：

    根节点
     ↓
    判断 238 属于 100~499
     ↓
    进入对应节点
     ↓
    继续查找
     ↓
    找到数据

优势：

-   不需要遍历所有数据
-   查询复杂度低
-   适合大量数据

------------------------------------------------------------------------

# 三、聚簇索引

在 InnoDB 中：

通常：

    PRIMARY KEY
            ↓
    聚簇索引

特点：

> 叶子节点保存完整数据行。

例如：

    id = 100

    username = Tom
    email = tom@test.com
    status = 1

全部存储在聚簇索引叶子节点。

查询：

``` sql
SELECT *
FROM users
WHERE id = 100;
```

过程：

    主键索引
     ↓
    找到 id=100
     ↓
    直接返回整行数据

不需要再次查询。

------------------------------------------------------------------------

# 四、普通索引（二级索引）

例如：

``` sql
CREATE INDEX idx_email
ON users(email);
```

这是一棵新的 B+ Tree。

但是叶子节点不是完整数据。

而是：

    email + 主键id

例如：

    tom@test.com → 100

为什么保存主键？

因为 InnoDB 的真实数据在聚簇索引中。

------------------------------------------------------------------------

# 五、回表

查询：

``` sql
SELECT *
FROM users
WHERE email='tom@test.com';
```

执行过程：

    email普通索引

            ↓

    找到：
    email=tom@test.com

    得到：
    id=100

            ↓

    根据id查询主键索引

            ↓

    获得完整数据

这个过程叫：

> 回表

原因：

普通索引没有保存完整数据，需要再次访问聚簇索引。

------------------------------------------------------------------------

# 六、覆盖索引

如果查询需要的字段全部存在索引中：

就不需要回表。

例如：

索引：

    email + id

查询：

``` sql
SELECT id,email
FROM users
WHERE email='tom@test.com';
```

需要：

    id ✅
    email ✅

索引已经包含。

流程：

    普通索引
     ↓
    直接返回

这叫：

> 覆盖索引

------------------------------------------------------------------------

# 七、联合索引

例如：

``` sql
CREATE INDEX idx_project_status
ON tasks(project_id,status);
```

不是两个索引：

    project_id索引
    +
    status索引

而是一棵：

    (project_id,status)

联合排序的 B+ Tree。

排序规则：

    先按照 project_id 排序

    project_id相同

    再按照 status 排序

例如：

    (1,0)
    (1,1)
    (1,2)

    (2,0)
    (2,1)

------------------------------------------------------------------------

# 八、最左前缀原则

假设：

``` sql
INDEX(a,b,c)
```

可以理解为：

    a
     ↓
    b
     ↓
    c

可以使用：

``` sql
WHERE a=1
```

✅

``` sql
WHERE a=1 AND b=2
```

✅

``` sql
WHERE a=1 AND b=2 AND c=3
```

✅

但是：

``` sql
WHERE b=2
```

通常无法充分利用。

原因：

索引首先按照 a 排序。

不知道 a，就无法快速定位 b。

注意：

SQL 条件顺序不重要：

``` sql
WHERE b=2 AND a=1
```

仍然可以使用：

    INDEX(a,b)

因为优化器会处理。

------------------------------------------------------------------------

# 九、EXPLAIN

EXPLAIN 用来查看：

> MySQL 准备如何执行 SQL。

使用：

``` sql
EXPLAIN
SELECT *
FROM users
WHERE email='test@qq.com';
```

它不会真正查询数据。

而是返回执行计划。

重点关注：

## key

实际使用的索引。

例如：

    key:
    idx_email

表示使用：

    idx_email

## rows

预计扫描行数。

例如：

    rows:10000000

表示预计检查大量数据。

## type

查询方式。

常见：

### ALL

全表扫描：

    一行一行检查

### ref

通过索引找到一批数据。

### range

范围查询。

# 十、数据库实战练习路线

## 实验1：无索引

创建：

    tasks

插入：

    100万数据

执行：

``` sql
EXPLAIN
SELECT *
FROM tasks
WHERE project_id=100;
```

观察：

    type=ALL
    key=NULL

说明：

全表扫描。

------------------------------------------------------------------------

## 实验2：添加索引

``` sql
CREATE INDEX idx_project
ON tasks(project_id);
```

再次：

``` sql
EXPLAIN
SELECT *
FROM tasks
WHERE project_id=100;
```

观察：

索引生效。

------------------------------------------------------------------------

创建：

``` sql
CREATE INDEX idx_project_status

```

测试：

``` sql
WHERE project_id=100

```

理解联合索引。

## 实验4：覆盖索引

测试：

``` sql
SELECT id,project_id,status

```

观察：

是否避免回表。

# 十一、学习总结

数据库学习核心链路：

    表设计
     ↓
    主键
     ↓
    索引
     ↓
    B+ Tree
     ↓
    聚簇索引
     ↓
    二级索引
     ↓
    回表
     ↓
    覆盖索引
     ↓
    联合索引
     ↓
    最左前缀
     ↓
    EXPLAIN
     ↓
    SQL优化

核心理解：

> 索引不是简单加速，而是通过数据结构改变查找方式。

> 聚簇索引保存真实数据。

> 普通索引保存索引字段和主键。

> 回表是通过普通索引找到主键后，再查询完整数据。

> 覆盖索引是不需要回表。

> 联合索引的字段顺序决定查询效率。

> EXPLAIN 用来验证 MySQL 是否按照预期使用索引。
