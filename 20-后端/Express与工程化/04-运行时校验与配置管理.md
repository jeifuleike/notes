```text
Runtime Validation
Environment Config
```

整体链路会变成：

```text
Request
↓
JSON Parser
↓
Validation
↓
Router
↓
Controller
↓
Service
↓
Repository
↓
下一步接 Database
```

## 1. TypeScript 类型为什么保护不了 HTTP 请求

例如：

```ts
export interface CreateUserDTO {
  name: string
  age: number
  email: string
}
```

然后：

```ts
export function createUser(
  req: Request,
  res: Response,
) {
  const data: CreateUserDTO =
    req.body
}
```

看起来 `data` 好像一定符合：

```ts
{
  name: string
  age: number
  email: string
}
```

实际上客户端完全可以发送：

```json
{
  "name": 123,
  "age": "abc",
  "email": false,
  "admin": true
}
```

原因是：

```text
TypeScript 类型
↓
只存在于编译期

HTTP Request
↓
是运行时真实数据
```

编译成 JavaScript 后：

```ts
interface CreateUserDTO
```

已经不存在了。

因此后端必须遵守：

> 所有外部输入默认都不可信。

包括：

```text
req.body
req.params
req.query
req.headers
cookie
文件上传
```

## 2. Runtime Validation

运行时校验就是：

```text
未知数据
↓
真正执行规则检查
↓
合法数据
```

TypeScript / Node 常见方案：

```text
Zod
Joi
Yup
Valibot
JSON Schema
```

这里使用：

```text
Zod
```

安装：

```bash
pnpm add zod
```

## 3. 创建 Zod Schema

新建：

```text
user/
└─ user.schema.ts
```

```ts
import { z } from 'zod'

export const createUserSchema =
  z.object({
    name: z
      .string()
      .trim()
      .min(2)
      .max(50),

    age: z
      .number()
      .int()
      .min(0)
      .max(150),

    email: z
      .string()
      .trim()
      .email(),
  })
```

这里的 Schema 和 TypeScript `interface` 最大区别：

```text
interface
→ 编译期存在

Zod Schema
→ 运行时存在
```

所以 Zod 可以真正检查客户端数据。

## 4. `parse()`

```ts
const data =
  createUserSchema.parse({
    name: 'Tom',
    age: 18,
    email: 'tom@test.com',
  })
```

合法时直接返回校验后的数据。

非法时：

```ts
createUserSchema.parse({
  name: 'T',
  age: -10,
  email: 'abc',
})
```

会：

```text
throw ZodError
```

## 5. `safeParse()`

`safeParse()` 不直接抛异常：

```ts
const result =
  createUserSchema.safeParse(
    req.body,
  )
```

成功：

```ts
{
  success: true,
  data: ...
}
```

失败：

```ts
{
  success: false,
  error: ...
}
```

使用：

```ts
const result =
  createUserSchema.safeParse(
    req.body,
  )

if (!result.success) {
  res.status(400).json({
    code: 'VALIDATION_ERROR',
    message:
      'Invalid request body',
  })

  return
}

const data = result.data
```

一定要区分：

```text
req.body
= 未校验、不可信数据

result.data
= 已校验数据
```

## 6. Zod 同时生成 TypeScript 类型

如果再单独维护：

```ts
interface CreateUserDTO {}
```

和：

```ts
createUserSchema
```

会出现重复定义。

可以直接：

```ts
export type CreateUserDTO =
  z.infer<
    typeof createUserSchema
  >
```

完整：

```ts
import { z } from 'zod'

export const createUserSchema =
  z.object({
    name: z.string(),
    age: z.number(),
    email: z.string().email(),
  })

export type CreateUserDTO =
  z.infer<
    typeof createUserSchema
  >
```

这样：

```text
Schema
↓
Runtime Validation

同时

Schema
↓
TypeScript Type
```

避免：

```text
Schema 改了
DTO 忘记同步
```

## 7. 为什么 Validation 应该抽成 Middleware

如果每个 Controller 都：

```ts
safeParse()

if (!success) {
  ...
}
```

很快会重复。

所以可以新建：

```text
common/
└─ middleware/
   └─ validate.ts
```

```ts
import type {
  RequestHandler,
} from 'express'

import type {
  ZodType,
} from 'zod'

import {
  AppError,
} from '../errors/app-error.js'

interface ValidationSchemas {
  body?: ZodType
  params?: ZodType
  query?: ZodType
}

export function validate(
  schemas: ValidationSchemas,
): RequestHandler {
  return (
    req,
    res,
    next,
  ) => {
    if (schemas.body) {
      const result =
        schemas.body.safeParse(
          req.body,
        )

      if (!result.success) {
        next(
          new AppError(
            400,
            'VALIDATION_ERROR',
            'Invalid request body',
          ),
        )

        return
      }

      req.body =
        result.data
    }

    if (schemas.params) {
      const result =
        schemas.params.safeParse(
          req.params,
        )

      if (!result.success) {
        next(
          new AppError(
            400,
            'VALIDATION_ERROR',
            'Invalid path parameters',
          ),
        )

        return
      }
    }

    if (schemas.query) {
      const result =
        schemas.query.safeParse(
          req.query,
        )

      if (!result.success) {
        next(
          new AppError(
            400,
            'VALIDATION_ERROR',
            'Invalid query parameters',
          ),
        )

        return
      }
    }

    next()
  }
}
```

## 8. Router 中使用 Validation

创建用户：

```ts
userRouter.post(
  '/',
  validate({
    body:
      createUserSchema,
  }),
  createUser,
)
```

执行链：

```text
POST /users
↓
validate()
↓
Zod
↓
失败
→ AppError
→ Global Error Middleware
→ 400

成功
↓
Controller
```

这样 Controller 就不再负责输入格式校验。

## 9. Params Validation

请求：

```http
GET /users/abc
```

如果直接：

```ts
Number(req.params.id)
```

结果：

```ts
NaN
```

可以：

```ts
export const userIdParamsSchema =
  z.object({
    id: z.coerce
      .number()
      .int()
      .positive(),
  })
```

这里：

```ts
z.coerce.number()
```

会尝试：

```text
'123'
↓
123
```

然后继续校验：

```text
整数
正数
```

## 10. Query Validation

请求：

```http
GET /users?page=2&pageSize=20
```

Query 参数来自 URL，所以本质是字符串。

可以：

```ts
export const getUsersQuerySchema =
  z.object({
    page: z.coerce
      .number()
      .int()
      .min(1)
      .default(1),

    pageSize: z.coerce
      .number()
      .int()
      .min(1)
      .max(100)
      .default(20),
  })
```

这样：

```text
?page=2
```

可以得到：

```ts
{
  page: 2,
  pageSize: 20,
}
```

## 11. Validation 与 Business Validation

这两个必须分开。

例如：

```text
email 是不是合法邮箱
→ Zod / Validation
```

而：

```text
email 是否已经注册
→ Service / Business Rule
```

再比如：

```text
age 是不是数字
→ Validation
```

而：

```text
当前用户有没有权限修改这个用户
→ Service
```

所以：

```text
Schema
负责输入是否合法

Service
负责业务是否合法
```

## 12. `.strict()`

可以：

```ts
export const createUserSchema =
  z.object({
    name: z.string(),
    age: z.number(),
    email: z.string().email(),
  })
  .strict()
```

如果客户端发送：

```json
{
  "name": "Tom",
  "age": 18,
  "email": "tom@test.com",
  "admin": true
}
```

会校验失败。

这可以防止客户端偷偷注入未声明字段。

## 13. Update Schema

PATCH 一般允许只传部分字段。

可以：

```ts
export const updateUserSchema =
  createUserSchema
    .partial()
```

这样所有字段都会变成可选。

但：

```json
{}
```

通常没有意义。

可以：

```ts
export const updateUserSchema =
  createUserSchema
    .partial()
    .refine(
      data =>
        Object.keys(data)
          .length > 0,
      {
        message:
          'At least one field is required',
      },
    )
```

## 15. `process.env` 的类型

即使：

```env
PORT=3000
```

读取：

```ts
process.env.PORT
```

仍然是：

```ts
string | undefined
```

因为环境变量本质上都是字符串。

可以：

```ts
const port =
  Number(
    process.env.PORT ??
    3000,
  )
```

但更推荐：

> 环境变量也使用 Zod 校验。

## 16. 用 Zod 校验环境变量

新建：

```text
config/
└─ env.ts
```

```ts
import 'dotenv/config'

import { z } from 'zod'

const envSchema =
  z.object({
    NODE_ENV: z
      .enum([
        'development',
        'test',
        'production',
      ])
      .default(
        'development',
      ),

    PORT: z.coerce
      .number()
      .int()
      .positive()
      .default(3000),

    DB_HOST:
      z.string().min(1),

    DB_PORT: z.coerce
      .number()
      .int()
      .positive()
      .default(3306),

    DB_USER:
      z.string().min(1),

    DB_PASSWORD:
      z.string(),

    DB_NAME:
      z.string().min(1),
  })

export const env =
  envSchema.parse(
    process.env,
  )
```

以后：

```ts
import {
  env,
} from './config/env.js'

app.listen(env.PORT)
```

这时候：

```ts
env.PORT
```

已经是：

```ts
number
```

而不是：

```ts
string | undefined
```

## 17. Fail Fast

如果：

```text
DB_HOST
```

没有配置，

项目启动时：

```ts
envSchema.parse(
  process.env,
)
```

就会直接报错。

这不是坏事。

因为：

> 配置错误应该在项目启动时尽早暴露，而不是等请求进来以后才发现。

这种思想叫：

```text
Fail Fast
```


而：

```text

```

可以提交。

例如：

