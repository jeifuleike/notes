# 第 05 节　创建项目时，怎样保证负责人也一起写入？

假设小林创建了一个叫“读书会”的项目。项目列表里能看到它，点进去却提示“你不是项目成员”。如果项目列表读取 `projects`，成员检查读取 `project_members`，两处结果就可能同时出现：程序保存了项目，写入成员时却失败了。

创建项目这一次操作要兑现一个业务约定：**创建成功时，既能查到项目，也能查到创建人在该项目里的 `owner` 成员记录。** 本节沿用第 04 节的 Nest、mysql2 和连接池，把这两次写入放进同一个 MySQL 事务。

## 为什么两行代码都写了 await，还是会留下半个项目？

`await` 能保证先拿到新项目的 ID，再用这个 ID 插入成员。它控制的是代码的执行顺序。MySQL 默认开启自动提交，如果直接调用两次 `pool.execute(...)`，第一条成功时项目就已经提交。即使第二条抛错，Nest 返回了错误响应，第一条记录依然存在。

事务让这两次写入共用一个提交决定。第一条 `INSERT` 执行后，程序就能从结果的 `insertId` 拿到项目 ID，立即交给第二条使用。此时项目还可以撤销。两条都成功才调用 `commit()`；成员写入失败则调用 `rollback()`，撤销本次事务已经写入的项目。

## 为什么 Service 要把连接传给两个 Repository？

第 04 节的一次普通查询可以直接用池。到了这里，要区分**连接池**和**从池里借出的一条连接**。MySQL 把当前事务记在连接对应的会话上。在连接 A 上开启事务，只能提交或回滚 A 上的写入。两个 Repository 即使注入了同一个池，分别调用 `pool.execute()` 时也没有指定使用 A。

| 层 | 创建项目时负责什么 |
| --- | --- |
| Controller | 接收已校验的项目名称，调用 Service。本节练习用已有测试用户的 ID 模拟当前用户。 |
| Service | 知道“创建项目”包含两次写入。它从池里借一条连接，把它传给两个 Repository，并决定何时提交或回滚。 |
| Repository | 知道表名、字段和 SQL。每个方法都在调用者传入的连接上写入，让 Service 决定整笔业务的结果。 |

下面是 Service 的核心方法。`this.pool` 是第 04 节的共享池，`this.projects` 和 `this.members` 是通过构造函数注入的两个 Repository。两次调用的第一个参数都是同一个 `conn`。

```ts
async createProject(name: string, ownerId: number): Promise<number> {
  const conn = await this.pool.getConnection();
  try {
    await conn.beginTransaction();
    const projectId = await this.projects.insert(conn, name, ownerId);
    await this.members.addOwner(conn, projectId, ownerId);
    await conn.commit();
    return projectId;
  } catch (error) {
    try {
      await conn.rollback();
    } catch {
      // 回滚也失败时，丢弃这条状态不明的连接。
      conn.destroy();
      throw error;
    }
    throw error;
  } finally {
    conn.release();
  }
}
```

`commit()` 决定数据是否提交，`release()` 让池里的连接可以再次被借用，这是两个独立动作。正常提交和成功回滚后都要归还连接，所以把归还放进 `finally`。如果回滚本身也失败，mysql2 的 `destroy()` 会将这条连接移出池，随后的 `release()` 不会把它放回空闲队列。

## Repository 实际写了什么？

下面分别是两个 Repository 的方法片段。`PoolConnection` 和 `ResultSetHeader` 都是从 `mysql2/promise` 导入的类型。示例沿用学习工程的字段，项目行保存负责人 ID，成员行保存该用户在该项目中的角色。[项目表迁移](../../../node/node-backend-study/labs/15-transactions/src/migrations/015-create-projects.sql) · [成员表迁移](../../../node/node-backend-study/labs/15-transactions/src/migrations/016-create-project-members.sql)

```ts
// ProjectsRepository
async insert(conn: PoolConnection, name: string, ownerId: number) {
  const [result] = await conn.execute<ResultSetHeader>(
    'INSERT INTO projects (name, owner_id, created_at) VALUES (?, ?, NOW())',
    [name, ownerId],
  );
  return result.insertId;
}

// ProjectMembersRepository
async addOwner(conn: PoolConnection, projectId: number, ownerId: number) {
  await conn.execute(
    `INSERT INTO project_members (project_id, user_id, role, joined_at)
     VALUES (?, ?, 'owner', NOW())`,
    [projectId, ownerId],
  );
}
```

读这两个方法时可以追踪两个值。**项目 ID** 来自第一条写入，作为第二条写入的 `project_id`。**连接**来自 Service，贯穿两次写入。前者保证成员属于正确的项目，后者保证写入可以一起回滚。

## 怎样亲眼看到回滚？

配套的 [Nest 事务案例](../../../node/node-backend-study/labs/nest-05-transactions/README.md) 可以直接运行。[集成测试](../../../node/node-backend-study/labs/nest-05-transactions/src/projects/transactions.test.ts) 用重复的成员主键触发回滚；下面的手动练习用外键失败验证同一件事。

在本地练习库中选择一个已经存在的测试用户。给下面两次调用取不同的、此前没用过的项目名。每次请求结束后，从另一个数据库连接检查结果。

| 尝试 | 怎么做 | 应该看到什么 |
| --- | --- | --- |
| 正常创建 | 以测试用户创建“读书会-成功-01” | 返回项目 ID。按该 ID 查项目和成员，各有一行；成员的 `user_id` 等于项目的 `owner_id`，角色为 `owner`。 |
| 让第二步失败 | 在本地测试里，给 `addOwner` 的第三个参数临时换成一个确认不存在的用户 ID，再创建“读书会-回滚-01”。第一步仍使用原来的有效用户。 | 项目插入成功后，成员插入因用户外键失败。请求报错，按这次的项目名查 `projects` 得到零行。练习后恢复参数。 |

失败场景要**单独查项目表**。如果只用内连接查询项目和成员，即便数据库里残留了一个没有成员的项目，查询也会返回零行，容易误以为回滚成功。

```sql
SELECT id, owner_id FROM projects WHERE name = '读书会-回滚-01';
```

回头再看开头的问题：如果 `ProjectsRepository.insert` 里有人把 `conn.execute` 改成了 `this.pool.execute`，为什么正常创建看起来仍然成功，回滚练习却能发现问题？能用“哪条连接提交了项目”回答，就抓住了这一节的重点。

这段事务只覆盖同一个 MySQL 会话里的两次 InnoDB 写入。如果以后还要刷新 Redis 缓存，MySQL 回滚无法撤销已执行的 Redis 写入。以后学 Spring Boot 的 `@Transactional`，可以继续追问同一个问题：框架怎样让两个数据访问方法加入同一笔事务？
