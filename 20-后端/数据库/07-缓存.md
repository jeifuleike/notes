# 缓存

本篇聚焦应用缓存：命中、回源、结果更新、故障与并发一致性。先读 Redis 篇；缓存可以采用 Redis，也可以采用其他实现。

## 1. 缓存是什么：命中、未命中与回源

缓存是在更方便快速访问的位置，保存一份可以复用的数据。进程内 Map、浏览器缓存和 Redis 缓存都是不同形式。

| 术语 | 含义 |
| --- | --- |
| 命中 | 缓存中有当前请求可用的数据 |
| 未命中 | 没有可用的缓存结果 |
| 回源 | 向 MySQL 等正式来源重新获取数据 |
| 缓存重建 | 将正式来源的结果重新放入缓存 |

常用的 Cache Aside（旁路缓存）由应用管理：

```text
读取请求
  ↓
读 Redis
  ├─ 命中 → 校验、解析后返回
  └─ 未命中 → 查 MySQL
                 ├─ 不存在 → 返回 404
                 └─ 存在 → 写 Redis 并设置 TTL → 返回
```

Redis 不会因为和 MySQL 同时运行，就自动知道 MySQL 更新了什么。缓存读写和失效需要应用设计。

不存在用户时是否缓存“空结果”属于另外的策略。第一阶段可以先不缓存不存在的数据，后面再学习短 TTL 的空值缓存。

## 2. MySQL 与 Redis 如何分工

MySQL 用关系表组织数据，适合关联查询、约束和事务。Redis 提供按 key 操作数据结构的能力。

| 维度    | MySQL / InnoDB | Redis 常见用法       |
| ----- | -------------- | ---------------- |
| 数据组织  | 表、行、列及关系       | key 对应某种数据结构     |
| 访问方式  | SQL、索引、JOIN    | GET、SET 等命令      |
| 常见角色  | 业务事实来源         | 缓存、计数、临时状态       |
| 持久化   | 事务日志和数据文件等     | 可配置 RDB、AOF 等    |
| 关系约束  | 主键、唯一约束、外键等    | 通常由应用设计关系与校验     |
| 适合的问题 | 订单、用户、项目及关联    | 热点用户副本、排行榜、限时验证码 |

这张表描述学习项目中的分工，不代表 Redis 只能存临时数据，也不代表 MySQL 每次查询都直接读磁盘。

用户查询示例：

```text
MySQL：保存用户的正式信息
Redis：保存经常被读取的信息副本

缓存没了 → 从 MySQL 重新获取
MySQL 数据没了 → 不能靠“缓存应该还在”保证恢复
```

选择缓存前先问：它是否访问频繁、查询成本是否值得优化、是否允许短暂旧值？并非所有接口都需要 Redis。

### MySQL 已有 Buffer Pool，为什么还可能使用 Redis

InnoDB 的 Buffer Pool 缓存数据页和索引页。命中后可以省掉相应磁盘读取，但 MySQL 通常仍需处理 SQL、访问索引、判断记录可见性，并完成查询要求的关联、过滤、统计等工作。[Buffer Pool 官方说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-buffer-pool.html)

应用放入 Redis 的往往是已经查询或计算好的结果，例如用户公开资料、项目首页汇总。命中后可以省去相应的 MySQL 查询及部分业务计算。

```text
Buffer Pool 命中：SQL → MySQL 处理 → 访问内存中的页 → 构造结果
Redis 结果命中：GET 对应 key → 获得已准备的结果 → 应用解析并返回
```

| 对比 | Buffer Pool | Redis 应用结果缓存 |
| --- | --- | --- |
| 缓存对象 | 页中的数据与索引记录 | 应用选择的对象、统计或接口结果 |
| 管理者 | MySQL 引擎 | 应用负责 key、TTL 与失效策略 |
| 主要减少的工作 | 磁盘读取 | 对应数据库查询及重复计算 |
| 数据更新管理 | 引擎结合事务与页管理 | 应用需要处理旧值与并发失效 |

两者都可能使用内存；不能用“一个读磁盘，一个读内存”解释全部差异。Redis 仍有网络、序列化和运维成本，简单而高效的 MySQL 查询不一定值得再加缓存。

## 3. 修改 MySQL 后，为什么通常删除缓存

```text
初始：MySQL name=Tom，Redis name=Tom
修改：MySQL name=Jack
问题：Redis 仍然是 Tom
```

基础处理方式：先更新 MySQL，成功后删除缓存。

```text
修改请求 → 更新 MySQL → 删除对应缓存 → 返回
下一次查询 → 未命中 → 从 MySQL 读取 Jack → 重建缓存
```

若先删除缓存，再更新 MySQL，中间另一个读取请求可能把尚未修改的旧值重新填进缓存。

但是，“先更新后删除”也不能保证并发强一致：

```text
A：缓存未命中，读到 MySQL 旧值 Tom，尚未写缓存
B：更新 MySQL 为 Jack，删除缓存
A：把先前读到的 Tom 写进缓存
```

这解释了为什么事务、并发和锁基础需要先学。TTL 可以限制这个旧缓存的生存期，但不能消除旧值窗口；持续并发写入时，也不能把 TTL 说成对所有时刻一致性的保证。

更严格的需求可能涉及版本校验、失效重试、消息或变更订阅，甚至直接从权威来源读取。MySQL 的一个普通事务无法同时回滚已经执行的 Redis 操作。

## 4. Redis 出错时，业务应该怎么办

需要先区分它在当前业务中的角色。

| 用途 | 失败时的设计方向 |
| --- | --- |
| 可重建的用户查询缓存 | 可以考虑绕过缓存查 MySQL |
| 正在控制登录频率的计数 | 绕过可能削弱防护，要明确策略 |
| 唯一保存的会话记录 | 不可简单假装身份验证成功 |

缓存读取失败、缓存写入失败、MySQL 查询失败是三个不同问题。不要用一个巨大 try/catch 把数据库异常吞掉，再当作缓存未命中。

修改 MySQL 成功但删除 Redis 失败，也不能告诉自己“整个修改已经回滚”。需要承认写入已生效，记录失效故障，并用 TTL、重试等措施控制旧值。

降级还有容量代价：所有请求突然回源可能压垮 MySQL。因此还要考虑超时、限流和依赖恢复策略。第一阶段先理解故障边界，不必一次实现所有机制。

## 5. 缓存穿透、击穿、雪崩

| 问题 | 发生了什么 | 常见处理方向 |
| --- | --- | --- |
| 穿透 | 反复请求不存在的数据，每次都回源 | 输入校验、短 TTL 空值缓存、布隆过滤器 |
| 击穿 | 一个热点 key 失效，大量请求同时重建 | 合并同一 key 请求、受控重建、提前刷新 |
| 雪崩 | 大批 key 同时失效，或缓存服务不可用 | TTL 加随机偏移、限流、降级和容量预案 |

空值缓存需要在后续创建数据时考虑失效。布隆过滤器可能误报“存在”，所以仍需查询正式数据来源。TTL 加随机偏移缓解批量到期，不能解决 Redis 整体宕机。

第一阶段先通过日志观察命中与回源，学会解释这些问题，再逐个实验，不必先堆复杂方案。

## 6. 动手自检

通过数据库日志观察首次回源、再次命中、过期后回源；再验证改名后的失效、坏 JSON、ID 错位与 Redis 断线。能解释旧值窗口与数据库错误的边界后，再深入缓存穿透、击穿和雪崩。

## 7. 企业级 Redis 缓存架构：从参数到故障边界

前六节回答“缓存如何命中、回源、失效、出错”。这一节换一个视角：如果这套缓存要承载真实流量，架构、参数和运维边界如何确定。

“企业级”不等于参数越多越好，也不等于一定要上 Cluster。它更接近四个可验证的目标：

| 目标 | 要回答的问题 | 需要留下的东西 |
| --- | --- | --- |
| 故障可预期 | Redis 变慢、宕机、内存满时，业务怎么退 | 超时、熔断、降级、容量预案 |
| 容量可计算 | 多少 key、多大 value、内存水位多少 | 容量估算、`maxmemory`、淘汰策略 |
| 一致性可解释 | 旧值最长活多久，哪些读必须强一致 | TTL、失效通道、版本号 |
| 变更可运维 | 参数怎么改、怎么回滚、怎么演练 | 配置版本化、指标、告警、runbook |

一个常见结论：多数业务缓存用“应用内 Cache Aside + Redis 主从或 Sentinel（也可以是托管实例）+ 强制 TTL + 故障降级 + 指标告警”已经足够；Cluster 只在单实例内存或吞吐确实不够时引入。下面给出的是可讨论的起点配置，不是可以不经压测直接复制的标准答案。Redis 版本、云厂商限制和合规要求都会改变结论。

### 7.1 缓存不止 Redis 一层

真实请求通常经过不止一层缓存：

```text
客户端 / 浏览器
  ↓
接入层（限流、鉴权、WAF）
  ↓
应用实例 A / B / C
  ├─ L1 进程内缓存（可选，容量小、延迟最低）
  ├─ L2 Redis 共享缓存
  └─ 降级、熔断、并发保护
  ↓
MySQL（事实来源）

旁路设施：
  失效通道：更新后删除 / 延迟双删 / binlog-CDC / 消息
  观测：指标、日志、追踪、慢查询
```

每一层的职责和失败方式不同：

| 层 | 主要作用 | 失败时的典型表现 | 不能解决什么 |
| --- | --- | --- | --- |
| L1 进程内缓存 | 挡住极热点读，省网络往返 | 每个实例各有一份旧值，失效困难 | 跨实例一致性、容量共享 |
| L2 Redis | 共享缓存、保护 MySQL | 网络超时、热 key、内存淘汰、故障切换 | 不自动知道 MySQL 变了 |
| MySQL | 保存正式数据、约束和事务 | 连接耗尽、慢查询、主从延迟 | 不能靠缓存保证恢复 |
| 失效通道 | 让旧副本尽快失效 | 消息丢失、重复、乱序、延迟 | 不能替代 TTL 兜底 |

因此，企业架构里通常不会只问“Redis 配多大”，而会同时问：

1. Redis 不可用时，这个接口是读 MySQL、返回降级内容，还是直接失败？
2. 旧值最多允许存在多久？由 TTL、主动失效还是版本号保证？
3. 缓存故障会不会把 MySQL 一起打垮？
4. 出问题时，值班人员能不能从指标和日志判断是哪一层坏了？

### 7.2 部署形态怎么选

Redis 的常见部署形态可以先用一张表区分（复制、Sentinel 和 Cluster 的机制细节见 [[20-后端/数据库/06-Redis]] 第 11 节，这里只讨论选型）：

| 形态 | 数据布局 | 故障转移 | 扩容方式 | 主要限制 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| 单机 | 一台节点保存全部数据 | 无 | 换更大的机器 | 节点故障即不可用 | 本地开发、小流量、可接受短暂中断 |
| 主从 + Sentinel | 主节点和副本保存全量数据 | Sentinel 自动选主 | 纵向扩容为主 | 单分片容量上限；异步复制可能丢最近写入 | 数据量能放进单机、需要自动故障转移 |
| Redis Cluster | 多个主节点分片，每片可带副本 | 分片内自动故障转移 | 增加分片、迁移槽位 | 跨槽多 key 操作受限；热 key 仍集中；运维复杂 | 单机内存或吞吐确实不够 |
| 云托管 Redis | 由服务商封装主从、Sentinel 或集群 | 通常自动 | 按产品规格扩容 | 连接数、代理模式、参数可调范围受限制 | 希望减少自建运维、接受托管约束 |

选择时先回答三个问题：

1. 工作集能否放进单机内存的 60%～70%，并留出故障切换和峰值余量？
2. 峰值 QPS 是否明显低于单实例的安全水位？
3. 能否接受故障切换期间秒级不可用，以及异步复制下少量已确认写入丢失？

三个答案都是“能”，优先主从 + Sentinel 或托管主从；有一个是“不能”，再评估 Cluster 或托管分片。为“看起来更企业”而上 Cluster，往往会先得到跨槽限制、迁移复杂度和更高的故障面。

一个常见的三可用区示意：

```text
可用区 A：Redis Master + Sentinel 1
可用区 B：Redis Replica + Sentinel 2
可用区 C：Redis Replica + Sentinel 3
```

Sentinel 通常至少三个、部署在不同故障域，法定票数设为 2。应用通过 Sentinel 发现当前主节点，而不是把主节点 IP 写死；DNS 切换也不能替代 Sentinel 客户端对拓扑变化的处理。

副本读要谨慎：副本可能落后于主节点，刚写完立刻读副本可能读到旧值。只有业务明确允许旧读时，才让读请求分流到副本；`node-redis` 的 Sentinel 客户端可以用 `replicaPoolSize` 做只读分流，但这不是“读扩展免费”。

### 7.3 服务端配置：纯缓存节点的起点

下面是一份“只做缓存”的 Redis 节点配置起点。它假设 Redis 7.2+/8.x、Linux、容器外有独立监控；如果使用托管服务，很多参数由控制台管理，不需要也不允许直接改配置文件。

```conf
# ---------- 网络与进程 ----------
bind 10.0.1.11 -::1
protected-mode yes
port 6379
daemonize no
supervised no
loglevel notice
logfile ""

# ---------- 认证与权限 ----------
# 推荐：aclfile /etc/redis/users.acl（需先准备文件）
# 没有 ACL 文件时，至少使用从密钥管理注入的 requirepass；
# 不要把密码写进仓库、镜像或日志。
# requirepass <REDIS_PASSWORD>

# 跨网络或跨可用区建议开启 TLS；开启后可以只暴露 TLS 端口。
# tls-port 6380
# port 0
# tls-cert-file /etc/redis/tls/redis.crt
# tls-key-file /etc/redis/tls/redis.key
# tls-ca-cert-file /etc/redis/tls/ca.crt
# tls-auth-clients yes

# ---------- 连接 ----------
tcp-backlog 511
timeout 300
tcp-keepalive 60
maxclients 10000

# ---------- 内存 ----------
maxmemory 12gb
maxmemory-policy allkeys-lfu
maxmemory-samples 10
lfu-log-factor 10
lfu-decay-time 1
lazyfree-lazy-eviction yes
lazyfree-lazy-expire yes
lazyfree-lazy-server-del yes
lazyfree-lazy-user-del yes
lazyfree-lazy-user-flush yes

# ---------- 持久化：纯缓存 ----------
save ""
appendonly no

# ---------- 慢查询与延迟 ----------
slowlog-log-slower-than 10000
slowlog-max-len 256
latency-monitor-threshold 100

# ---------- 客户端输出缓冲 ----------
client-output-buffer-limit normal 256mb 64mb 60
client-output-buffer-limit replica 512mb 128mb 60
client-output-buffer-limit pubsub 32mb 8mb 60

# ---------- 事件循环与 I/O ----------
hz 10
dynamic-hz yes
io-threads 4
io-threads-do-reads yes

# ---------- 复制 ----------
replica-read-only yes
replica-serve-stale-data yes
repl-backlog-size 256mb
replica-priority 100
min-replicas-to-write 0
min-replicas-max-lag 10

# ---------- 小对象编码（按数据规模调整） ----------
hash-max-listpack-entries 128
hash-max-listpack-value 64
zset-max-listpack-entries 128
zset-max-listpack-value 64
set-max-intset-entries 512
list-max-listpack-size -2

# ---------- 危险能力 ----------
enable-protected-configs no
enable-debug-command no
enable-module-command no

# ---------- 仅 Cluster 节点需要 ----------
# cluster-enabled yes
# cluster-config-file nodes.conf
# cluster-node-timeout 5000
# cluster-require-full-coverage no
# cluster-migration-barrier 1
```

这些参数不是孤立的“最佳值”，每一组都对应一个故障模型：

| 参数 | 起点 | 为什么这样设 | 什么时候调整 |
| --- | --- | --- | --- |
| `maxmemory` | 物理内存或容器限额的 60%～70% | Redis 的 `used_memory` 不等于进程 RSS；复制缓冲、fork COW、内存碎片、连接缓冲都要留空间 | 压测后按峰值 RSS 和碎片率调整 |
| `maxmemory-policy` | 纯缓存用 `allkeys-lfu` | 纯缓存实例里所有 key 都可淘汰；LFU 更偏好长期热点 | 混放非缓存 key 时不要用 `allkeys-*`，或直接拆实例 |
| `lazyfree-*` | 开启 | 删除大 key、淘汰大量 key 时减少主线程阻塞 | 极低延迟场景观察 `latency` 后再细化 |
| `save ""`、`appendonly no` | 纯缓存关闭 | 缓存允许冷启动重建；持久化会增加 fork、磁盘和恢复成本 | 存会话、队列、锁、计数器时不能照抄，见 7.4 |
| `timeout` | 300 秒 | 回收空闲连接，避免连接数虚高 | 长连接池空闲时间更长时设 0 或更大 |
| `maxclients` | 10000 | 防止连接耗尽文件描述符 | 按 `ulimit -n`、实例数和客户端连接数计算 |
| `io-threads` | 4（至少 4 核时） | TLS、较大 value 场景下分担网络读写 | 核数少时不要超过可用核数；它不是热 key 的解药 |
| `slowlog-log-slower-than` | 10000 微秒 | 10ms 以上命令先记录下来 | 本地排查可临时降低；生产不要长期设 0 |
| `client-output-buffer-limit` | 按最大回复量设 | 防止慢消费者或大结果把内存撑爆 | 大 `MGET`、大 key、Pub/Sub 场景要单独评估 |
| `repl-backlog-size` | 256mb | 副本短暂断线后可从 backlog 增量同步，避免全量重同步风暴 | 按“写入速率 × 允许断线秒数”估算 |
| `cluster-require-full-coverage` | 缓存场景设 `no` | 部分槽位不可用时，仍让可用槽位服务读请求 | 对“全有或全无”有要求的业务设 `yes` |

几个容易忽略的边界：

- `maxmemory` 不是容器内存上限。把两者设成同一个值，Redis 在 fork、复制缓冲或碎片上升时可能被 OOM Killer 杀掉。容器限额应明显大于 `maxmemory`。
- `allkeys-lfu` 只适合“这个实例里全是可淘汰缓存”。如果同一实例还放会话、队列或锁，淘汰可能把不可丢的数据赶走；正确做法通常是拆实例，而不是继续调策略。
- `save ""` 和 `appendonly no` 意味着 Redis 重启后是冷缓存。冷启动时大量请求同时回源，可能比 Redis 宕机本身更危险；需要预热、限流和 MySQL 并发保护。
- `io-threads` 只分担网络读写，不改变单 key 命令仍在主线程执行的模型。一个超大 value 或超热 key 仍然会拖慢该分片。
- `CONFIG SET` 可以运行时改一部分参数，但不等于变更管理。生产应把配置文件纳入版本控制，变更走评审、灰度和回滚，并定期用 `CONFIG GET` 检查漂移。

### 7.4 如果实例里不只有缓存

“Redis 缓存架构”经常被混入其他用途。它们的失败代价不同，不能共用一套淘汰和持久化策略：

| 用途 | 能否丢数据 | 推荐策略 | 关键风险 |
| --- | --- | --- | --- |
| 页面、用户资料、列表缓存 | 可以重建 | `allkeys-lfu`、TTL、关闭持久化 | 冷启动回源风暴 |
| 登录会话 | 丢失会导致重新登录 | 独立实例、AOF `everysec`、副本、容量告警 | 淘汰或故障切换导致集体掉线 |
| 限流、验证码计数 | 短窗口内敏感 | 独立实例、TTL、明确的失败策略 | Redis 故障时直接放行会削弱防护 |
| 分布式锁 | 丢失可能造成并发冲突 | 独立实例、fencing token、租约和续期 | 主从切换可能双持有，不能替代数据库约束 |
| 队列、Streams | 通常不可丢 | 持久化、副本、消费者组、监控积压 | 与缓存混放会被淘汰或 flush 误伤 |

结论不是“这些都不能用 Redis”，而是：**不要把不同数据可靠性要求的工作负载塞进同一个实例，然后指望一个 `maxmemory-policy` 同时满足它们。** 至少要做逻辑隔离和容量配额，条件允许时做物理隔离。

### 7.5 客户端配置

以本项目使用的 `node-redis` 6 为例，一个常驻服务通常只创建一个客户端，并在进程内复用它。下面是一份偏保守的起点：

```ts
import { createClient } from 'redis'
import { env } from '../config/env.js'

export const redis = createClient({
  url: env.REDIS_URL,
  username: env.REDIS_USERNAME,
  password: env.REDIS_PASSWORD,
  socket: {
    connectTimeout: 1000,
    keepAlive: true,
    noDelay: true,
    reconnectStrategy: retries => {
      if (retries > 10) return new Error('redis reconnect exhausted')
      return Math.min(100 * 2 ** retries, 3000) + Math.floor(Math.random() * 200)
    },
  },
  disableOfflineQueue: true,
}).withCommandOptions({ timeout: 200 })

redis.on('error', () => console.error('[redis] connection error'))
```

几个配置点的含义：

| 配置 | 作用 | 取舍 |
| --- | --- | --- |
| `connectTimeout` | 建立 TCP/TLS 连接的超时 | 太长会拖住启动和故障恢复；太短会在网络抖动时误判 |
| `socketTimeout` | 连接空闲多久后关闭 | 与“单条命令超时”不是一回事；不要用它替代命令预算 |
| `reconnectStrategy` | 断线后的重连节奏 | 指数退避加随机抖动，避免所有实例同时重连；达到上限后应告警并让进程退出或重建 |
| `disableOfflineQueue` | 断线时不再排队命令 | 快速失败，避免恢复瞬间积压大量请求；代价是短暂抖动会变成错误，需要降级 |
| `withCommandOptions({ timeout })` | 单条命令超时（`node-redis` 6） | 超时只让调用方失败，命令可能仍在服务端执行；不能盲目重试非幂等命令 |
| 单个客户端复用 | 普通命令多路复用 | 阻塞命令、Pub/Sub、`MONITOR` 需要独立连接，不能和普通请求混用 |

如果使用 Sentinel，客户端应让 Sentinel 发现主节点，而不是自己写死地址。`node-redis` 6 的形态大致如下：

```ts
import { createSentinel } from 'redis'

export const redis = createSentinel({
  name: 'app-cache',
  sentinelRootNodes: [
    { host: '10.0.1.21', port: 26379 },
    { host: '10.0.1.22', port: 26379 },
    { host: '10.0.1.23', port: 26379 },
  ],
  sentinelClientOptions: { password: process.env.SENTINEL_PASSWORD },
  nodeClientOptions: {
    username: process.env.REDIS_USERNAME,
    password: process.env.REDIS_PASSWORD,
    socket: { connectTimeout: 1000, keepAlive: true },
    disableOfflineQueue: true,
  },
  replicaPoolSize: 0,
  scanInterval: 10_000,
}).withCommandOptions({ timeout: 200 })
```

`replicaPoolSize: 0` 表示先不读副本，避免复制延迟造成“刚写完读不到”。只有业务允许旧读时，才把它调大并接受副本延迟。

Cluster 客户端需要至少三个根节点做拓扑发现，且凭据、TLS 等要放在 `defaults` 里，不能只写在 `rootNodes` 上：

```ts
import { createCluster } from 'redis'

export const redis = createCluster({
  rootNodes: [
    { url: 'rediss://10.0.1.31:6379' },
    { url: 'rediss://10.0.1.32:6379' },
    { url: 'rediss://10.0.1.33:6379' },
  ],
  defaults: {
    username: process.env.REDIS_USERNAME,
    password: process.env.REDIS_PASSWORD,
    socket: { connectTimeout: 1000, keepAlive: true },
    disableOfflineQueue: true,
  },
}).withCommandOptions({ timeout: 200 })
```

客户端还有三个容易踩的边界：

1. **超时不是取消。** 命令超时后，服务端可能仍在执行。`GET`、`SET`、`DEL` 通常可以安全重试；`INCR`、扣减库存、加锁这类非幂等操作不能因为超时就盲目重试。
2. **连接数要算总账。** 每个应用实例、每个 Cluster 分片、每种独立连接都会占用 `maxclients`。应用实例数乘以每实例连接数，再留出故障切换和运维连接的余量。
3. **不要把连接池当成数据库连接池。** `node-redis` 的普通命令默认在一条连接上多路复用；为每条请求创建客户端会制造连接风暴。需要隔离的是阻塞命令、Pub/Sub 和不同用途的连接，而不是无脑加池。

### 7.6 Key、Value 与 TTL 规范

企业缓存的第一道“架构”其实在 key 设计里。推荐把 key 当作接口契约，而不是随手拼字符串：

```text
{应用}:{环境}:{领域}:{实体}:{标识}:{字段}
shop:prod:user:1001:profile
shop:prod:user:1001:permissions
```

如果使用 Cluster 且需要把同一实体的多个 key 放在同一槽位，可以用 Hash Tag：

```text
shop:prod:{user:1001}:profile
shop:prod:{user:1001}:permissions
```

Hash Tag 只应服务于确实需要多 key 原子操作或同槽查询的场景。不要给所有 key 套同一个 `{app}`，否则所有数据落到一个槽位，分片失去意义。

Value 建议使用带版本的信封，而不是直接把业务对象 `JSON.stringify`：

```json
{
  "v": 1,
  "kind": "user",
  "cachedAt": 1762732800000,
  "data": { "id": 1001, "name": "Tom", "age": 28, "email": "tom@example.com" }
}
```

这样做的好处：

- 结构变更时可以按 `v` 识别旧数据，未知版本按未命中处理，而不是把旧结构硬解析成新类型。
- 可以明确区分正常值和“负缓存”标记，避免把不存在标记当成用户对象。
- 可以在信封中扩展 `freshUntil`、`hardUntil`、压缩标记等字段，而不改变业务对象。

TTL 的几个原则：

| 原则 | 说明 |
| --- | --- |
| 缓存 key 必须有 TTL | 不用 TTL 的 key 会把内存问题从“容量规划”变成“永久泄漏” |
| TTL 加随机抖动 | 例如基础 60 秒加 0～15 秒，避免大批 key 同一秒到期 |
| 负缓存用更短 TTL | 不存在结果通常 5～30 秒即可，避免长期挡住后来创建的数据 |
| TTL 不是一致性保证 | 它只限制旧值最长存活时间；并发回填仍可能产生旧值窗口 |
| 批量 key 不要同一时刻创建 | 预热、发布、定时任务都可能制造“整点雪崩” |

大 key 也需要提前定阈值。经验上，单个 String 超过几十 KB 就应评估，达到 MB 级通常应拆分或压缩；Hash/List/Set/ZSet 的成员数达到数千就应检查访问方式，避免 `HGETALL`、`LRANGE 0 -1` 这类一次性拉全量。删除大 key 优先用 `UNLINK`，并确认 `lazyfree` 已开启。

### 7.7 一致性：把“旧值最长活多久”写进设计

第 3 节已经说明“先更新 MySQL 再删缓存”仍有并发窗口。企业设计不是追求一句“强一致”，而是按业务选择可接受的收敛方式：

| 业务要求 | 常见策略 | 旧值窗口 | 代价 |
| --- | --- | --- | --- |
| 秒级旧值可接受 | 更新数据库成功后删除缓存；TTL 兜底 | 通常毫秒到秒；删除失败时到 TTL | 实现简单，需监控删除失败 |
| 尽量缩短并发回填 | 延迟双删：更新后删除，短延迟再删一次 | 仍然不是强一致 | 第二次删除可能误删更新后的新值，需版本校验 |
| 多写入源、多实例 | binlog/CDC → 消息队列 → 按 key 失效 | 取决于管道延迟 | 需要幂等、顺序和积压监控 |
| 读己之写 | 写后短时间内读主库；或写回新值并带版本 | 可控但增加主库压力 | 需要请求上下文或用户粘性 |
| 必须强一致 | 该读路径不走缓存，直接读权威来源 | 无缓存旧值 | 放弃缓存收益 |

几个可落地的细节：

1. **先提交数据库，再删除缓存。** 删除失败时不能声称事务回滚；记录指标和日志，依赖 TTL 或补偿任务收敛。
2. **按版本删除，避免误删新值。** 如果缓存值带版本号，删除脚本可以只删除“版本不高于本次更新”的值，降低延迟双删误删新值的概率。
3. **不要把 keyspace notification 或 Pub/Sub 当作可靠失效通道。** 它们是尽力而为的，进程断线、订阅丢失、消息堆积都会漏；可靠失效应走 MQ/CDC，TTL 只做最后兜底。
4. **空值缓存要有创建时失效。** 缓存“不存在”后，新建数据必须删除对应负缓存，否则用户会在一小段时间内继续看到 404。
5. **缓存删除与数据库事务不在一个原子边界里。** Redis 和 MySQL 没有跨系统事务；不要用“删缓存失败就回滚 MySQL”的假象掩盖问题。

一个按版本删除的 Lua 示意（只删除不比预期版本新的值）：

```lua
-- KEYS[1] = 缓存 key
-- ARGV[1] = 本次更新后的版本号
local raw = redis.call('GET', KEYS[1])
if not raw then
  return 0
end
local ok, value = pcall(cjson.decode, raw)
if not ok or type(value) ~= 'table' then
  return redis.call('DEL', KEYS[1])
end
if tonumber(value.v or 0) <= tonumber(ARGV[1]) then
  return redis.call('DEL', KEYS[1])
end
return 0
```

Lua 在主线程执行，脚本要短，不能在里面做全量扫描；Cluster 下所有 key 必须落在同一槽位。这个脚本只是降低误删概率，不把系统变成强一致。

### 7.8 穿透、击穿、雪崩的企业级做法

第 5 节给出了概念，这里补上工程上的组合方式：

| 问题 | 触发条件 | 组合防护 | 代价与边界 |
| --- | --- | --- | --- |
| 穿透 | 大量请求不存在的数据 | 参数校验、短 TTL 负缓存、布隆过滤器、按用户/IP 限流 | 布隆过滤器有误报，仍需回源确认；负缓存要处理创建失效 |
| 击穿 | 单个热点 key 过期，瞬间大量回源 | 进程内 single-flight、受控重建、逻辑过期、分布式锁 | 单机 single-flight 只能合并本进程；分布式锁有租约和故障切换问题 |
| 雪崩 | 大批 key 同时过期，或 Redis 整体不可用 | TTL 抖动、预热、多级缓存、熔断、MySQL 并发上限、排队和降级 | 抖动不解决 Redis 宕机；限流会牺牲部分请求 |
| 热 key | 单个 key 的 QPS 远高于其他 key | L1 缓存、读副本、key 拆分、请求合并 | 读副本可能旧；key 拆分增加聚合复杂度 |
| 大 key | 单 value 或集合过大 | 拆分、压缩、分页读取、`UNLINK` | 压缩消耗 CPU；拆分改变数据模型 |

进程内 single-flight 的最小实现：

```ts
const inflight = new Map<string, Promise<unknown>>()

export function singleFlight<T>(key: string, fn: () => Promise<T>): Promise<T> {
  const existing = inflight.get(key) as Promise<T> | undefined
  if (existing) return existing

  const task = Promise.resolve()
    .then(fn)
    .finally(() => inflight.delete(key))

  inflight.set(key, task)
  return task
}
```

要点：

- 失败也要在 `finally` 清理，否则一次失败会永久复用坏 Promise。
- key 要带租户、实体和查询条件；不同查询不能误合并。
- 它只约束单个进程。多实例部署时，最坏回源次数是“实例数”，不是“请求数”；这通常已经足够，不必为每次读加分布式锁。
- 不要把长时间任务放进 single-flight，否则会占住内存并拖慢等待者。

如果确实需要跨实例协调，分布式锁只能作为“减少重复重建”的手段，不能作为业务正确性的唯一保证：

```ts
import { randomUUID } from 'node:crypto'
import { redis } from './client.js'

const token = randomUUID()
const acquired = await redis.set(lockKey, token, { NX: true, PX: 3000 })
try {
  if (acquired) {
    // 重建缓存；耗时可能超过租约，需要续期或缩小任务粒度
  }
} finally {
  await redis.eval(
    `if redis.call('GET', KEYS[1]) == ARGV[1] then
       return redis.call('DEL', KEYS[1])
     end
     return 0`,
    { keys: [lockKey], arguments: [token] },
  )
}
```

锁的边界：

- 租约到期而任务没完成，另一个实例可能同时进入；需要 watchdog 续期，或把任务拆短。
- 主从切换可能丢掉刚写入的锁；对金额、库存等正确性敏感的操作，要用数据库行锁、条件更新或 fencing token，而不是只信 Redis 锁。
- 释放锁必须比较 token，不能直接 `DEL`，否则可能删掉别人的锁。

逻辑过期可以把“重建”从请求路径挪走：缓存值里存 `freshUntil` 和 `hardUntil`，在 `freshUntil` 之前直接返回；超过 `freshUntil` 但在 `hardUntil` 之前返回旧值并异步刷新；超过 `hardUntil` 才回源。它的代价是必须明确允许的最大旧值时间，并防止异步刷新任务无限堆积。

### 7.9 降级、熔断与容量保护

Redis 失败时，不同业务不能共用一句“降级查 MySQL”：

| 业务 | Redis 不可用时的方向 | 不能做什么 |
| --- | --- | --- |
| 可重建的查询缓存 | 绕过缓存查 MySQL，但要限并发、限流、熔断 | 无上限地把全部流量打到 MySQL |
| 登录失败计数 | 明确策略：本地计数、更严格校验或暂时拒绝 | 直接放行，削弱暴力破解防护 |
| 会话 | 多数场景应失败关闭或走备用会话存储 | 假装用户已登录 |
| 分布式锁 | 依赖数据库约束或 fencing token | 因为拿不到锁就认为操作安全 |

熔断器建议按依赖实例划分，而不是每个接口一个。常见状态机：

```text
closed（正常放行）
  └─ 连续失败达到阈值 → open（快速失败，不再打 Redis）
       └─ 冷却时间到 → half-open（放少量探测请求）
            ├─ 探测成功 → closed
            └─ 探测失败 → open
```

阈值要按流量定，例如“10 秒内 20 次失败或失败率超过 50%”打开 5 秒；探测只放 1 个请求。不要在没有样本量时用“失败率”判断，低流量下 1 次失败就是 100%。

降级还需要并发保护，否则缓存故障会演变成数据库故障：

- 为回源查询设置独立并发上限（信号量或数据库连接池上限），超限快速返回 503 或降级内容。
- 为整个请求设预算，例如网关 500ms、缓存 50ms、MySQL 200ms、降级路径 100ms；缓存超时不能吃掉数据库预算。
- 重试只用于幂等操作，最多一次，带抖动；不要在重试里再嵌套重试。
- 恢复时先预热热点 key、逐步放量，避免冷缓存瞬间被全部流量打穿。

### 7.10 观测与告警

没有观测的“企业级配置”无法维护。至少分三层看：

| 层 | 关键指标 | 说明 |
| --- | --- | --- |
| 业务缓存 | 命中率、回源 QPS、回源耗时、负缓存命中、single-flight 合并数 | 命中率要按业务命名空间看，不能只看全局 |
| Redis | `used_memory`、`maxmemory`、`evicted_keys`、`expired_keys`、`keyspace_hits/misses`、`instantaneous_ops_per_sec`、`latency`、`connected_clients`、`rejected_connections`、`blocked_clients` | `evicted_keys` 持续增长通常是容量或策略问题 |
| 依赖与复制 | 命令 p99、超时率、熔断状态、`master_link_status`、复制延迟、`rdb_last_bgsave_status`、`aof_last_write_status` | 复制延迟和持久化状态在启用对应能力时才关注 |

几个常用现场命令：

```text
INFO memory
INFO stats
INFO replication
INFO clients
SLOWLOG GET 10
LATENCY DOCTOR
MEMORY DOCTOR
CLIENT LIST
ACL LOG
```

以及离线抽样工具：

```text
redis-cli --bigkeys
redis-cli --hotkeys        # 需要 LFU 策略
redis-cli --scan --pattern 'shop:prod:*' --count 100
```

告警起点可以这样设，但要结合基线调整：

- `used_memory / maxmemory > 80%` 预警，`> 90%` 升级处理。
- `evicted_keys` 持续增长，或命中率相对基线下降 20% 以上。
- `rejected_connections > 0`，说明连接数或文件描述符已经不够。
- 同可用区命令 p99 明显升高（例如从 1ms 升到 10ms 以上），或 `SLOWLOG` 持续出现业务命令。
- 副本 `master_link_status:down`，或复制偏移落后超过业务容忍时间。
- 应用侧缓存超时率、熔断打开次数、降级次数、回源 QPS 突增。

日志和追踪里不要记录完整 value、密码、token 或用户隐私字段。key 可以记录“模板”（如 `user:profile`）和哈希后的 ID；需要排查具体 key 时，通过受控的运维通道查询。

### 7.11 安全与多租户

Redis 默认不是“放在内网就安全”。最低要求：

| 项目 | 做法 |
| --- | --- |
| 网络 | 只监听私网地址，安全组/防火墙限制来源，禁止公网直接暴露 6379 |
| 认证 | 关闭 `default` 用户的匿名能力，按应用创建 ACL 用户，密码从密钥管理注入并定期轮换 |
| 传输 | 跨网络或跨可用区使用 TLS，客户端用 `rediss://`，校验证书 |
| 命令权限 | 应用用户只授予实际命令和 key 前缀；禁用 `FLUSHALL`、`KEYS`、`CONFIG`、`DEBUG`、`MODULE`、`SHUTDOWN` 等 |
| 数据 | 不把明文密码、支付信息等敏感数据放进缓存；确需存放时在应用层加密 |
| 审计 | 保留 `ACL LOG`、`SLOWLOG`、变更记录和关键运维操作日志 |

一个最小 ACL 文件示意：

```conf
# /etc/redis/users.acl
user default off

# 业务应用：只允许访问 app: 前缀，只授予缓存需要的命令。
user app-cache on ><APP_PASSWORD> ~app:* -@all +get +set +del +mget +expire +ttl +eval +evalsha

# 运维：只读观察，禁止 FLUSHALL、KEYS、CONFIG SET。
user ops on ><OPS_PASSWORD> ~* -@all +info +slowlog|get +slowlog|len +memory|usage +client|list +latency|history +config|get
```

上线前用 `ACL LOG` 观察实际被拒绝的命令，再逐步收紧；不要一次把权限开到 `+@all` 然后忘记收。多租户场景下，ACL 的 key 前缀只能做第一层隔离，热点租户仍可能占满内存或带宽，需要独立实例、配额或至少按租户监控。

### 7.12 容量估算、发布与演练

容量估算不要只看“原始数据大小”。一个可用的起点：

```text
100 万用户 × 平均 2 KB ≈ 2 GB 原始数据
JSON、key、对象头和 allocator 开销按 30%～50% 估 ≈ 2.6～3 GB
复制缓冲、碎片、fork COW、峰值余量再留 30% ≈ 3.4～3.9 GB
→ 单节点 maxmemory 4 GB 起步，主机内存 6～8 GB
```

实际要用压测和 `INFO memory` 校准，不要把这个例子当成固定比例。尤其注意：

- Redis 的 `used_memory` 是分配器视角，进程 RSS 通常更高；容器限额要按 RSS 留余量。
- 开启 RDB 时，fork 后的写时复制可能让内存在短时间内明显上升。
- 主从复制有复制缓冲和 backlog；副本越多、断线越久，占用越高。
- 大量小 key 的对象头和 allocator 开销可能远超预期，必要时用 Hash 分桶。

发布与演练建议：

1. **配置即代码。** 配置文件进版本库，按环境渲染；变更走评审和灰度，保留回滚版本。
2. **先改副本，再切主。** 能在副本验证的参数先在副本验证；Cluster 迁移按槽位和副本顺序进行。
3. **演练故障，而不是只写预案。** 在隔离环境演练：杀主节点、注入 100ms 网络延迟、打满内存、断开副本、冷启动。
4. **验证客户端行为。** 故障切换后客户端是否能发现新主、是否重复重连、是否把错误正确降级；这些比“Sentinel 显示切换成功”更重要。
5. **验证数据库保护。** 缓存全挂时，回源 QPS 是否被限住，数据库连接池是否被打满，接口是否快速失败而不是堆积。

### 7.13 最小落地清单

不要一次把所有机制都堆上。可以按阶段推进：

| 阶段 | 必做项 |
| --- | --- |
| P0：上线前 | 强制 TTL、key 规范、`maxmemory` 与淘汰策略、超时、认证与网络隔离、缓存故障降级、基础指标和告警、禁止 `FLUSHALL`/`KEYS` |
| P1：稳定期 | TTL 抖动、负缓存、single-flight、熔断与回源并发上限、慢查询观察、容量压测、故障演练 |
| P2：规模化 | 多级缓存、CDC/消息失效、Cluster 或分片、租户隔离、客户端侧缓存、自动化容量评估 |

每一项都要能回答三个问题：它解决什么故障？引入什么新故障？怎么验证它真的生效？答不出来，就先不要加。

### 7.14 常见误区

1. `maxmemory` 等于容器内存上限，结果 fork 或碎片上升时被 OOM Kill。
2. 所有 key 都不设 TTL，靠 `allkeys-lru` 掩盖内存持续增长。
3. 把 Redis 当数据库，没开持久化却存会话、订单或队列。
4. 一个 key 存整页、整列表或超大 JSON，造成网络、删除和淘汰阻塞。
5. 每个请求新建客户端，制造连接风暴。
6. 命令超时后盲目重试 `INCR`、扣库存等非幂等操作。
7. 用 keyspace notification 或 Pub/Sub 做可靠缓存失效。
8. 以为 Cluster 能解决热 key；热 key 仍然落在一个槽位、一个主节点。
9. 把读副本当成强一致读，忽略复制延迟。
10. 先删缓存再更新数据库；或更新失败后仍然删缓存。
11. 缓存异常时用一个巨大 `try/catch` 把数据库错误也吞掉。
12. 直接复制别人的 `redis.conf`，不看版本、内存、网络和工作负载。

### 7.15 自检：把配置讲清楚

学完这一节，至少能回答：

1. 你的缓存 key 最长能活多久？删除失败时旧值还能活多久？
2. Redis 整体不可用时，读接口和写接口分别怎么退？MySQL 由谁保护？
3. 为什么 `maxmemory` 不能等于容器内存上限？
4. 你的实例里是否混放了会话、限流、锁或队列？淘汰策略会不会误伤？
5. 热 key 和大 key 怎么发现？发现后分别怎么处理？
6. 命中率下降时，怎么区分“流量变化”“key 设计变化”和“Redis 容量/故障”？
7. 故障切换后，客户端如何发现新主？有没有演练过？
8. 哪些读路径允许旧值？旧值窗口由 TTL、版本号还是业务补偿控制？
