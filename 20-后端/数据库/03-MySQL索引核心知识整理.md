# MySQL 数据库核心知识整理

## 一、数据库为什么需要索引

索引通过有序的数据结构减少查找所需的扫描量。是否需要性能索引没有固定行数门槛，要结合查询频率、数据分布、扫描量、读写比例与执行计划判断。小表扫描可能更便宜；主键与必要的唯一约束不应等数据量大才设置。

以一条主键查询为例，若实际使用主键索引，就不是从第一行逐个扫描。只有在说明“没有可用索引的查询”时，才适合用逐行查找作对照。

------------------------------------------------------------------------

# 二、B+ Tree 索引结构

MySQL InnoDB 常用 B+ Tree 作为索引结构。

核心思想：

> 先找到范围，再逐层缩小搜索。

例如：

                  [100 | 500]
                 /      |      \
              <100   100~499   >=500

查询：

    id = 238

过程：

    根节点
     ↓
    判断 238 属于 100~499
     ↓
    进入对应节点
     ↓
    继续查找
     ↓
    找到数据

优势：

-   不需要遍历所有数据
-   查询复杂度低
-   适合大量数据

------------------------------------------------------------------------

# 三、聚簇索引

在 InnoDB 中：

通常：

    PRIMARY KEY
            ↓
    聚簇索引

特点：

> 叶子节点保存完整数据行。

例如：

    id = 100

    username = Tom
    email = tom@test.com
    status = 1

全部存储在聚簇索引叶子节点。

查询：

``` sql
SELECT *
FROM users
WHERE id = 100;
```

过程：

    主键索引
     ↓
    找到 id=100
     ↓
    直接返回整行数据

不需要再次查询。

------------------------------------------------------------------------

# 四、二级索引（普通索引或唯一索引）

例如：

``` sql
CREATE INDEX idx_email
ON users(email);
```

这是一棵新的 B+ Tree。

但是叶子节点不是完整数据。

而是：

    email + 主键id

例如：

    tom@test.com → 100

为什么保存主键？

因为 InnoDB 的真实数据在聚簇索引中。

------------------------------------------------------------------------

# 五、回表

查询：

``` sql
SELECT *
FROM users
WHERE email='tom@test.com';
```

执行过程：

    email普通索引

            ↓

    找到：
    email=tom@test.com

    得到：
    id=100

            ↓

    根据id查询主键索引

            ↓

    获得完整数据

这个过程叫：

> 回表

原因：

普通索引没有保存完整数据，需要再次访问聚簇索引。

------------------------------------------------------------------------

# 六、覆盖索引

如果查询需要的字段全部存在索引中：

就不需要回表。

例如：

索引：

    email + id

查询：

``` sql
SELECT id,email
FROM users
WHERE email='tom@test.com';
```

需要：

    id ✅
    email ✅

索引已经包含。

流程：

    普通索引
     ↓
    直接返回

这叫：

> 覆盖索引

------------------------------------------------------------------------

# 七、联合索引

例如：

``` sql
CREATE INDEX idx_project_status
ON tasks(project_id,status);
```

不是两个索引：

    project_id索引
    +
    status索引

而是一棵：

    (project_id,status)

联合排序的 B+ Tree。

排序规则：

    先按照 project_id 排序

    project_id相同

    再按照 status 排序

例如：

    (1,0)
    (1,1)
    (1,2)

    (2,0)
    (2,1)

------------------------------------------------------------------------

# 八、最左前缀原则

假设：

``` sql
INDEX(a,b,c)
```

可以理解为：

    a
     ↓
    b
     ↓
    c

可以使用：

``` sql
WHERE a=1
```

✅

``` sql
WHERE a=1 AND b=2
```

✅

``` sql
WHERE a=1 AND b=2 AND c=3
```

✅

但是：

``` sql
WHERE b=2
```

通常无法充分利用。

原因：

索引首先按照 a 排序。

不知道 a，就无法快速定位 b。

注意：

SQL 条件顺序不重要：

``` sql
WHERE b=2 AND a=1
```

仍然可以使用：

    INDEX(a,b)

因为优化器会处理。

------------------------------------------------------------------------

# 九、EXPLAIN

EXPLAIN 用来查看：

> MySQL 准备如何执行 SQL。

使用：

``` sql
EXPLAIN
SELECT *
FROM users
WHERE email='test@qq.com';
```

它不会真正查询数据。

而是返回执行计划。

重点关注：

## key

实际使用的索引。

例如：

    key:
    idx_email

表示使用：

    idx_email

## rows

预计扫描行数。

例如：

    rows:10000000

表示预计检查大量数据。

## type

查询方式。

常见：

### ALL

全表扫描：

    一行一行检查

### ref

通过索引找到一批数据。

### range

范围查询。

# 十一、学习总结

数据库学习核心链路：

    表设计
     ↓
    主键
     ↓
    索引
     ↓
    B+ Tree
     ↓
    聚簇索引
     ↓
    二级索引
     ↓
    回表
     ↓
    覆盖索引
     ↓
    联合索引
     ↓
    最左前缀
     ↓
    EXPLAIN
     ↓
    SQL优化

核心理解：

> 索引不是简单加速，而是通过数据结构改变查找方式。

> 聚簇索引保存真实数据。

> 普通索引保存索引字段和主键。

> 回表是通过普通索引找到主键后，再查询完整数据。

> 覆盖索引是不需要回表。

> 联合索引的字段顺序决定查询效率。

> EXPLAIN 用来验证 MySQL 是否按照预期使用索引。


# 十二、字符串如何定位到索引节点

普通主键和二级索引通常用 B+ 树组织。上层节点保存分界信息用于指路，叶子节点保存索引记录。

邮箱虽然看起来没有规律，也可以比较大小。先用字母顺序理解：alice 排在 mike 前，nancy 排在 mike 与 tom 之间。真实 MySQL 根据字段的排序规则（collation）比较字符串，大小写、重音等处理取决于该规则，不一定是简单比较字符编码。

```text
              分界值：[mike | tom]
                 /       |
           小于 mike   mike 到 tom   大于等于 tom
```

查询 nancy 时，比较分界值后走中间分支。树不需要先知道它属于什么邮箱域名或业务大类。

分界值与节点由数据库动态维护，不是开发者预先规定“a 开头一类、b 开头一类”。

# 十三、邮箱唯一索引的约束范围

`UNIQUE(email)` 只要求邮箱不重复；InnoDB 二级索引记录携带主键，是为了定位用户行，不代表主键参与 email 的唯一性规则。

`UNIQUE(id, email)` 只限制组合重复，无法阻止不同 ID 的用户使用相同邮箱。唯一性判断也受字段排序规则影响。

# 十四、写入如何维护索引

不会。正常写入是局部维护已有索引。

1. 根据索引键找到合适的叶子节点。
2. 检查必要约束，在节点中按顺序插入记录。
3. 有空间时通常只修改相关页。
4. 空间不足时，可能拆分节点并更新父节点分界信息。
5. 如果父节点也需要拆分，继续向上调整；根节点拆分可能使树增高。

这与给已有表新增索引、显式重建索引或某些表结构变更不同，普通 INSERT 不会每次重建全部索引。

索引维护由数据库在处理写入时负责，不需要 Node 后端再调用一次“刷新索引”，也不是等定时任务把树重新生成。

| 操作 | 需要理解的索引维护 |
| --- | --- |
| INSERT | 写入行，并维护涉及的主键和二级索引 |
| UPDATE 非索引列 | 修改行数据，通常不需要改变未受影响的二级索引键 |
| UPDATE 索引列，例如 email | 维护旧键与新键的对应记录；唯一索引还需检查冲突 |
| DELETE | 记录删除并维护相关索引；InnoDB 的标记删除与后台清理不一定同时完成 |

索引维护参与事务，回滚后不能留下一个对后续查询有效的孤立索引项。

部分符合条件的非唯一二级索引修改，在启用相关机制时可能先记录到 change buffer，再合并到索引页。这是内部优化，不意味着业务可以读到随意过时的索引结果。邮箱唯一索引需要在写入时检查唯一性，不能按同样方式理解为延后检查。

索引能减少查询扫描，但也占空间、增加写入维护成本，所以不是每个字段都应该建索引。
