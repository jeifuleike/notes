# Docker 基础与使用场景

> 学习目标：知道 Docker 解决什么问题，理解镜像、容器、网络和存储，能选择合适的使用场合，并能看懂一个 Node + 数据服务的容器化方案。
>
> 本章以 Linux 容器为主。示例用于解释原理，不表示已在当前电脑部署或验收；镜像版本、安装要求和产品条款以官方文档为准。资料核对日期：2026-11-08。

## 1. Docker 到底是干什么的

Docker 是一套构建、分发和运行容器化应用的工具。

假设你写了一个 Express 服务。它运行时不仅需要 JavaScript 文件，还需要指定版本的 Node、npm 依赖、某些系统库，以及端口、环境变量等配置。只把代码复制到另一台电脑，未必能直接运行。

使用 Docker 后，可以把代码、运行时和依赖构建成**镜像**，交给目标机器上的容器运行环境启动。启动后的运行实例就是**容器**。数据库密码、端口映射、持久化目录等通常在运行时配置，不应该全部烘焙到镜像里。

```text
代码 + 依赖声明 + Dockerfile
            ↓ 构建
          应用镜像
            ↓ 推送 / 拉取
          镜像仓库
            ↓ 启动并注入配置
          应用容器
            ↓ 网络连接
     MySQL / Redis / 外部 API
```

可以先记住：**镜像描述“运行什么”，运行配置描述“怎么运行”，容器是实际运行的实例，卷保存需要长期保留的数据。**

官方对这些对象和工作流程的介绍见 [Docker overview](https://docs.docker.com/get-started/docker-overview/)。

## 2. 为什么要用它：从环境问题理解价值

### 2.1 没有 Docker 时的常见问题

- 甲用 Node 的一个版本，乙用另一个版本，依赖安装和运行结果不同。
- 一台电脑上的多个项目需要不同版本的数据库或系统库。
- 新成员加入时，需要按文档逐项安装软件、创建目录、配置服务。
- 测试服务器和生产服务器装的东西不完全一致，发布后才暴露问题。
- 临时测试一个 Redis，安装和清理服务比测试本身还麻烦。

Docker 把其中许多人工操作转成可保存、可审查的文件和可分发的镜像，减少每台机器重新拼装环境的工作。

### 2.2 它能带来的能力

| 能力 | 具体例子 | 仍需自己处理的部分 |
| --- | --- | --- |
| 环境标准化 | 团队使用同一份应用镜像 | 配置、数据、内核和架构仍可能不同 |
| 依赖隔离 | 不同项目分别运行不同数据库版本 | 主机资源和映射端口仍会竞争 |
| 快速创建与清理 | 为接口测试临时启动一个数据库 | 数据卷的保留、清理策略 |
| 可追踪交付 | 用镜像版本或 digest 标识一次发布 | 镜像测试、漏洞修复、数据库迁移 |
| 组合服务 | 一份 Compose 描述 API、Redis、数据库 | 业务重试、监控、备份 |
| 便于扩展实例 | 同一镜像启动多个 API 实例 | 负载均衡、共享状态、调度 |

Docker 不会自动修复代码错误、SQL 慢查询、业务并发问题，也不意味着服务天然高可用。

## 3. 容器是什么，和虚拟机有什么区别

### 3.1 容器首先是运行中的进程

以 Linux 容器为例，容器内的 Node 最终仍是运行在 Linux 内核之上的进程。内核通过 namespace 隔离进程视图、网络等，通过 cgroup 统计和限制资源；容器还拥有自己的文件系统视图。

容器里看到的 `/app`、进程列表和网卡，可以与宿主机上看到的不同，但这不代表里面运行了一套独立 Linux 内核。基础镜像中的 Debian、Alpine 等主要提供用户空间文件、库和工具。

资源隔离也不代表每个容器自动获得合理的 CPU、内存配额。需要按负载显式配置限制；容器和宿主机仍共享底层资源。隔离与安全机制可参考 [Docker Engine security](https://docs.docker.com/engine/security/)。

### 3.2 与虚拟机比较

| 维度 | 容器 | 虚拟机 |
| --- | --- | --- |
| 核心方式 | 隔离进程及其运行环境 | 虚拟化硬件，运行来宾操作系统 |
| 内核 | 同一运行环境中的 Linux 容器共享 Linux 内核 | 每台虚拟机有自己的来宾内核 |
| 启动成本 | 通常较小，但应用本身仍需初始化 | 通常还需启动来宾操作系统 |
| 常见用途 | 打包服务、构建任务、测试依赖 | 完整操作系统环境、较强隔离边界 |
| 安全边界 | 共享内核，依赖权限和内核安全 | 通常提供更强的系统隔离 |

容器和虚拟机可以一起使用：云服务器可能本来就是虚拟机，其内部再运行容器。

### 3.3 Windows 上为什么还涉及 WSL 2

常见的 Node、MySQL、Redis 示例镜像是 Linux 镜像，需要 Linux 内核。Windows 上 Docker Desktop 可以借助 WSL 2 或相应虚拟化后端提供这个环境。

因此，“容器共享内核”指共享容器所在 Linux 环境的内核，不是 Linux 应用直接使用 Windows 内核。Windows 容器是另一类，需要匹配的镜像和运行模式。

镜像还区分 `amd64`、`arm64` 等 CPU 架构。多平台镜像或模拟执行能改善兼容性，但不能保证任意镜像在任意机器上无差别运行。

安装前按 [Windows 安装说明](https://docs.docker.com/desktop/setup/install/windows-install/) 检查虚拟化、WSL、系统要求及 Docker Desktop 使用条款。

## 4. 必须分清的对象和工具

| 名词 | 是什么 | 类比 / 例子 |
| --- | --- | --- |
| Dockerfile | 构建镜像的文本说明 | 指定基础镜像、复制文件、安装依赖 |
| Image，镜像 | 运行应用的只读模板与元数据 | `redis:7`、自建的 `study-api:1.0` |
| Container，容器 | 从镜像创建的运行实例及其状态 | 一个正在运行的 Redis |
| Registry，镜像仓库服务 | 保存和分发镜像 | Docker Hub、企业私有仓库 |
| Repository，镜像仓库中的命名集合 | 某个名称下的一组镜像版本 | `team/study-api` |
| Tag，标签 | 可移动的版本名称 | `1.0`、`latest` |
| Digest，摘要 | 按内容标识镜像 | `sha256:...` |
| Volume，卷 | Docker 管理的持久化存储 | MySQL 数据目录 |
| Network，网络 | 容器通信的连接环境 | API 与数据库之间的网络 |
| Docker CLI | 终端中的客户端 | `docker ps` |
| Docker Engine | 管理镜像、容器、网络等的核心服务 | CLI 将请求发给它 |
| Docker Desktop | 桌面集成产品 | 包含界面、运行环境和常用工具 |
| Docker Compose | 按 YAML 定义和管理多个服务 | `docker compose up -d` |

CLI 可以操作远程 Engine，所以命令实际影响的是当前 context 指向的环境。删除或清理前可以用 `docker context show` 确认目标。

Dockerfile 负责构建单个镜像；Compose 负责描述多个服务如何运行。Compose 并不要求每个服务都自己构建，也可以直接使用现成镜像。

### 标签不等于不可变版本

`latest` 只是普通标签，不承诺最新、稳定或适合你的项目。其他标签也可能被重新指向。需要严格追踪发布时，应记录镜像 digest；同时建立定期更新和重新测试机制，不能固定旧镜像后永久不更新。

镜像通常只包含应用自身及其运行依赖。API 镜像不会因为项目使用 MySQL，就自动把 MySQL 服务也装进去。

## 5. 镜像、容器和进程的生命周期

```text
docker build / pull → 本地镜像
                         ↓ docker run（创建并启动）
                       容器运行
                         ↓ 主进程退出 / docker stop
                       容器停止
                         ↓ docker start
                       同一容器再运行
                         ↓ docker rm（通常先停止）
                       容器删除
```

- 同一镜像可以创建多个容器，各有自己的运行状态和可写层。
- 停止容器不会删除它的可写层；删除并重建容器时，旧可写层中的数据不会自动回来。
- 删除容器不等于删除镜像，删除镜像也不等于删除独立数据卷。
- `docker restart` 重新启动原容器，不会自动使用刚拉取的新镜像。
- 要升级镜像，通常需要基于新镜像重建容器，并重新挂载原来的持久化数据。

容器通常以前台主进程作为存活依据。主进程结束，容器就退出；`-d` 只是让客户端不持续占用当前终端，不会让已退出的程序继续运行。不要通过在容器里“后台启动服务后立刻结束脚本”的方式维持服务。

设计上通常让一个容器承担一个主要职责，例如 API、数据库分别运行。一个服务可能有多个协作进程，“一个容器只能有一个进程”并非硬性规则。

## 6. 第一个例子：运行一个本地 Web 服务

前提：已安装并启动 Docker 的运行环境，终端能连接 Engine。

```powershell
docker version
docker info
docker run --name docker-web-demo -d -p 127.0.0.1:8080:80 nginx:stable
```

逐项理解最后一条命令：

- `run`：创建并启动容器；本地没有镜像时通常会尝试拉取。
- `--name`：给容器起名，方便后续管理；同一 Engine 内名称不能冲突。
- `-d`：后台运行。
- `-p 127.0.0.1:8080:80`：将宿主机回环地址上的 8080 映射到容器的 80。
- `nginx:stable`：使用 Nginx 镜像的 `stable` 标签；这里用于演示，并非精确锁定版本。

浏览器访问 `http://localhost:8080`。随后查看和停止：

```powershell
docker ps
docker logs --tail 50 docker-web-demo
docker stop docker-web-demo
docker ps -a
docker start docker-web-demo
```

实验结束后，先停止再运行 `docker rm docker-web-demo`，只删除这个演示容器。没有必要为了清理一个示例去全局清空 Docker。

## 7. 网络：三个 localhost 和两个端口

这是新手最容易卡住的地方。

### 7.1 localhost 指向当前网络环境自身

假设 Windows 上运行 Node，Docker 中运行 Redis：

```text
宿主机 Node → localhost:6379 → 已发布的 Redis 容器端口
```

如果 Node 和 Redis 都在同一 Compose 项目默认网络中：

```text
API 容器 → redis:6379 → Redis 容器
```

API 容器里的 `localhost` 通常指 API 容器自己，不能拿它访问另一个 Redis 容器。Compose 内通常用服务名进行名称解析，不依赖会变化的容器 IP。

从 Docker Desktop 容器访问宿主机服务，常见地址是 `host.docker.internal`；原生 Linux Engine 上不要假定它自动存在，需要按环境配置 host gateway 等方式。

### 7.2 容器端口与宿主机端口

```text
-p 127.0.0.1:8080:3000
   宿主机地址:宿主机端口:容器端口
```

- 浏览器访问宿主机 8080；应用在容器里监听 3000。
- 容器内应用通常要监听 `0.0.0.0:3000`，只监听容器自己的 `127.0.0.1` 可能无法通过发布端口访问。
- `EXPOSE 3000` 是镜像元数据，不会自动发布端口；仍需 `-p` 或 Compose `ports`。
- 同网络容器之间通常可直接访问服务端口，不必先发布给宿主机。
- `-p 8080:3000` 未指定绑定地址时通常发布到所有宿主机接口，可能被其他机器访问；开发示例优先显式绑定回环地址。
- 同一个宿主机地址与端口不能同时随意分配给多个服务。

官方说明：[容器网络与端口发布](https://docs.docker.com/engine/network/)。

## 8. 存储：容器可以重建，业务数据要保留

### 8.1 三种常见存储选择

| 方式 | 数据位置和管理方式 | 适合什么 |
| --- | --- | --- |
| 容器可写层 | 当前容器自己的文件系统变化 | 可丢弃临时文件 |
| Named volume，命名卷 | Docker 管理，生命周期独立于容器 | 数据库数据、需要长期保存的文件 |
| Bind mount，绑定挂载 | 明确指定宿主机路径 | 开发源码、配置文件、需要主机直接管理的文件 |
| tmpfs | 内存中的临时挂载 | 无需持久化的临时数据；停止后不保留 |

例如：

```text
--mount type=volume,source=mysql-data,target=/var/lib/mysql
```

表示把名为 `mysql-data` 的卷挂到 MySQL 容器的数据目录。容器替换后继续挂载同一卷，数据才有机会继续被数据库读取；数据库版本和数据格式仍须兼容。

### 8.2 必须分清的边界

- **卷不是备份。** 删错数据、磁盘损坏和误删卷仍会造成丢失，需要独立备份并验证恢复。
- 挂载会遮住目标目录原本可见的内容。开发时把整个项目目录挂到 `/app`，可能把镜像中的依赖目录一起遮住。
- 绑定挂载默认可能允许容器修改宿主机文件，只读配置可使用只读挂载。
- Docker Desktop 中卷通常位于其 Linux 环境中，不应凭直觉去 Windows 某目录直接修改数据库文件。
- 多个数据库实例不要同时随意挂同一个数据目录；共享文件不代表数据库具备协调并发访问的能力。

依据：[Docker 存储机制](https://docs.docker.com/engine/storage/)。

## 9. Dockerfile：如何把自己的 Node 服务做成镜像

以下假设项目已有 `package.json`、`package-lock.json` 和 `server.js`，使用 Node 内置 HTTP 或已声明在生产依赖中的框架，服务监听 `0.0.0.0:3000`。

```dockerfile
FROM node:24-bookworm-slim
WORKDIR /app

COPY package.json package-lock.json ./
RUN npm ci --omit=dev

COPY --chown=node:node . .
ENV NODE_ENV=production
USER node
EXPOSE 3000
CMD ["node", "server.js"]
```

这里选择了一个明确的 Node 主版本和基础发行版作为示例；实际应与项目兼容性和维护策略匹配。标签仍可能更新，需要精确复现时再固定 digest。

| 指令 | 含义 | 常见误区 |
| --- | --- | --- |
| `FROM` | 选择基础镜像 | 不是连接某个已运行容器 |
| `WORKDIR` | 设置后续工作目录 | 不必每条命令都手动 `cd` |
| `COPY` | 从构建上下文复制文件 | 不能任意复制上下文外的文件 |
| `RUN` | 构建镜像时执行命令 | 不会在每次启动容器时重新执行 |
| `ENV` | 设置镜像中的默认环境变量 | 不适合保存密码 |
| `USER` | 设置后续运行用户 | 非 root 用户仍需正确的目录权限 |
| `EXPOSE` | 说明预期监听端口 | 不等于 `-p` |
| `CMD` | 默认启动命令 | 可以在运行时被覆盖 |
| `ENTRYPOINT` | 定义主执行入口 | 常配合 `CMD` 提供默认参数 |
| `ARG` | 构建参数 | 不应当作秘密传递机制 |

`CMD` 的 JSON 数组写法让程序直接成为容器主进程，有利于接收停止信号。应用仍应处理 `SIGTERM`，停止接收新请求、关闭连接后退出。

### 9.1 构建上下文与 .dockerignore

在项目根目录执行：

```powershell
docker build -t study-api:local .
docker run --name study-api-demo -d -p 127.0.0.1:3000:3000 study-api:local
```

最后的 `.` 是构建上下文，不是随便加的标点。Dockerfile 中的 `COPY` 从这个上下文取文件。

项目根目录的 `.dockerignore` 可写：

```text
node_modules
.git
.env
.env.*
!.env.example
npm-debug.log
coverage
```

这既减少无用内容，也避免把本地依赖或秘密误带进镜像。`.gitignore` 不会自动代替 `.dockerignore`。

### 9.2 为什么先复制依赖声明

镜像构建通常可以复用缓存。先复制锁文件并安装依赖，再复制源代码，源代码变化时更有机会复用依赖安装步骤。基础层或输入发生变化会影响后续缓存。

不要把 Windows 的 `node_modules` 直接复制进 Linux 镜像：原生模块可能与操作系统、CPU 和库版本绑定。应在目标构建环境安装。

### 9.3 TypeScript 与多阶段构建

TypeScript 项目通常还需要开发依赖来编译。可以在构建阶段安装全部依赖并生成 `dist`，再把构建产物和生产依赖复制到运行阶段。最终镜像不必携带编译器和全部源码。

不要直接套用上面的 `--omit=dev` 然后指望不存在的 TypeScript 编译器完成构建。多阶段构建也适合前端：第一阶段构建静态文件，第二阶段用 Web 服务器提供文件。

指令语义见 [Dockerfile reference](https://docs.docker.com/reference/dockerfile/)，缓存、基础镜像和多阶段构建策略见 [构建最佳实践](https://docs.docker.com/build/building/best-practices/)。

## 10. Compose：让 API 与 Redis 组成一个应用

当你需要同时配置几个容器时，把长串启动参数写进 `compose.yaml` 更容易维护。

以下是**本地学习配置**：假设上一节 Node 项目已使用 Redis 客户端，读取 `REDIS_URL`；安装 npm 包并不等于代码已经实现连接和重试。

```yaml
name: docker-study

services:
  api:
    build: .
    ports:
      - "127.0.0.1:3000:3000"
    environment:
      NODE_ENV: production
      REDIS_URL: redis://redis:6379
    depends_on:
      redis:
        condition: service_healthy
    restart: unless-stopped

  redis:
    image: redis:7
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10
    restart: unless-stopped

volumes:
  redis-data:
```

理解这份文件：

- `api`、`redis` 是服务名；Compose 默认网络支持用服务名连接。
- `build: .` 从当前项目构建 API 镜像；Redis 直接使用现成镜像。
- 只把 API 端口发布到宿主机；Redis 无需为了 API 访问而额外发布。
- `environment` 把配置传给容器，应用仍要主动读取。
- 命名卷保存 Redis 数据；AOF 开启了持久化机制，但不保证每一次写入在断电后都不丢，也不能替代备份。
- `healthcheck` 检查 Redis 是否能响应 PING；它不等于检查整个业务链路正常。
- `depends_on` 加 `service_healthy` 能在启动时等待健康条件；服务运行后断线，应用仍需重连和错误处理。
- `restart` 是进程退出等情况下的重启策略；普通 Docker 运行不会仅因状态变为 `unhealthy` 就自动重启容器。

这个示例没有配置 Redis 认证，适用于受控的本地演示网络；生产环境要结合网络边界、认证、秘密管理等重新设计。

在 `compose.yaml` 所在项目目录运行：

```powershell
docker compose config
docker compose up -d --build
docker compose ps
docker compose logs --tail 100 -f api
docker compose exec redis redis-cli ping
docker compose down
```

`config` 可查看解析后的配置，但输出可能包含敏感配置，分享前检查。`logs -f` 持续跟随日志，按 Ctrl+C 退出日志查看。

`down` 通常删除项目容器和网络，保留命名卷；**`down -v` 会进一步删除相应卷，可能直接删除业务数据**。不要把它当普通停止命令。只想暂停可以用 `docker compose stop`。

Compose 项目名影响资源命名。换了项目名或目录后，可能创建新卷而看到空数据，不能据此立即认定原卷已经丢失。

启动依赖的具体行为见 [Compose startup order](https://docs.docker.com/compose/how-tos/startup-order/)。

## 11. 开发、构建和运行配置不要混淆

### 11.1 开发环境与生产环境

| 方面 | 开发环境常见做法 | 生产环境常见做法 |
| --- | --- | --- |
| 源码 | 绑定挂载、热更新 | 构建后放进镜像 |
| 依赖 | 包含调试、编译工具 | 尽量仅保留运行所需内容 |
| 修改代码 | 修改本地源码触发刷新 | 重新构建、测试、发布镜像 |
| 数据服务 | 本地临时容器或测试数据 | 明确持久化、备份和恢复策略 |
| 日志 | 终端查看 | 采集、保留、轮转、告警 |

本地 Node + Docker 中的 MySQL/Redis 是完全合理的组合。初学时不必立刻把所有东西都放进容器，先隔离复杂依赖通常就能获得价值。

### 11.2 前端项目尤其要注意构建时配置

Vite 等工具常把环境值在构建时写进静态文件。静态文件已经构建好后，给 Nginx 容器加一个环境变量，通常不会自动改变 JS 中的 API 地址；需要重新构建或专门设计运行时配置加载。

浏览器请求由用户电脑发出，不能直接解析 Compose 内部的 `api` 服务名。前端通常通过公开 API 地址或同域反向代理访问后端。

### 11.3 .env 与秘密

Compose 的 `.env` 常用于 `${变量}` 插值，并不意味着所有变量都会自动进入容器。`environment`、`env_file` 与应用自己加载 `.env` 是不同机制。

不要把密码、令牌通过 `COPY . .`、`ARG` 或 `ENV` 写进镜像。删除后续层中的文件也不保证早期层的秘密被抹掉。构建时需要私密凭证可采用构建 secret；运行时结合平台秘密管理或受控文件注入。环境变量同样可能通过诊断和管理接口被有权限的人查看。

## 12. 发布、升级与回滚的正确理解

常见交付过程是：

```text
提交代码 → 自动测试 → 构建镜像 → 镜像测试 / 扫描
       → 推送仓库 → 目标环境拉取 → 重建容器 → 检查健康和业务
```

生产发布通常运行 CI 已验证过的同一份镜像，避免在每台服务器现场重新拼装不同产物。

- 更新镜像通常要拉取新镜像并重建，`pull` 本身不会替换正在运行的容器。
- 回滚应用可以切换旧镜像，但数据库已经执行的破坏性迁移不会因此自动回滚。
- 数据库镜像升级前要查兼容性、升级路径和备份恢复方案，不能随意换 tag 后继续挂旧数据卷。
- 单机 Compose 可以用于合适规模的部署，但单台主机故障时，全部服务可能一起不可用。
- Kubernetes 等编排系统进一步管理跨机器调度、服务发现、扩缩容和恢复；引入后仍需运维知识。Docker 和 Kubernetes 并非二选一的同类产品，Kubernetes 也不要求使用 Docker Engine 作为运行时。

## 13. 日常管理和排障：先观察，再修改

| 要回答的问题 | 常用命令 | 观察重点 |
| --- | --- | --- |
| 客户端能连上运行环境吗 | `docker version`、`docker info` | Client / Server 信息与连接错误 |
| 当前操作哪个环境 | `docker context show` | 本地还是远程 |
| 为什么“找不到容器” | `docker ps -a` | 是否已退出、名字是否正确 |
| 应用报了什么错 | `docker logs --tail 100 名称` | 启动错误、连接失败、权限问题 |
| 配置实际是什么 | `docker inspect 名称` | 挂载、端口、退出码、健康状态 |
| 容器里能执行什么 | `docker exec -it 名称 sh` | 镜像未必包含 bash 或调试工具 |
| 是不是资源不足 | `docker stats` | CPU、内存；结合 OOM 状态判断 |
| 占用了多少磁盘 | `docker system df` | 镜像、容器、卷、构建缓存 |
| Compose 解析是否正确 | `docker compose config` | 插值、服务配置、挂载路径 |

应用日志优先写标准输出和标准错误，让 Docker 或平台采集。日志仍会占磁盘，需要合理配置轮转和保留。

### 常见故障的推理顺序

1. **容器刚启动就退出**：先查日志和退出码；检查启动命令、缺失文件、环境变量、目录权限。不要先反复重装 Docker。
2. **浏览器访问不到**：检查应用进程、监听地址、容器端口、端口映射、宿主机防火墙，再检查代理链路。
3. **API 连不上数据库**：确认两者分别在宿主机还是容器中，检查地址是否误用 localhost，再检查网络、服务就绪、凭证和权限。
4. **改代码没生效**：确认运行的是哪个镜像；没有挂载源码时通常需要重新构建并重建容器，重启旧容器并不会更新文件。
5. **重建后数据没了**：确认是否挂卷、挂载目标是否正确、项目名是否变化、是否误删卷；先检查现存卷再继续清理。
6. **Windows 下脚本执行失败**：检查 CRLF/LF、执行权限、路径大小写和解释器；不同基础镜像提供的工具也可能不同。
7. **拉取镜像失败**：检查镜像名、标签、仓库权限、网络、代理及平台架构；不要把仓库下载问题当成应用代码问题。

不要用 `docker commit` 保存手工改好的容器来代替正常构建流程；修改应回到代码和 Dockerfile，才能追踪和复现。

## 14. 安全与资源管理的基础底线

- 镜像中的软件仍可能有漏洞，优先使用来源清楚的镜像，持续更新并测试。
- 尽量用非 root 用户运行应用；按需减少 capabilities、使用只读文件系统等约束。
- 不要为解决普通权限问题随意使用 `--privileged` 或挂载整个宿主机根目录。
- 把 Docker socket 挂进容器通常会授予非常强的宿主机控制能力，不能当普通文件共享。
- 给 CPU、内存、日志和磁盘设定与业务匹配的预算；例如运行时可使用 `--memory`、`--cpus`，并验证实际生效。
- 用端口发布和网络规则限制访问面，不因“在容器里”就忽略数据库认证。
- 运行不可信代码时要评估共享内核风险。一般容器不能视为绝对安全沙箱，可能还需要虚拟机或专门的隔离方案。

这些措施提高可控性，但不会代替应用鉴权、输入校验、TLS、备份和监控。权限边界参考 [Engine 安全说明](https://docs.docker.com/engine/security/)。

清理时优先定位具体容器、镜像或缓存。`prune` 一类命令可能批量清理未使用资源；是否包含卷、哪些卷会被删与具体命令和选项有关，执行前必须查看帮助并确认数据归属。

## 15. 什么场合适合用，什么场合要慎重

| 场景 | 判断 | 原因 / 前提 |
| --- | --- | --- |
| 本地学 MySQL、Redis、消息队列 | 很适合 | 少污染本机，容易切换和重建；保留所需数据卷 |
| 团队统一后端开发依赖 | 很适合 | 配置可以纳入版本管理 |
| CI 中运行构建、集成测试 | 很适合 | 可创建相对独立、可重复的执行环境 |
| 发布无状态 HTTP API | 常见适用场景 | 配置外置、日志可采集、状态有明确归属 |
| 单机运行多个小服务 | 可以考虑 Compose | 能接受单机边界，并能维护备份和升级 |
| 生产数据库 | 可以，但需专门设计 | 卷、性能、备份、升级、恢复、高可用都不能省略 |
| 只写一个简单前端页面 | 未必需要 | 本地 Node 工具链可能已经足够 |
| 多租户不可信代码执行 | 不能仅凭普通容器认定安全 | 需要更强隔离与资源控制评估 |
| 需要完全不同内核或完整桌面 OS | 优先评估虚拟机 | 普通 Linux 容器不提供独立内核 |
| 大规模跨服务器自动调度 | Docker 单独不够 | 还需要编排、可观测性和平台治理 |
| 强依赖 GPU、USB 或特殊驱动 | 先核查平台支持 | 容器不能自动解决宿主机驱动兼容性 |

选择时问自己：

1. 当前痛点是环境、依赖、交付，还是代码本身？
2. 哪些服务值得独立运行，数据由谁持有？
3. 目标机器的操作系统、CPU 架构和资源是否支持？
4. 谁处理镜像更新、凭证、日志、备份和故障恢复？
5. 引入后的维护成本是否小于它减少的环境成本？

对当前 Node 后端学习路线，可以先让 Node 在本机运行，用 Docker 启动 MySQL/Redis；熟悉连接与持久化后，再给 Node 写 Dockerfile，最后用 Compose 整合。先理解每个服务，再自动化组合它们。

## 16. 用这些问题检查自己是否理解

1. **安装 Docker 后就有 Redis 吗？** 没有。还要获取镜像、创建容器并启动服务。
2. **安装 npm 的 redis 包就有 Redis 服务吗？** 没有，那是客户端库。
3. **容器里有一整台独立操作系统吗？** 通常没有独立内核，主要是隔离的进程及用户空间。
4. **同一镜像启动两次会共享业务数据吗？** 不会自动共享，取决于卷、外部数据库等设计。
5. **停止容器会丢所有文件吗？** 通常不会；删除重建时旧可写层才是主要风险。
6. **写了 EXPOSE 就能从浏览器访问吗？** 不能，仍需端口发布、正确监听和网络可达。
7. **API 容器能用 localhost 找到另一个数据库容器吗？** 通常不能，应使用相应网络中的服务名。
8. **健康检查通过就表示业务正确吗？** 不能，只代表该检查条件成立。
9. **拉取新镜像再 restart 就更新了吗？** 通常没有，需要以新镜像重建容器。
10. **卷保证永不丢数据吗？** 不能，持久化、备份和恢复是不同职责。
11. **应用能在本机运行，就一定能在容器运行吗？** 不一定，还要检查文件路径、系统依赖、权限、监听地址和平台架构。
12. **能启动容器就算完成生产部署吗？** 不算，还需要配置管理、访问控制、监控、备份、升级和恢复能力。
