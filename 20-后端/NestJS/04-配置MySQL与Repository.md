# 第 04 节　Nest 应用怎样使用 MySQL？

这一节解决的是**数据存在哪里，程序怎样读写它**。可以从一个常见现象开始理解：把记录存在 JavaScript 数组里，在页面上点刷新，还能查到；把后端程序停掉再启动，刚才那条记录就消失了。刷新只让浏览器重新发请求，重启后端却会重新创建那块内存。

如果希望程序重启以后仍能读到之前保存的数据，就需要**持久化**。MySQL 是一种常用选择。理解它怎么接入 Nest，可以依次看四个问题。

## 数据库、SQL 和驱动分别是什么？

**MySQL 是管理数据的服务。** 它可以独立于 Nest 运行，把记录持久保存在自己的存储中。关系型数据库用**表**组织数据：一行是一条记录，一列是一种属性。**主键**用来唯一标识一行，所以即使两个人同名，也可以用不同的 ID 分清。

**SQL 是跟关系型数据库交谈的语言。** 常见的四个操作是 `SELECT` 查询、`INSERT` 新增、`UPDATE` 更新、`DELETE` 删除。下面这一行就表达了一次读取：

```sql
SELECT name FROM users WHERE id = ?
```

它的意思是“在用户表里，找到指定 ID 的那一行，取出姓名”。这里的 `?` 是**占位符**，执行时再单独传入具体的 ID。SQL 负责表达要做的事，参数负责提供这次要用的值。

**驱动**是让程序能和数据库通信的库。在 Node 里可以用 `mysql2` 把这段 SQL 和参数发给 MySQL，再拿回结果。查询要经过网络并等待数据库处理，驱动的 Promise 接口会先返回一个 `Promise`。程序需要用结果做判断时就写 `await`，例如等查询完成，再看有没有查到记录。[mysql2 官方文档](https://sidorares.github.io/node-mysql2/docs)

## 配置是什么？为什么数据库地址要单独配置？

**配置是运行程序时提供给它的参数。** 同一套代码在自己电脑上可能连接本地测试库，部署后则要连接服务器上的库。查询语句可以完全一样，数据库地址和账号却要随环境变化。

| 常见配置 | 它回答的问题 |
| --- | --- |
| `DB_HOST`、`DB_PORT` | 去哪台机器、哪个端口找 MySQL 服务？ |
| `DB_NAME` | 这台 MySQL 上有多个数据库，要使用哪一个？ |
| `DB_USER`、`DB_PASSWORD` | 使用哪个数据库账号连接？ |

开发时常把这些值放在本机的 `.env` 文件里。Nest 的 `ConfigModule` 可以加载它们，其他组件通过 `ConfigService` 读取。把配置集中起来以后，换数据库地址只需改一处，真实密码也可以留在代码仓库之外。[Nest 配置文档](https://docs.nestjs.com/techniques/configuration)

**检查配置**和**尝试连接**发生在不同的时刻。比如端口写成 `abc`，程序启动时检查格式就能发现；端口写成 `3306`，格式正确，但那台机器有没有在运行 MySQL，得真的连接才能知道。排查问题时，这个区别比记配置项的名字更重要。

## 连接池是什么？为什么不用一次就新建一条连接？

一条**数据库连接**是程序与 MySQL 之间已经建立的通信通道。建立它要经过网络连接和身份验证。如果每次执行一条 SQL 都重新连接、查完立即断开，许多请求会把时间花在重复准备上。

**连接池是一组由驱动管理、可以反复使用的数据库连接。** 一次普通查询大致经历三个动作：

1. **取连接。** 有空闲连接就复用。没有空闲连接、数量还没达到上限时，池可以新建一条。
2. **执行 SQL。** 这条连接把语句发给 MySQL，等待结果。其他请求可以使用池里的其他连接。
3. **归还连接。** 使用 `pool.execute(...)` 做单次查询时，驱动会在完成后自动归还，供下个请求使用。

连接数上限的作用也就容易理解了。假设上限是 5，前五条连接都忙时，如果配置了等待，第六个查询就排队。**共享一个池**表示大家共用这套管理机制，池内仍然可以有多条连接同时工作。[mysql2 连接池说明](https://sidorares.github.io/node-mysql2/docs#using-connection-pools)

平时在 Nest 中，会在模块里用**工厂 Provider** 创建池。这里的“工厂”就是一个创建对象的函数：Nest 把配置传给它，它返回池。需要读写数据库的类通过依赖注入拿到同一个池。应用运行期间持续复用，应用关闭时统一释放。这是第 02 节学过的依赖注入在管理共享资源时的一种用途。

## Repository 是什么？为什么要单独放一层？

Repository 常译为**仓库**，在这里指项目中集中负责数据读写的类。它给其他代码提供“按 ID 查找”“保存”“更新”这些方法，内部决定查哪张表、用什么 SQL，以及如何把结果整理成程序使用的对象。

例如，数据库把创建时间这一列叫作 `created_at`，TypeScript 代码习惯叫它 `createdAt`。Repository 可以在读取时做一次转换，其他地方就能一直用 `createdAt`。以后调整数据库列名，只需要在知道表结构的地方修改。

| 你在考虑的问题 | 通常由谁负责 |
| --- | --- |
| 调用方提交的 ID 是不是整数？ | 请求入口的 Pipe。上一节的请求校验就在这里 |
| 根据这个 ID 去哪张表、取哪些列？ | Repository。它使用连接池执行 SQL |
| 查不到时，这个操作应该如何处理？ | Service。比如查询详情时抛出 404 |

Repository 的价值在于给数据访问提供一个稳定的调用方式。只有一条临时查询时，这个价值还不明显；当多个操作都要读同一张表、共用字段映射，或者要把内存存储换成 MySQL 时，把这些细节集中管理就能少改很多地方。[[20-后端/数据库/57-Repository数据访问|展开阅读 Repository 数据访问]]

## 已经做过请求校验，为什么数据库还有约束？

第 03 节讲的是**单次输入是否符合要求**。数据库约束还可以规定**存下来的多条记录之间必须满足什么关系**。邮箱很容易看出两者的区别：

- **邮箱格式正确**只需检查这一次传来的字符串，DTO 校验就能判断。
- **邮箱不能重复**要考虑表里已有的记录，以及别的请求正在写入的记录。两个请求可能同时查到“邮箱未使用”，然后同时尝试插入。给邮箱列加**唯一约束**后，MySQL 会拒绝重复的那次写入，应用再把这次冲突表达为 409。

把一条读取请求串起来，就是 **Service 提出要读什么 → Repository 组织 SQL → 驱动通过池里的连接访问 MySQL → 查询结果返回给 Service**。配置在程序启动时告诉它连接哪里；持久化则让下次启动的程序还能从那里读回同一条记录。
