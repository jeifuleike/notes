### 背景

原有 Obsidian 库按 `10-前端`、`20-后端`、`30-AI与Agent` 等领域分类，但缺三样东西：

- 临时区：对话结论和零散想法没有落点，过几天就丢。
- AI 可读层：Codex 每次都要重新摸索项目约定。
- Skill 管理：收藏的第三方 Skill 和知识库自身的 Skill 混在一起。

目标不是“多一个笔记文件夹”，而是让知识走完 **收集 → 判断 → 融合 → 发布**，并且这一步能重复执行。

### 目标与约束

- 人读知识与 AI 知识分开；收藏 Skill 与系统 Skill 分开。
- 不移动、不改写旧笔记；新增内容先进临时区。
- 正式发布必须人工批准；不自动 `git commit`。
- 不修改 `.obsidian/workspace.json`。
- 公司内容不得写入个人知识库。

### 架构

| 层 | 目录 | 读者 | 作用 |
|---|---|---|---|
| 临时区 | `00-Inbox/` | 人 + AI | 收集、审核报告、归档 |
| 人读知识 | `10`-`60` 领域目录 | 人 | 原理、教程、案例、复盘 |
| AI 知识资产 | `70-AI知识资产/` | AI | 工作流规范、工程约束、决策、项目上下文、来源 |
| 收藏 Skill | `80-Skill库/` | AI | 候选、已采用、已淘汰 |
| 系统机器 | `90-知识系统/` | 维护者 | 设计、config、模板、脚本、安装器、自身 Skill |

`90` 是机器层，不放正文，所以换电脑或复制到新库只需要搬这一套。

### 关键决策

1. 不整体安装现成项目，只借鉴 `obsidian-kb-skill` 的读写分离、preflight、doctor、来源追踪，自己造薄层。
2. Markdown 是唯一存储，Git 负责版本与回滚，Python 做确定性检查，Codex 只做判断与写作。
3. Skill：`kb-curator` 是唯一有写权限的 Skill，默认只写 `00-Inbox/`；`kb-query` 严格只读；`codex-asset-sync` 负责备份和恢复 Codex 资产。
4. 分级 L1-L4，只有 L3/L4 才生成 AI 操作卡，只有输入输出稳定的流程才生成 Skill 候选。
5. 审核阶段只出提案报告，用户回复“执行 1、3”后才改正式库。
6. 检索先用词法，不提前上向量库；QMD 按需接入，已留 `kb.py export` 接口。
7. 主动询问靠全局 `AGENTS.md` 行为规则和 Skill description；不使用 Stop hook 强制追加一轮。
8. 模板只给结构和引导注释，不堆章节；AI 卡硬上限 100 行。

### 工具链

`90-知识系统/脚本/kb.py` 提供 13 个子命令：`config`、`doctor`、`inbox`、`review`、`index`、`daily`、`audit`、`export`、`search`、`lint`、`capture`、`archive`、`log`。

模板 9 个：收集、QuickAdd 收集、人读笔记、AI 操作卡、工作流规范、Skill 评估、审核报告、工作日日报、休息日日报。

Skill 3 个：`kb-curator`、`kb-query`、`codex-asset-sync`；`~/.codex/skills` 使用真实副本，`notes` 只保存 `80-Skill库/Codex备份/skills/`。

### 自动化

- 日报：每天 06:00 计划任务 `Codex-KB-DailyNote` + 登录快捷方式补跑，按工作日/休息日选模板，已存在的非空文件不覆盖。
- 月度审计：Codex 自动化每月 1 日 09:00 跑 `kb.py audit`，只报告不改文件。
- 一键收集：QuickAdd `收集到 Inbox`，模板指向 `90-知识系统/模板/QuickAdd收集.md`。
- 首页：`kb.py index` 生成 `00-知识库首页.md`，静态双链 + Obsidian 反向链接。

### 验收方式

- `kb.py doctor`：目录、模板、Skill、安装文件完整性。
- `kb.py lint`：断链、重复标题、缺字段、AI 卡过期、Inbox 积压。
- `kb.py audit`：月度快照，有错误返回非零。
- `python -m unittest discover -s 90-知识系统/脚本/tests`：14 个端到端测试。

### 未来期望

- 让真实闭环跑起来：Inbox 持续有内容，审核报告能被批准执行，处理日志有记录。
- 公司电脑独立部署，`-Scope vault-only`，公司内容不进个人库。
- 补 2026 年法定假日与调休到 `daily.rest_days` / `daily.work_days`。
- 笔记量上来后接 QMD 做语义检索，词法检索保留兜底。
- 沉淀出“搭建新知识库”的标准流程，做到换一个领域只改 `config.json` 和内容。

### 复用到新知识库

1. 复制 `90-知识系统` 到新库，保留 `skills/`、`模板/`、`安装/`、`脚本/`。
2. 改 `config.json` 的 `vault`、`routing`、`daily.dir`。
3. 建 `00-Inbox/`、`70-AI知识资产/`、`80-Skill库/` 及领域目录。
4. 跑 `install-codex-kb.ps1`，装 Skill、hook、全局规则。
5. 在 Codex 里 `/hooks` 信任 `kb-capture-ask.py`。
6. 建日报任务和月度审计任务。
7. 先跑 `doctor` 和测试，再开始收集。

### 待办与风险

- 公司机未部署；`/hooks` 信任未确认。
- 真实发布闭环还没跑过，发布路径只在临时库验证。
- Git 尚未提交；两个日报模板在 Git 中显示为删除 + 新增，提交时识别为 rename。

## 06 前端测试浏览器分工与分层门禁

### 内容

1. **浏览器工具分工（`ego-browser` vs Playwright）**
   - **实时观察与真实联调用 `ego-browser`**：访问需要已登录会话或人工协助认证的运行系统、采集页面 DOM/计算样式/动效与截图基线、真实测试环境交互联调及问题复现，优先使用 `ego-browser`；未安装或不可连时回退到 Playwright 或受控浏览器并注明工具。
   - **自动化回归门禁固定用 Playwright**：E2E 与视觉快照门禁依赖路由拦截、脱敏固定 fixture、固定时钟与可复现比对，必须由 Playwright 执行；`ego-browser` 单次交互不替代自动化门禁，Playwright Mock 也不替代真实联调。
   - **共享浏览器安全约束**：使用 `ego-browser` 仅操作当前任务空间，不在全局清理 Cookie/缓存，不触发生产写接口；Windows PowerShell 下通过 UTF-8 `.mjs` 文件执行脚本，验证结束释放任务空间与页面。

2. **分层验证门禁与视觉快照收敛**
   - **单功能定向门禁**：按“本功能 + 受影响调用方 + 核心冒烟”执行一次测试构建并启动 preview，在单次测试进程中同时跑 E2E 与视觉用例，避免重复构建、重复起服和无差别全量回归。
   - **周期/共享层全量门禁**：每累计交付若干功能（如 3 个）、发版前，或修改共享底座且影响范围不明时执行一次全量门禁。
   - **视觉证据收敛**：自动视觉回归收敛为 2–4 张能区分主要布局的核心稳态；控件 hover 位移、颜色、透明度与过渡参数改由 E2E 行为和计算样式断言覆盖；功能规格正文保持精简，原始测量数据通过链接引用。

3. **按验收场景并行开发、测试与 UI 采集**
   - 简单页面由同一实现者完成实现与本功能测试，减少上下文交接损耗。
   - 测试准备可与开发重叠或需独立视角时，契约稳定即并行分派测试编写 fixture 与拦截，首个可运行场景就绪即开始执行；影响实现的 UI 证据在冻结前采齐，补充对照图可并行。

### 为什么可能有用

- 适用于所有带前端 UI 交付、系统复刻或需要真实登录态联调的项目，既降低单功能验证耗时，又避免 Playwright 硬处理登录态或用非确定性浏览器脚本替代回归门禁。
- 已同步补充至临时区待整理 Skill 草稿：[[80-Skill库/候选/feature-delivery/SKILL]]、[[80-Skill库/候选/multi-agent-collaboration/SKILL]]。

目标：写给第一次学的人，让其看完能独立做，不是给已经会的人列复习提纲。“详细”有两个验收条件：该主题的基础知识要覆盖全；完成当前任务要用到的每个概念要解释透。增加术语数量不能代替其中任何一项。

### 一章的写作顺序

1. **定起点。** 写明读者需要已经会什么、这次要解决什么问题、最后能独立交付什么。第一次出现的工具交代在哪里操作；已有经验只作旁注，删掉旁注，主线也应读得懂。
2. **画知识地图。** 先回答主题是什么、可以按什么依据分类、各类别是什么关系。不要把不同维度混为一谈；例如“整数”回答能存什么，“局部变量”回答在哪里声明。总览可以先看不背，但不能用一个例子冒充全貌。
3. **逐类展开。** 从旧办法的局限引出新概念。说明它解决什么、写法各部分什么意思、何时选它、与最相似的概念有什么区别。长主题分节或分篇，不删掉基础去凑篇幅。
4. **从最小结果走到完整例子。** 给出环境、文件、运行位置和预期结果。标清完整文件与局部替换片段。每一步只引入一个关键变化，先预测再观察；用具体输入逐行追踪值、调用或产物，而不是贴出成品再概括。
5. **用错误检验解释。** 给一个可控反例：改哪一处、错误在哪一步出现、怎样辨认、怎样恢复；也要考虑程序照常运行但答案不对的情形。
6. **把决定权还给读者。** 从跟做、预测到关掉示例独立做。题目给输入、约束和预期结果；提示与核对放在题目之后。读完、抄完、作者验证过，都不等于读者已掌握。

### 交稿检查

- 从空白开始，读者能否知道第一步在哪里做？每个陌生词能否就地理解，或明确知道现在为什么可以先不管？
- 能否指出一个“只改一处”的前后对比，并解释为什么输出变了或没变？任务能否换一组输入验收？
- 教程是否区分实测和预期？如果需要外部环境而没跑通，就写清验证边界，不把配置检查当作运行成功。

### 复用场景与来源

写新语言、工具、框架的入门章节，或把速查笔记改成教材时使用。已确认样板：[[20-后端/Java/01-变量类型与输出]]。
