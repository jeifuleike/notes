# Java 后端课程编写要求

本目录的读者有 Vue、TypeScript、Express、Nest 和 MySQL 实践经验，正在把 Java 作为主力后端语言。选题、类比起点和验收任务见 [[20-后端/Java/00-Java后端学习路线]]。可以用熟悉的前端或 Nest 场景帮助理解，但 Java 本身的概念、规则和运行机制必须独立讲清楚；不能把 TypeScript 知识当作学习 Java 的前置条件。

## 零基础教材优先

通用结构与验收以 [[70-AI知识资产/工作流规范/05-零基础学习笔记编写]] 为准；Java 的解释颗粒度参考 [[20-后端/Java/01-变量类型与输出|第 01 节]] 和 [[20-后端/Java/03-类对象与列表|第 03 节]]。笔记要让读者能从空白代码开始理解和验证，而不是只提供语法速查表。

## 一节课怎样展开

1. **给一个实际问题。** 开头点明读完可以做什么。沿用团队任务项目中的用户、项目、成员、任务和变更记录。新需求尽量建立在上节可运行的结果上。
2. **先解释概念，再解释语法。** 说明这个概念解决什么问题、它和相邻概念有什么区别，再逐段解释关键语法。不能只贴一段代码、逐行翻译，却不解释设计目的。
3. **讲清执行过程和边界。** 对 `new`、构造方法、方法调用、类型转换、异常、依赖注入等关键机制，顺着一条调用路径解释“谁创建、谁调用、什么时候执行、由谁检查、什么时候失败”。区分编译期检查和运行期行为。
4. **区分相近概念。** 优先用 Java 例子比较两种写法。需要时补充 TypeScript、Nest 或 Node 对照，并明确类比的边界，不能把两种语言的底层机制说成完全相同。
5. **交付最小可运行示例。** 标清 JDK 或依赖前提、文件名、包和执行目录。命令适用于 Windows PowerShell。给出关键输出、HTTP 状态或数据库结果。若代码只是局部片段，明确说明它不是完整文件；声称可运行的代码必须给出完整上下文。
6. **安排一次可观察的失败。** 写清“先预测什么、改变哪一个条件、从哪里看结果、怎样恢复”。按当节主题选失败点，例如编译期类型错误、运行期异常、事务回滚或外部服务超时。测试过的代码可以报告实际结果；未执行的步骤标为预期。
7. **留一个独立改动。** 给输入、约束和可检查的结果，留出自己选择实现的空间。末尾给出能进入下一节的判断标准。写出了教材与读者完成练习分别记录。

## 知识解释的最低要求

- 首次出现的重要 Java 关键字或语法，至少解释用途、所在位置和它影响的对象或行为。
- 不要省略容易造成误解的前提。例如：构造方法没有返回类型；只有未声明任何构造方法时才自动提供默认无参构造方法；`final` 引用不等于对象不可变；接口引用的编译期可见成员由引用类型决定。
- 讲类型、对象和引用时，要区分变量声明、对象创建、引用复制和对象内部状态变化。
- 讲访问控制时，要说明同类、同包、子类和不同包之间的可见性；讲接口时，要说明抽象方法、默认方法、静态方法、常量和实现关系。
- 讲集合时，要区分接口与具体实现、元素类型约束、容器是否可修改，以及元素对象是否可修改。
- 讲数值类型时，要区分整数除法、浮点近似表示、精度与格式化显示；不能把 `printf("%.2f", value)` 说成修改了原变量精度。
- 讲方法时，要区分形参和实参、返回和打印、重载和重写；解释 Java 参数传递时必须准确说明引用值的复制。
- 讲构建时，要区分源码、字节码、JVM 执行、类路径和构建工具；旧产物存在不代表当前源码编译成功。
- 讲测试时，要区分测试框架、构建工具、依赖和插件；明确一条测试实际覆盖了哪条调用路径，以及它没有验证什么。
- 重要结论要配合反例或失败实验，避免只靠背诵表格。
- 可以提供知识地图和对照表，但不能用表格替代必要的原理解释、代码走读和实验。

## 控制深度与章节边界

- 语法课讲到能运行、能读懂错误；面向对象课讲清对象、类型和调用边界；框架课讲清对象创建、代理和调用边界；并发与事务课检查最终状态；观测与排障课拿日志、指标、执行计划或线程快照支持判断。
- 每节集中解决一个主问题。遇到与本节主题紧密相关、且后续工程必需的基础机制，可以在同一节系统展开；不要为了追求短小而删掉必要的基础解释。
- 不要把后续章节的深入内容提前讲完。当前节先建立准确模型，复杂规则在路线对应课次继续验证，并通过链接说明后续位置。
- 已有基础用简短对照带过；遇到跨语言差异、故障或容易写出错误代码的地方可以放慢。普通课预计 60～90 分钟，允许实验拆成两次。
- 单测、真实数据库测试和本地实验各写明能证明什么。业务涉及并发、重试或权限时，验收需覆盖相应的失败路径。

## 示例代码与命令质量门禁

每次修改笔记后，逐项检查：

1. **版本一致。** 本课程以 JDK 21 为基准。若使用较新语法，必须确认它在 Java 21 中可用；不要无意中混入更高版本才支持的语法。
2. **文件与类名一致。** 有 `public` 顶层类时，文件名与类名完全一致；包声明、目录结构和运行时完整类名要互相匹配。
3. **代码块上下文明确。** 说明是完整文件、类内部片段、方法内部片段还是命令行内容。不能让读者把方法声明误放进 `main`，或把 PowerShell 命令粘贴进 Java 文件。
4. **命令有执行位置。** 每条命令都说明从哪个目录运行；涉及 `-d`、`-cp`、`target`、`out` 时，解释输入和输出路径。
5. **结果可核对。** 给出预期输出或关键报告字段。若没有实际执行，不得写“实测通过”；应标为预期结果。
6. **实验可恢复。** 故意制造错误后，必须给出恢复方式，避免读者把坏代码留到下一节。
7. **前后内容一致。** 代码中的类名、方法名、包名、目录、依赖版本和命令必须在整篇笔记中一致。
8. **链接可追踪。** 新增或改名章节后，更新学习路线和相邻章节的链接；Obsidian 链接保留现有库内路径风格。

## 文件维护要求

- 优先在现有章节上增补和重组，不随意推翻已有学习路线、业务案例、JDK 版本或命名。
- 修改章节后同步检查学习路线中的章节标题、先修关系、验收目标，避免目录描述与正文不一致。
- 检查与相邻章节的重复：本节只建立概念，后续章节再深入时应注明“本节已学过什么”和“本节新增什么”。
- 使用一致的术语、类名、文件名和业务示例。完整示例应能按文中命令运行；不要在同一文件中放置多个同名顶层类。
- 修改多个文件时，先确定共同术语和项目版本，再批量调整；完成后重新检查所有相互引用的文件。

## 建议的章节结构

不是每节都机械套用全部标题，但重要章节应覆盖相应环节：

1. 本节解决的问题与学习目标。
2. 先建立概念地图，解释为什么需要该机制。
3. 从最小代码开始，逐步引入语法。
4. 逐行解释关键代码与执行顺序。
5. 与容易混淆的概念对比。
6. 结合当前贯穿项目完成一个完整示例。
7. 故意制造一个典型错误，解释发生阶段、错误原因和恢复方式。
8. 给独立练习、预期结果和完成标准。
9. 说明本节与下一节的衔接。

## 示范：第 16 节怎样写

从“Express Service 把同一条连接传给两个 Repository”讲起。让读者预测“Spring 里两个 Mapper 都没接收连接参数，第二次写失败后，第一条记录会怎样”。展示一个 Service 和两次写入，说明代理调用与事务管理的关系，在独立连接中查表。最后调整调用位置，让读者用前后结果解释事务边界。
