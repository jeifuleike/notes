# 第 03 节　Nest 怎么检查请求参数？

**请求校验，就是在后端使用一份外部数据之前，先确认它符合接口的要求。** 比如接口接收邮箱，至少有两个问题要问：调用方传了这个字段吗？传来的字符串符合邮箱格式吗？这两个问题只看输入就能回答，无需查数据库。

在 Nest 里，你会经常一起看到三个名字：**DTO 描述输入，ValidationPipe 执行检查，异常处理决定出错时怎么回复。** 它们之所以一起出现，是因为一条规则从“写下来”到“真的对请求生效”，中间有几个不同的步骤。

## 有了 TypeScript，为什么还需要校验？

你写下 `email: string` 时，TypeScript 会在**检查代码时**提醒你：这里应该放字符串。如果你在自己的代码里直接传一个数字，编辑器就可能标红。

但 HTTP 请求是程序**运行时**才从网络收到的。浏览器、手机或者接口工具都可以发来 `{"email": 123}`。这些数据没有经过你项目的 TypeScript 检查。即使对方传来的是字符串，`"明天下午"` 也满足“字符串”这个类型，却不符合邮箱格式。

这就是后端需要校验的原因。前端校验让填写者及时看到提示，后端校验让所有调用方都要遵守同一套输入要求。

## DTO 是什么？装饰器又做了什么？

DTO 是 *Data Transfer Object*，中文叫**数据传输对象**。这里说的“请求 DTO”，描述的是**调用某个接口时可以提交哪些数据**。写 DTO 时，先站在调用方的角度想：它需要填什么，哪些必填，哪些可以省略？

Nest 里常用一个类来写请求 DTO。看一个字段就够了：

```ts
class ContactDto {
  @IsEmail()
  email!: string;
}
```

这几行可以分开读：

- `ContactDto` 给这组输入起了名字。把它标在 Controller 的请求体参数上，Nest 就能在具备装饰器类型元数据的编译配置下找到这个类。
- `email!: string` 声明字段及其 TypeScript 类型。`!` 是给编译器看的，意思是这个属性会在稍后赋值。
- `@IsEmail()` 来自 `class-validator`。这种写在字段上的标记叫**装饰器**。它登记一条可在运行时读取的规则：这个值必须符合邮箱格式。

为什么常用 `class`？因为程序运行时类还在，校验工具可以找到它和它的规则。TypeScript 的 `interface` 编译后会消失。至于规则**什么时候执行**，要看下一步。

## Pipe 是什么？平时什么时候用它？

Pipe 是 Nest 在调用 Controller 方法**之前**处理参数的一种机制。可以把它理解成一个函数：接收原始值，处理成功就向下传值，处理失败就抛出异常。最常见的两种用途是**校验**和**转换**。[Nest 官方 Pipe 说明](https://docs.nestjs.com/pipes)

| 你想做什么 | 常用工具 | 会发生什么 |
| --- | --- | --- |
| 检查一组表单字段 | `ValidationPipe` | 按 DTO 上的规则逐项检查。邮箱格式错误时，默认返回 400，Controller 方法不会执行 |
| 把路径参数变成整数 | `ParseIntPipe` | URL 里的 `"12"` 变成数字 `12`，传来 `"abc"` 则返回 400 |

**日常用法**是启动时通过 `app.useGlobalPipes(new ValidationPipe())` 注册校验，然后在需要接收请求体的路由上写 `@Body() input: ContactDto`。前一句启用检查，后一句指定这次检查哪份规则。工具在启动时注册一次，检查在每次请求到来时执行。[Nest 官方校验说明](https://docs.nestjs.com/techniques/validation)

规则要多严格，取决于接口怎么约定。例如一个 DTO 只接受邮箱，调用方却多传了字段。开启 `whitelist: true` 会移除没有校验装饰器的字段；再开启 `forbidNonWhitelisted: true`，便会拒绝整个请求。再如局部更新，“没传邮箱”通常表示保留原值，而 `{"email":null}` 是明确传了空值。设计接口时要分别决定是否接受这两种输入。

## 校验失败以后，异常和 Filter 是什么关系？

**异常**表示当前操作无法按正常流程完成。Pipe 发现输入不符合约定，可以抛出 `BadRequestException`。Nest 自带异常处理，会把它转成 HTTP 响应。状态码告诉调用方发生了哪类问题，响应体里的消息可以告诉它该改哪里。

| 情况 | 为什么会失败 | 常见状态码 |
| --- | --- | --- |
| 邮箱格式不对、ID 应为整数却传了字母 | 仅看请求值就能发现问题 | 400 |
| ID 是合法整数，但查不到对应记录 | 输入通过了校验，查询后才知道结果 | 404 |
| 处理时发生意外故障 | 服务端未能完成请求 | 500 |

**Exception Filter（异常过滤器）** 是 Nest 留给开发者定制错误响应的地方。日常写接口，使用内置异常就能返回对应的状态码。等到团队希望每个接口都返回相同结构的错误消息，或者希望集中记录意外故障，再写一个 Filter 就有了具体目的。它处理的是请求中抛出的异常，正常返回的数据不会经过它。[Nest 官方异常处理说明](https://docs.nestjs.com/exception-filters)

把这几个概念连起来读一次：**DTO 上写着“邮箱要合法”，ValidationPipe 在请求到来时检查，不合法就抛异常，Nest 把异常回复给调用方。** 自定义 Filter 是最后一步可以选择的扩展。
