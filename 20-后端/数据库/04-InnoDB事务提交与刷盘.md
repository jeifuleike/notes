# InnoDB 事务提交、内存数据页与刷盘

本文专门说明一次写入何时返回成功，以及内存数据、日志和磁盘数据文件之间的关系。索引结构与节点维护见 [[20-后端/数据库/03-MySQL索引核心知识整理]]，不在此重复。

## InnoDB 是什么

MySQL 是关系型数据库管理系统，InnoDB 是其内部的存储引擎，不是另一款独立数据库。

MySQL 负责解析 SQL、规划执行等工作，InnoDB 负责表的数据组织、索引、事务、锁和故障恢复等。建表时的 `ENGINE=InnoDB` 表示这张表由该引擎管理。

## 一次添加、修改 SQL，究竟等什么完成才返回

先以普通自动提交的写入为例：

```text
后端发送 INSERT / UPDATE
          ↓
数据库定位相关页，必要时从磁盘读入内存
          ↓
处理锁、检查约束、修改数据与相关索引，生成日志
          ↓
自动提交，满足配置要求的日志持久化条件
          ↓
数据库返回成功，后端 await 结束

修改后的数据页由数据库择机写回磁盘数据文件
可能在返回前发生，也可能在返回后发生
```

关键是：返回前，数据库已经执行修改，不是仅把“以后要修改的任务”丢进队列。只是修改过的所有数据页，不要求都在返回前写回磁盘。

### 内存里保存的是什么

InnoDB 的 Buffer Pool（缓冲池）缓存数据页和索引页。执行修改时，相关页中的内容会改变；内存内容与磁盘版本不一致的页称为脏页。这里的“脏”表示尚未同步写回，不表示数据错误。

此外还有日志相关缓冲区，不能把“内存里的新数据”和“日志里的修改记录”混成同一种东西。

### 日志刷盘与数据页刷盘不同

| 动作 | 作用 |
| --- | --- |
| 日志刷盘 | 将恢复所需的日志可靠持久化 |
| 数据页刷盘 | 把修改后的页写回数据文件 |

默认 `innodb_flush_log_at_trx_commit=1` 时，事务提交要求相关 redo 日志写入并刷到磁盘。这里描述的是 redo 的默认持久化条件，不是对所有部署配置的保证；实际持久性还依赖存储系统正确执行刷盘请求。

redo log 是重做日志，可用于故障恢复。因此即使部分数据页尚未写回，数据库重启时仍可利用已持久化的日志恢复已提交修改。

不能理解为“先改内存、直接成功返回、之后才做任何磁盘写入”；也不能理解为“返回成功时所有数据文件都更新完了”。

## SQL 执行完成与事务提交有什么区别

| 情况 | 一条写入 SQL 返回成功意味着什么 |
| --- | --- |
| 默认自动提交、未显式开启事务 | 该语句成功执行，并完成它的自动提交 |
| 显式事务中 | 该语句执行成功，但整个事务仍可能尚未提交 |

显式事务示例：

```text
开启事务
  ↓
插入项目成功：语句结束，但未提交
  ↓
插入 owner 成员成功：语句结束，但未提交
  ↓
commit 成功：事务提交完成
  ↓
后端可以返回业务成功
```

这几步必须使用同一数据库连接。SQL 执行完成、事务提交、所有脏页写回数据文件，是三个不同概念。

## 数据页没刷盘，其他用户读到新值会不会出错

读到已经提交、尚未刷盘的新值是正常行为，不会因为它暂时还在内存中就变成错误数据。

例如某值从 100 修改成 200：

```text
内存数据页：200
磁盘数据页：暂时还是 100
事务状态：已提交
相关 redo 日志：已按配置持久化
```

数据库查询会结合缓冲池中的页与事务可见性规则读取数据，不是每次只去读磁盘上的旧文件。内存和磁盘由同一个数据库引擎统一管理。

| 数据状态 | 如何理解 |
| --- | --- |
| 已提交，数据页未刷盘 | 可以被符合可见性规则的查询读到，是正常行为 |
| 未提交，可能回滚 | 读到其他事务的这种修改叫脏读 |

READ COMMITTED 和 REPEATABLE READ 隔离级别下，普通查询不会脏读其他事务的未提交修改。查询可能读取历史已提交版本；锁定读、写操作等也可能等待锁。

所以判断能否读取，重点是事务状态、隔离级别、快照与查询类型，不是数据页是否已经写回磁盘。也不能反过来说“提交后所有已有事务立刻看到最新值”。
