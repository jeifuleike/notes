# 索引与 B+ Tree

从索引解决的问题开始，接着理解 B+ Tree 结构，再学习聚簇与二级索引、回表、覆盖与联合索引、写入维护、命令和执行计划。原来的两篇内容在本篇连续阅读。

## 1. 数据库为什么需要索引

索引通过有序的数据结构减少查找所需的扫描量。是否需要性能索引没有固定行数门槛，要结合查询频率、数据分布、扫描量、读写比例与执行计划判断。小表扫描可能更便宜；主键与必要的唯一约束不应等数据量大才设置。

以一条主键查询为例，若实际使用主键索引，就不是从第一行逐个扫描。只有在说明“没有可用索引的查询”时，才适合用逐行查找作对照。

------------------------------------------------------------------------

## 2. B+ Tree 索引结构

MySQL InnoDB 常用 B+ Tree 作为索引结构。

核心思想：

> 先找到范围，再逐层缩小搜索。

例如：

                  [100 | 500]
                 /      |      \
              <100   100~499   >=500

查询：

    id = 238

过程：

    根节点
     ↓
    判断 238 属于 100~499
     ↓
    进入对应节点
     ↓
    继续查找
     ↓
    找到数据

优势：

-   不需要遍历所有数据
-   查询复杂度低
-   适合大量数据

------------------------------------------------------------------------

## 3. 字符串如何定位到索引节点

普通主键和二级索引通常用 B+ 树组织。上层节点保存分界信息用于指路，叶子节点保存索引记录。

邮箱虽然看起来没有规律，也可以比较大小。先用字母顺序理解：alice 排在 mike 前，nancy 排在 mike 与 tom 之间。真实 MySQL 根据字段的排序规则（collation）比较字符串，大小写、重音等处理取决于该规则，不一定是简单比较字符编码。

```text
              分界值：[mike | tom]
                 /       |
           小于 mike   mike 到 tom   大于等于 tom
```

查询 nancy 时，比较分界值后走中间分支。树不需要先知道它属于什么邮箱域名或业务大类。

分界值与节点由数据库动态维护，不是开发者预先规定“a 开头一类、b 开头一类”。

## 4. 聚簇索引

在 InnoDB 中：

通常：

    PRIMARY KEY
            ↓
    聚簇索引

特点：

> 叶子节点保存完整数据行。

例如：

    id = 100

    username = Tom
    email = tom@test.com
    status = 1

全部存储在聚簇索引叶子节点。

查询：

``` sql
SELECT *
FROM users
WHERE id = 100;
```

过程：

    主键索引
     ↓
    找到 id=100
     ↓
    直接返回整行数据

不需要再次查询。

------------------------------------------------------------------------

## 5. 二级索引（普通索引或唯一索引）

例如：

``` sql
CREATE INDEX idx_email
ON users(email);
```

这是一棵新的 B+ Tree。

但是叶子节点不是完整数据。

而是：

    email + 主键id

例如：

    tom@test.com → 100

为什么保存主键？

因为 InnoDB 的真实数据在聚簇索引中。

------------------------------------------------------------------------

## 6. 回表

查询：

``` sql
SELECT *
FROM users
WHERE email='tom@test.com';
```

执行过程：

    email普通索引

            ↓

    找到：
    email=tom@test.com

    得到：
    id=100

            ↓

    根据id查询主键索引

            ↓

    获得完整数据

这个过程叫：

> 回表

原因：

普通索引没有保存完整数据，需要再次访问聚簇索引。

------------------------------------------------------------------------

## 7. 覆盖索引

如果查询需要的字段全部存在索引中：

就不需要回表。

例如：

索引：

    email + id

查询：

``` sql
SELECT id,email
FROM users
WHERE email='tom@test.com';
```

需要：

    id ✅
    email ✅

索引已经包含。

流程：

    普通索引
     ↓
    直接返回

这叫：

> 覆盖索引

------------------------------------------------------------------------

## 8. 联合索引

例如：

``` sql
CREATE INDEX idx_project_status
ON tasks(project_id,status);
```

不是两个索引：

    project_id索引
    +
    status索引

而是一棵：

    (project_id,status)

联合排序的 B+ Tree。

排序规则：

    先按照 project_id 排序

    project_id相同

    再按照 status 排序

例如：

    (1,0)
    (1,1)
    (1,2)

    (2,0)
    (2,1)

------------------------------------------------------------------------

## 9. 最左前缀原则

假设：

``` sql
INDEX(a,b,c)
```

可以理解为：

    a
     ↓
    b
     ↓
    c

可以使用：

``` sql
WHERE a=1
```

✅

``` sql
WHERE a=1 AND b=2
```

✅

``` sql
WHERE a=1 AND b=2 AND c=3
```

✅

但是：

``` sql
WHERE b=2
```

通常无法充分利用。

原因：

索引首先按照 a 排序。

不知道 a，就无法快速定位 b。

注意：

SQL 条件顺序不重要：

``` sql
WHERE b=2 AND a=1
```

仍然可以使用：

    INDEX(a,b)

因为优化器会处理。

## 10. 写入如何维护索引

普通 INSERT 不会每次重建整棵索引树；正常写入是局部维护已有索引。

1. 根据索引键找到合适的叶子节点。
2. 检查必要约束，在节点中按顺序插入记录。
3. 有空间时通常只修改相关页。
4. 空间不足时，可能拆分节点并更新父节点分界信息。
5. 如果父节点也需要拆分，继续向上调整；根节点拆分可能使树增高。

这与给已有表新增索引、显式重建索引或某些表结构变更不同，普通 INSERT 不会每次重建全部索引。

索引维护由数据库在处理写入时负责，不需要 Node 后端再调用一次“刷新索引”，也不是等定时任务把树重新生成。

| 操作 | 需要理解的索引维护 |
| --- | --- |
| INSERT | 写入行，并维护涉及的主键和二级索引 |
| UPDATE 非索引列 | 修改行数据，通常不需要改变未受影响的二级索引键 |
| UPDATE 索引列，例如 email | 维护旧键与新键的对应记录；唯一索引还需检查冲突 |
| DELETE | 记录删除并维护相关索引；InnoDB 的标记删除与后台清理不一定同时完成 |

索引维护参与事务，回滚后不能留下一个对后续查询有效的孤立索引项。

部分符合条件的非唯一二级索引修改，在启用相关机制时可能先记录到 change buffer，再合并到索引页。这是内部优化，不意味着业务可以读到随意过时的索引结果。邮箱唯一索引需要在写入时检查唯一性，不能按同样方式理解为延后检查。

索引能减少查询扫描，但也占空间、增加写入维护成本，所以不是每个字段都应该建索引。

关于 SQL 何时返回、redo 与数据页刷盘，见 [[20-后端/数据库/55-InnoDB提交与刷盘]]。索引创建与 EXPLAIN 命令示例见本篇后面的对应章节。

## 11. Index：根据查询路径设计索引

索引阶段先拿出第一步的查询清单。

```sql
SELECT id, title, status, created_at
FROM tasks
WHERE project_id = ? AND status = ?
ORDER BY created_at DESC, id DESC
LIMIT ?;
```

对应候选索引可以研究：

```sql
CREATE INDEX idx_tasks_project_status_time
ON tasks(project_id, status, created_at, id);
```

先用项目与状态定位，再考虑排序和分页。id 作为时间相同情况下的稳定排序依据。这里只是候选方案，是否使用、是否避免额外排序要通过 EXPLAIN 和实际数据确认。

如果另一个高频查询没有 status 过滤，这个联合索引未必同时很好地满足它的排序需求。不能把所有可能的列都加进一个超大联合索引。

成员表主键 (project_id, user_id) 方便按项目定位成员；从 user_id 反查所有项目则要单独检查所需访问路径。外键可能已经带来了支持索引，应先检查实际 SHOW INDEX，避免机械添加重复索引。

索引会增加写入维护和存储成本。覆盖索引、最左前缀与执行计划见本篇对应章节；内部树结构与节点维护见本篇前面的对应章节。本节从需求推导候选方案。

**本阶段检查**：每个性能索引有对应查询吗？是否看过执行计划和扫描量？唯一索引是否承担正确性约束？新增索引对写入有何影响？

## 12. 索引：创建、查看、删除

### 查看表的索引

```sql
SHOW INDEX FROM tasks;
```

### 创建单列索引

```sql
CREATE INDEX idx_practice_project_id
ON sql_practice_tasks(project_id);
```

### 创建联合索引

```sql
CREATE INDEX idx_practice_project_status
ON sql_practice_tasks(project_id, status);
```

联合索引字段的**排列顺序**很重要，常见查询：

```sql
WHERE project_id = 100

WHERE project_id = 100 AND status = 1
```

通常更容易利用 `(project_id, status)` 这个索引。

只使用 `WHERE status = 1` 时，一般不能像从最左列开始那样高效定位，但 MySQL 某些情况下可能选择 **Index Skip Scan（跳跃扫描）** 等访问策略；不能把“最左前缀”理解为不符合就绝对不会用索引。

### 删除索引

```sql
DROP INDEX idx_practice_project_id
ON sql_practice_tasks;
```

注意：索引名称不等于字段名称；`idx_practice_project_id` 是索引名，`project_id` 才是表字段名。

## 13. EXPLAIN

EXPLAIN 用来查看：

> MySQL 准备如何执行 SQL。

使用：

``` sql
EXPLAIN
SELECT *
FROM users
WHERE email='test@qq.com';
```

它不会真正查询数据。

而是返回执行计划。

重点关注：

### key

实际使用的索引。

例如：

    key:
    idx_email

表示使用：

    idx_email

### rows

预计扫描行数。

例如：

    rows:10000000

表示预计检查大量数据。

### type

查询方式。

常见：

#### ALL

全表扫描：

    一行一行检查

#### ref

通过索引找到一批数据。

#### range

范围查询。

------------------------------------------------------------------------

### 进一步分析实际查询


### 只查看预计执行计划

```sql
EXPLAIN
SELECT *
FROM tasks
WHERE project_id = 100;
```

关注：

| 字段 | 意思 |
| --- | --- |
| `type` | 访问方式，如 `ALL`、`ref` |
| `possible_keys` | 优化器认为可能使用的索引 |
| `key` | 最终选择的索引 |
| `rows` | 预计检查的行数（估算值） |
| `Extra` | 附加执行信息，例如 `Using where` |

`type = ALL` 常代表全表扫描；`key = NULL` 表示此节点未选择索引。但**全表扫描不等于一定慢**，要结合表大小和查询选择性。

### 实际执行并查看耗时

```sql
EXPLAIN ANALYZE
SELECT *
FROM tasks
WHERE project_id = 100;
```

可能看到：

```text
Index lookup on tasks using idx_project_id (project_id=100)
(actual time=0.236..2.02 rows=1027 loops=1)
```

解读：

- `Index lookup`：通过索引查找。
- `actual time=0.236..2.02`：此执行节点从产出第一条结果到产出最后结果的时间信息，单位毫秒。
- `rows=1027`：该节点实际输出约 1027 行。
- `loops=1`：该节点执行了一次。
- `cost`：优化器使用的**相对成本单位**，不是毫秒。

`EXPLAIN ANALYZE` **确实会执行查询**，不能把它当作只查看计划；分析修改性语句时尤其需要谨慎。

### 为什么有时全表扫描也快？

对 `WHERE status = 1` 而言，如果匹配全表约三分之一的记录，而查询还需要 `SELECT *`，走二级索引可能需要大量回表，优化器就可能认为全表扫描更划算。

对 `WHERE project_id = 100` 而言，如果只匹配约 1000 条，在百万行数据里通常更适合走索引。

## 14. IGNORE INDEX / FORCE INDEX：索引提示

你前面实验过这组语句：

```sql
-- 正常：让优化器自主选择索引
EXPLAIN ANALYZE
SELECT *
FROM project_management.tasks
WHERE project_id = 100;
```

```sql
-- 实验：不允许使用指定的两个索引
EXPLAIN ANALYZE
SELECT *
FROM project_management.tasks
IGNORE INDEX (idx_project_id, idx_project_status)
WHERE project_id = 100;
```

`IGNORE INDEX` 影响的是**当前 SQL 的索引选择**，**不会删除索引或改动表结构**。如果还有其他可用索引，优化器仍可选择其他索引。

其他两种提示：

```sql
-- 提示优化器使用所列索引作为候选
SELECT * FROM tasks USE INDEX (idx_project_id)
WHERE project_id = 100;

-- 强烈倾向使用该索引，但不是任何情况下都绝对强制
SELECT * FROM tasks FORCE INDEX (idx_project_id)
WHERE project_id = 100;
```

**建议**：正常业务优先让优化器选择；索引提示更适合调试、对照测试和经过验证的特殊场景。
